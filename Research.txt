The growing prevalence of integrating Large Language Models (LLMs) in software development has created many security risks, including susceptible code synthesis, abusing dormant security vulnerabilities, and challenges regarding discovery and fixing vulnerabilities caused by the models. Currently adopted security methods focus on output vulnerability detection, static analysis methods from traditional software security, or merely rely on individualized interpretability methods which lack capacity to bridge the internal features of the LLMs to vulnerability-worthy features and corresponding security implications. To fill this gap, this paper proposes CRAFT-Sec, an explainable multi-feature security framework to assist in vulnerability detection, mitigation, explainable localization, and the automatic fixing of code produced by LLMs. The framework proposes to merge multi-feature vulnerability detection with interpretable structure based on Sparse Autoencoder (SAE) in order to establish security-relevant latent representations and learn about their relations to vulnerable code generation. In addition, feature interaction analysis is used to analyze the combined effect of selected internal model features jointly in causing the security vulnerabilities. The learnings will be combined with static and dynamic program analysis to validate the identified vulnerabilities; pinpoint their exact locations; and generate rationalizing security explanations. Next, an automated repair driver will be proposed to generate security-oriented code changes while retaining functional correctness and changes to unintended behavior. The framework will be assessed through controlled experiments with existing vulnerability benchmarks, different LLMs, and a set of representative Cloud Weakness Enumeration (CWE) categories. The evaluation will take into account the detection efficiency, localization, repair effectiveness, functional correctness, interpretability, and computational cost. As a result, CRAFT-Sec seeks to fill the gap between high-level interpretability of models and actual software security, and it aims to establish a single and interpretable basis for creating LLM-assisted code generation systems in a more secure and transparent way.
Abstract
The increasing integration of Large Language Models (LLMs) into software development has introduced significant security challenges, particularly concerning the generation of vulnerable code, exploitation of latent security weaknesses, and the difficulty of identifying and repairing model-induced vulnerabilities. Existing security approaches predominantly rely on output-based vulnerability detection, conventional static analysis, or isolated interpretability techniques, which often lack the ability to establish connections between internal model representations, vulnerability-inducing features, and their corresponding security consequences. To address these limitations, this paper proposes CRAFT-Sec, an explainable multi-feature security framework designed to support vulnerability detection, prevention, explainable localization, and automated repair in LLM-generated code. The proposed framework integrates multi-feature vulnerability detection with Sparse Autoencoder (SAE)-based interpretability to identify security-relevant latent representations and investigate their relationships with vulnerable code-generation behaviors. Furthermore, feature interaction analysis is employed to examine how combinations of internal model features contribute to security weaknesses. These insights are integrated with static and dynamic program analysis to validate detected vulnerabilities, identify their precise locations, and generate interpretable security explanations. Subsequently, an automated repair component is proposed to produce security-oriented code modifications while preserving functional correctness and minimizing unintended behavioral changes. The framework will be evaluated through controlled experiments using established vulnerability benchmarks, diverse LLMs, and representative Common Weakness Enumeration (CWE) categories. Evaluation will consider detection effectiveness, localization accuracy, repair success, functional correctness, interpretability, and computational overhead. CRAFT-Sec aims to bridge the gap between model-level interpretability and practical software security, providing a unified and explainable foundation for developing more secure, transparent, and reliable LLM-based code generation systems.
Keywords: Large Language Model Security; Vulnerability Detection; Mechanistic Interpretability; Sparse Autoencoders; Feature Interaction Analysis; Explainable Artificial Intelligence; Automated Program Repair; Secure Code Generation.






















1. INTRODUCTION
1.1. Background and Motivation
Large Language Models (LLMs) have emerged as a transformative technology in artificial intelligence, demonstrating remarkable capabilities in natural language understanding, reasoning, and automated code generation. Recent advances in transformer-based architectures and large-scale pretraining have enabled LLMs to understand programming instructions, generate source code, explain complex algorithms, identify programming errors, and assist developers throughout the software development lifecycle. Consequently, LLM-powered coding assistants are increasingly being integrated into modern software engineering environments, supporting activities such as code completion, software prototyping, debugging, documentation generation, and program maintenance [1].
The integration of LLMs into software development represents a significant shift in conventional programming practices. Developers can now translate natural language requirements into executable source code, obtain implementation suggestions, and automate repetitive programming tasks with comparatively limited manual intervention. These capabilities offer opportunities to improve development productivity, reduce implementation effort, and accelerate software delivery. However, the growing dependence on AI-generated source code introduces important concerns regarding software reliability, security, and functional correctness. Unlike conventional development workflows, where developers are primarily responsible for manually implementing and reviewing security-sensitive logic, LLM-assisted development introduces an additional layer of uncertainty associated with probabilistic code generation.
Although generated programs may appear syntactically correct and functionally plausible, their internal implementation can contain security weaknesses that are not immediately apparent during ordinary code inspection. These weaknesses may originate from insecure programming patterns, insufficient input validation, improper authentication and authorization mechanisms, unsafe memory operations, inadequate cryptographic practices, and incorrect handling of external inputs. Furthermore, LLMs may reproduce insecure implementation patterns learned from publicly available source-code repositories, potentially introducing vulnerabilities into otherwise legitimate software applications. Previous empirical investigations have demonstrated that AI-generated code can contain security weaknesses across multiple programming languages and vulnerability categories [2], [3].
Consequently, ensuring the security of LLM-generated code requires more than evaluating whether a generated program successfully performs its intended functionality. It requires systematic mechanisms capable of identifying security-relevant behaviors, explaining the underlying causes of vulnerabilities, and generating reliable corrective modifications. This requirement motivates the development of integrated security frameworks that combine vulnerability detection, model-level interpretability, program analysis, and automated vulnerability repair.
1.2. Security Challenges in LLM-Generated Code
One of the fundamental challenges associated with AI-generated software is the potential discrepancy between functional correctness and security correctness. A program may successfully execute its intended operation while simultaneously exposing sensitive information, accepting malicious input, or enabling unauthorized access. Traditional software testing primarily evaluates whether a program satisfies its functional requirements, whereas security evaluation must additionally consider adversarial inputs, execution contexts, data flows, and potential exploitation scenarios.
Existing empirical studies have highlighted the security implications of AI-assisted programming. Fu et al. investigated security weaknesses in code generated by AI coding assistants and identified vulnerabilities across multiple Common Weakness Enumeration (CWE) categories [2]. Similarly, Wang et al. introduced CodeSecEval to investigate the security characteristics of code-generation models across different vulnerability types, demonstrating the importance of evaluating security independently from conventional code-generation quality [3].
These findings emphasize that the security of generated code cannot be guaranteed solely through the use of advanced language models or carefully designed prompts. A model may generate secure code in one context but produce vulnerable implementations under different requirements, programming languages, or input conditions. Moreover, security weaknesses may emerge through interactions among multiple code components rather than through an isolated vulnerable statement.
Another significant challenge concerns the relationship between the internal computational behavior of an LLM and the vulnerabilities appearing in its generated output. Conventional vulnerability scanners can identify suspicious source-code patterns, but they generally provide limited information about why a particular model generated a vulnerable implementation. Understanding this relationship is important for developing preventive mechanisms capable of addressing security weaknesses before vulnerable code is delivered to developers.
1.3. Limitations of Conventional Security Analysis
Conventional software security analysis primarily relies on static analysis, dynamic analysis, rule-based vulnerability detection, and software testing. Static analysis examines source code or intermediate representations without executing the program. It can identify potentially insecure programming constructs, suspicious data flows, and violations of predefined security rules. Dynamic analysis, in contrast, evaluates program behavior during execution and can reveal vulnerabilities through test inputs, runtime monitoring, and controlled execution environments.
Although these techniques are essential components of modern software security, their independent application presents several limitations. Static analysis tools may generate false positives, depend on predefined rules, and struggle with complex semantic relationships or context-dependent vulnerabilities. Their effectiveness can also be affected by incomplete program models, external dependencies, and insufficient contextual information. Johnson et al. identified false positives and difficulties in interpreting analysis warnings among the barriers affecting developers' adoption of static analysis tools [4].
Dynamic analysis provides complementary evidence by examining actual program execution. However, its effectiveness depends on the quality and coverage of test cases, the availability of suitable execution environments, and the ability to reproduce relevant attack conditions. Vulnerabilities that require uncommon execution paths, complex environmental configurations, or specific combinations of inputs may remain undetected.
Furthermore, conventional analysis techniques primarily operate on the generated source code rather than the internal representations of the language model responsible for producing it. Consequently, they can identify potentially vulnerable code without necessarily explaining the model-level factors associated with its generation. This limitation restricts their ability to support deeper vulnerability prevention and model-behavior analysis.
Combining static and dynamic analysis can improve vulnerability assessment by integrating complementary forms of evidence. Nevertheless, an additional interpretability mechanism is required to connect source-code vulnerabilities with the internal computational features of the generating model. This motivates the integration of program-level security analysis with mechanistic interpretability.
1.4. Machine Learning-Based Vulnerability Detection and Interpretability Challenges
Machine learning and deep learning approaches have increasingly been investigated for automated vulnerability detection. These approaches commonly employ source-code representations, token sequences, abstract syntax trees, control-flow graphs, data-flow information, and learned semantic embeddings to classify vulnerable code or identify potentially insecure program structures. Compared with purely rule-based approaches, learned representations can capture certain complex patterns and relationships that are difficult to express through manually defined security rules.
Despite these advantages, existing machine learning-based vulnerability detection approaches face several challenges. Their effectiveness may depend heavily on training dataset quality, vulnerability distribution, programming language, and representation strategies. Dataset imbalance, duplicated samples, distribution shifts, and limited representation of previously unseen vulnerability patterns can negatively affect generalization. Furthermore, many classification-oriented approaches provide vulnerability labels or probability scores without sufficiently explaining the underlying security mechanisms.
The emergence of LLMs introduces another dimension to this problem: vulnerabilities may be associated not only with source-code structures but also with the internal computational representations involved in code generation. Conventional machine learning-based detection systems generally analyze observable program characteristics, leaving the relationship between internal model features and security-related generation behavior insufficiently explored.
Mechanistic interpretability offers a promising direction for addressing this limitation. Rather than treating neural networks as entirely opaque systems, mechanistic interpretability investigates their internal representations, computational components, and information-processing mechanisms to develop explanations of model behavior. However, interpreting modern LLMs remains challenging because their internal representations are distributed across high-dimensional activation spaces. Individual neurons may participate in multiple computational patterns, making it difficult to associate specific neurons with clearly defined semantic or functional concepts.
This phenomenon is commonly discussed in terms of polysemanticity and superposition. Bricken et al. demonstrated that dictionary-learning approaches can identify interpretable features within language-model activations, providing a foundation for examining internal model representations beyond individual neurons [5]. Similarly, Huben et al. investigated Sparse Autoencoders (SAEs) as a mechanism for recovering interpretable features from language-model activations and demonstrated their potential for investigating internal model behavior [6].
Nevertheless, identifying individual interpretable features does not automatically establish their causal contribution to a particular behavior. A security-related model behavior may involve multiple interacting features, contextual dependencies, and distributed computational mechanisms. Therefore, interpreting individual feature activations without examining their relationships may provide an incomplete understanding of vulnerability-inducing behavior. 1.5. Research Gaps and Problem Statement
Although existing research has advanced LLM-based code generation, vulnerability detection, and automated program repair, several important research challenges remain.
First, there is a need for stronger integration between source-code vulnerability detection and the internal representations of code-generating language models. Conventional security tools primarily identify vulnerabilities at the program level, whereas mechanistic interpretability investigates model-level computational behavior. The limited integration between these perspectives makes it difficult to establish a unified explanation of how internal model features relate to vulnerable code-generation outcomes.
Second, existing vulnerability detection approaches frequently emphasize individual code patterns, token representations, or classification outputs. However, security weaknesses may emerge through interactions among multiple source-code features and model-level representations. A multi-feature detection strategy is therefore necessary to investigate complementary security indicators rather than depending exclusively on a single detection signal.
Third, although SAEs offer a promising approach to decomposing neural activations into potentially interpretable features, their application to security-oriented analysis of code-generating LLMs requires further investigation. In particular, the relationships between SAE-derived features, vulnerability categories, and insecure code-generation behaviors remain an important research direction.
Fourth, existing vulnerability analysis systems often provide limited explanations connecting detected weaknesses to their precise source-code locations and underlying causes. Security practitioners require actionable explanations that identify vulnerable statements, relevant data flows, triggering conditions, and associated security risks.
Finally, automated vulnerability repair remains challenging because generating a syntactically valid patch does not necessarily guarantee security improvement or functional correctness. Pearce et al. demonstrated that LLM-based vulnerability repair can be effective in relatively simple scenarios but encounters difficulties in more realistic repair settings [7]. Subsequent investigations have also highlighted challenges involving complex dependencies, contextual requirements, and real-world program structures [8].
These observations identify the need for an integrated framework that connects model-level security interpretability with program-level vulnerability analysis and automated repair. Specifically, the research problem addressed in this study is:
How can internal model representations, interacting security-relevant features, and complementary program-analysis techniques be integrated into an explainable framework capable of detecting, localizing, preventing, and repairing vulnerabilities in LLM-generated source code while maintaining functional correctness?
1.6. Proposed CRAFT-Sec Framework
To address the identified research challenges, this paper proposes CRAFT-Sec (an Explainable Multi-Feature Security Framework), an integrated security framework designed to investigate and mitigate vulnerabilities associated with LLM-generated code.
CRAFT-Sec is designed around the principle that reliable software security requires both observable program-level evidence and interpretable model-level information. Instead of relying exclusively on conventional vulnerability scanners or black-box classification systems, the framework combines multiple complementary analytical components to support a more comprehensive security assessment.
The proposed framework consists of several interconnected components.
The first component performs multi-feature vulnerability detection by examining relevant source-code characteristics, including lexical, syntactic, semantic, structural, and security-related indicators. These features are intended to support the identification of potentially vulnerable programming patterns across relevant CWE categories.
The second component incorporates SAE-based interpretability to decompose selected internal LLM activations into sparse, potentially interpretable feature representations. These representations will be investigated to identify features associated with secure and insecure code-generation behaviors.
The third component performs feature interaction analysis to examine relationships among security-relevant latent features. Through co-activation analysis and appropriately controlled interventions, this component aims to investigate whether individual features or combinations of features are associated with particular vulnerability-inducing behaviors.
The fourth component integrates static and dynamic program analysis to validate suspicious code patterns, investigate relevant data and control flows, and assess vulnerabilities under controlled execution conditions. Combining these analytical techniques is intended to improve the reliability of vulnerability assessment.
The fifth component provides explainable vulnerability localization by associating detected weaknesses with relevant source-code statements, vulnerable operations, security indicators, and supporting analysis evidence. The objective is to produce explanations that are understandable and actionable for software developers and security analysts.
Finally, the automated vulnerability repair component generates candidate security-oriented patches based on the identified vulnerability, its contextual information, and the available explanation evidence. Candidate repairs will be assessed through security re-analysis, functional testing, and regression testing to determine whether the modifications address the vulnerability without introducing unacceptable behavioral changes.
Importantly, CRAFT-Sec is proposed as a research framework rather than an experimentally validated security solution. Its effectiveness, generalizability, interpretability, and computational feasibility will be established through systematic experimental evaluation.

The primary objective of this research is to design and investigate an explainable, multi-feature security framework for vulnerability detection, prevention, localization, and automated repair in LLM-generated code.
The specific research objectives are as follows:

2. SAE-based model interpretability: Investigate the use of Sparse Autoencoders to extract potentially interpretable security-relevant features from internal LLM activations.
3. Feature interaction analysis: Examine the relationships among individual and interacting latent features to investigate their associations with vulnerable code-generation behaviors.
4. Integrated program analysis: Combine static and dynamic analysis techniques to validate detected vulnerabilities and investigate their relevant execution and data-flow characteristics.
5. Explainable vulnerability localization: Develop an explanation mechanism capable of identifying vulnerable source-code locations and presenting supporting evidence, security implications, and relevant vulnerability classifications.
6. Automated vulnerability repair: Design a repair mechanism that generates candidate security patches and evaluates them for vulnerability mitigation, functional correctness, and regression safety.
7. Comprehensive experimental evaluation: Evaluate the proposed framework using established vulnerability benchmarks, multiple LLMs, relevant CWE categories, and appropriate comparative and statistical analysis.

2. RELATED WORK
The security of Large Language Model (LLM)-generated software has become an increasingly important research area as AI-assisted programming expands across software development activities. Existing studies have investigated this problem from several perspectives, including conventional vulnerability detection, machine learning-based classification, deep learning, secure code generation, mechanistic interpretability, and automated program repair. Although these research directions provide important foundations, they frequently address different stages of the security lifecycle independently. This section critically reviews the relevant literature, examines methodological differences and limitations, and identifies the research gaps motivating the proposed CRAFT-Sec framework.
2.1 Vulnerability Detection in LLM-Generated Code
The increasing adoption of LLM-powered coding assistants has created new opportunities for automated software development while introducing security concerns regarding generated source code. Unlike conventional software vulnerabilities, which generally originate from human implementation decisions, vulnerabilities in AI-generated code may reflect patterns learned from training data, prompt interpretation, model behavior, and contextual dependencies.
Pearce et al. [1] conducted an empirical investigation of GitHub Copilot by generating programs across 89 scenarios covering different security weaknesses, prompts, and application domains. Their evaluation identified vulnerabilities in approximately 40% of the generated programs. This study established an important empirical foundation for examining the security implications of AI-generated code. However, its controlled generation scenarios do not fully represent the diversity of real-world developer interactions and software environments.
Fu et al. [2] extended this research perspective by investigating AI-generated code contributions in real GitHub projects. Their analysis examined 733 code snippets generated by Copilot, CodeWhisperer, and Codeium, identifying security weaknesses across 43 CWE categories. The study also investigated whether static-analysis warnings could guide LLM-based vulnerability repair. Its real-world orientation provides valuable evidence, although the use of available project contributions introduces limitations related to sample availability, generation provenance, and selection bias.
Asare et al. [3] investigated the security implications of Copilot through a user-centered study involving 25 participants. Their findings suggested that the security effects of AI assistance depend on programming-task difficulty rather than producing a uniform increase in insecure implementations.
More recently, CoV-Eval introduced a multi-task evaluation perspective covering secure code generation, vulnerability detection, classification, and repair across multiple LLMs [4]. This broader evaluation strategy highlights that security performance cannot be adequately represented by a single code-generation or classification metric.
Collectively, these studies establish the importance of evaluating AI-generated code independently from functional correctness. Nevertheless, they primarily emphasize observable code behavior, empirical security assessment, and model-level task performance. The internal representations associated with vulnerability-inducing generation, particularly the interactions among security-relevant latent features, remain less systematically integrated into vulnerability detection pipelines. CRAFT-Sec addresses this research direction by investigating the relationship between internal model representations and externally observable source-code vulnerabilities.
2.2 Traditional Static and Dynamic Code Analysis
Static and dynamic program analysis constitute two fundamental approaches to software vulnerability detection. Static analysis examines source code, intermediate representations, or program structures without requiring execution. It can identify suspicious operations, unsafe data flows, insecure API usage, and violations of predefined security rules.
Tools such as CodeQL and commercial static application security testing systems employ program queries, data-flow analysis, and security-oriented rules to identify potentially vulnerable code. These techniques are particularly useful for detecting established vulnerability patterns and supporting continuous integration security workflows.
Johnson et al. [5] investigated the adoption of static analysis tools and identified practical barriers associated with warning interpretation, false positives, and integration into developer workflows. Such limitations demonstrate that detecting suspicious code is not equivalent to producing actionable security knowledge.
Dynamic analysis complements static techniques by observing program behavior during execution. Dynamic application security testing, fuzz testing, and runtime monitoring can expose vulnerabilities through controlled inputs and execution scenarios. Fuzzing approaches such as AFL have demonstrated the effectiveness of systematically exploring program input spaces to discover unexpected behaviors [6].
However, dynamic analysis depends on execution coverage, test quality, environmental configuration, and the reproducibility of relevant conditions. Static analysis, conversely, may struggle with complex semantic relationships, external dependencies, and context-sensitive execution behavior.
The two approaches are therefore complementary rather than interchangeable. Their combination can improve vulnerability validation, but neither inherently explains why an LLM generated a particular insecure implementation. This distinction motivates integrating conventional program analysis with model-level interpretability rather than replacing established security-analysis techniques.
2.3 Machine Learning-Based Software Vulnerability Detection
Machine learning-based vulnerability detection emerged partly in response to the limitations of manually constructed security rules and conventional pattern-matching techniques. Early approaches investigated supervised classification using manually extracted program characteristics, including function-call patterns, API usage, code complexity, and security-sensitive operations. Although these techniques reduced dependence on exhaustive rule definitions, their effectiveness remained closely connected to feature engineering and the representativeness of training datasets.
Li et al. [7] introduced VulDeePecker, an early deep learning-based vulnerability detection system that represents programs through semantically related code gadgets. By employing bidirectional recurrent neural networks, the approach learns vulnerability-related representations without requiring developers to manually define every detection feature. Its use of code gadgets also provides finer contextual information than simple file-level classification. However, the approach depends on predefined code-gadget extraction procedures and may not capture every semantic relationship necessary to identify complex vulnerabilities.
Zhou et al. [8] proposed Devign, which applies graph neural networks to comprehensive program representations. Rather than treating source code exclusively as a sequential token stream, Devign incorporates structural and semantic information to identify vulnerable functions. This approach demonstrates the importance of representing relationships among program components. Nevertheless, graph construction, dataset labeling, and the availability of representative training samples remain important practical considerations.
These approaches illustrate the transition from manually specified vulnerability indicators toward learned program representations. Their primary advantage is the ability to identify statistical patterns associated with vulnerable code. However, learned classifiers may provide limited explanations of the specific conditions responsible for their predictions. Furthermore, a model trained on particular projects, languages, or vulnerability distributions may perform inconsistently when applied to previously unseen software environments.
Another important limitation concerns the distinction between correlation and causation. A machine learning classifier may identify code characteristics frequently associated with vulnerabilities without establishing whether those characteristics are responsible for the underlying security weakness.
CRAFT-Sec extends this research direction by investigating multiple complementary security features while incorporating interpretable internal model representations and independent program-level validation.
2.4 Deep Learning and Transformer-Based Vulnerability Detection
The development of deep learning has enabled vulnerability detection systems to learn increasingly sophisticated representations of source code. Recurrent neural networks, convolutional architectures, graph neural networks, and Transformer-based models have been investigated for identifying vulnerability-related patterns.
Transformer architectures are particularly relevant because self-attention mechanisms can capture relationships among tokens across relatively long contexts. Feng et al. [9] introduced CodeBERT, a bimodal pretrained model designed to learn representations from programming and natural languages. By incorporating both natural-language and programming-language information, CodeBERT provides transferable representations for downstream software engineering tasks.
However, general-purpose code representations do not automatically guarantee effective security discrimination. A representation optimized for code search, documentation generation, or semantic understanding may not sufficiently distinguish secure implementations from vulnerable alternatives.
Zhou et al. [8] demonstrated the importance of incorporating structural program semantics through graph-based learning. Building on this direction, Fu et al. [10] introduced LineVul, a Transformer-based vulnerability prediction approach designed to identify vulnerable functions and localize suspicious source-code lines. Their work highlights the importance of moving beyond function-level classification toward more precise vulnerability localization.
Despite these advances, Transformer-based vulnerability detection systems remain dependent on their training distributions, annotation quality, input representations, and classification objectives. Attention weights and token-level importance scores may provide useful diagnostic information, but they should not automatically be interpreted as faithful explanations of model reasoning.
More importantly, these systems primarily investigate representations of the analyzed source code. They do not necessarily reveal the internal features of the separate LLM responsible for generating that code. Consequently, an important distinction remains between explaining why a vulnerability classifier identifies a source-code pattern and understanding the internal model behavior associated with generating a vulnerable implementation.
CRAFT-Sec seeks to investigate both perspectives through the combination of source-code feature analysis and SAE-based examination of code-generating model activations.
2.5 LLM-Based Secure Code Generation and Analysis
Recent research has investigated whether LLMs can generate secure source code, identify existing vulnerabilities, and automatically produce corrective modifications. These capabilities suggest that language models may function not only as software development assistants but also as components of security analysis and remediation workflows.
Pearce et al. [1] demonstrated that AI-generated code can contain significant security weaknesses under controlled generation scenarios. Fu et al. [2] subsequently examined real-world generated code contributions and investigated the potential of using static-analysis warnings to guide LLM-based repairs. Their findings suggest that combining conventional security tools with LLM-based correction can provide a practical remediation strategy.
Asare et al. [3] further demonstrated that the influence of coding assistants on security outcomes can depend on the nature and complexity of programming tasks. This indicates that the security implications of AI-assisted development cannot be adequately characterized through generated-code benchmarks alone.
More comprehensive evaluations have also emerged. The CoV-Eval benchmark developed by the authors of [4] considers multiple security tasks, including code generation, vulnerability detection, classification, and repair. Its evaluation of 20 proprietary and open-source models highlights the difference between recognizing vulnerable code and consistently generating secure implementations or successful repairs.
These studies provide valuable evidence concerning the practical security capabilities of LLMs. Nevertheless, LLM-based security analysis introduces several challenges. First, model-generated explanations may be plausible without accurately identifying the underlying vulnerability. Second, the same model may produce inconsistent judgments across prompts and contextual variations. Third, generated patches may remove an observed vulnerability while introducing functional regressions or additional security weaknesses.
Prompt-based security guidance also does not provide a complete solution because it primarily modifies the model's input rather than establishing whether the internal generation process has changed in a reliable and measurable manner.
Therefore, an important research direction is to connect LLM-based security analysis with independent evidence from program analysis and interpretable internal representations. CRAFT-Sec adopts this perspective by treating LLM-based generation and repair as components that require external validation rather than assuming that model-generated security judgments are inherently reliable.
2.6 Mechanistic Interpretability in Large Language Models
Mechanistic interpretability investigates the internal computational mechanisms responsible for neural network behavior. Rather than treating a model as an entirely opaque mapping between inputs and outputs, this research direction examines internal activations, neurons, features, attention mechanisms, and computational circuits.
Elhage et al. [11] developed foundational theoretical perspectives on superposition and the representation of multiple features within neural networks. Their analysis helps explain why individual neurons may not correspond to single, easily interpretable concepts. A neuron can respond to multiple unrelated patterns because neural networks may represent more features than their available dimensions through overlapping activation directions.
This phenomenon creates significant difficulties for interpreting modern LLMs. Individual neuron activations may reflect multiple semantic or functional characteristics, making neuron-level explanations insufficient for understanding complex model behavior.
Mechanistic interpretability attempts to address this problem by identifying more meaningful computational units and investigating how these units contribute to model outputs. Research on induction heads and other attention-related circuits has also demonstrated that specific internal computational structures can contribute to identifiable language-model behaviors [12].
However, transferring these techniques to software security introduces additional challenges. Security-related behaviors are often highly contextual and may depend on the interaction between programming instructions, source-code structures, security requirements, and model-generated continuations.
Furthermore, identifying a feature associated with a vulnerable code pattern does not establish that the feature causes the vulnerability. Causal interpretation requires controlled interventions, appropriate baselines, and evidence that the observed behavior changes when the relevant internal representation is manipulated.
CRAFT-Sec investigates mechanistic interpretability as a means of examining security-relevant model behavior while distinguishing descriptive feature associations from experimentally supported causal relationships.
2.7 Sparse Autoencoders and Latent Feature Extraction
Sparse Autoencoders have become an important technique for investigating the internal representations of Transformer-based language models. They aim to decompose high-dimensional neural activations into a larger collection of sparsely activated latent features.
Bricken et al. [13] demonstrated that dictionary-learning approaches using Sparse Autoencoders can recover interpretable features that are difficult to identify through direct neuron inspection. Their research investigated feature decomposition, superposition, feature splitting, and the potential use of extracted features for understanding and steering model behavior.
Huben et al. [14] further demonstrated that SAE-derived representations can provide interpretable features and support the investigation of counterfactual model behavior. Their findings provide additional motivation for using sparse feature representations as a basis for mechanistic analysis.
Conceptually, an SAE attempts to approximate an activation vector using a sparse combination of learned feature directions:
[
\mathbf{x} \approx \mathbf{b}+\mathbf{D}\mathbf{f}
]
where (\mathbf{x}) represents the original model activation, (\mathbf{b}) denotes a bias term, (\mathbf{D}) represents the learned decoder dictionary, and (\mathbf{f}) contains sparse latent feature activations.
The sparsity constraint encourages a relatively small number of features to activate for a given input. This can improve the interpretability of internal representations compared with directly examining individual neurons.
Nevertheless, SAEs introduce their own methodological challenges. Reconstruction quality, sparsity, feature splitting, dead features, feature absorption, and dictionary size can influence the resulting representations. An SAE feature that appears interpretable through activation examples may still capture multiple related or unrelated behaviors.
Additionally, the interpretation of an extracted feature requires validation across diverse inputs and contexts. Automated feature descriptions alone are insufficient to establish semantic accuracy or causal importance.
Although SAE research has advanced general LLM interpretability, its systematic application to vulnerability-inducing code-generation behavior remains an emerging research direction. CRAFT-Sec proposes investigating this application through security-oriented feature extraction, feature characterization, and controlled behavioral analysis.
2.8 Feature Interaction Analysis and Explainable AI
Explainable Artificial Intelligence (XAI) seeks to make machine learning predictions more understandable by identifying the information and computational factors associated with model outputs. Existing XAI methods can broadly be categorized into feature-attribution techniques, perturbation-based explanations, surrogate models, gradient-based approaches, and model-specific interpretability mechanisms.
Lundberg and Lee [15] introduced SHAP, a unified framework for interpreting model predictions through Shapley values derived from cooperative game theory. SHAP provides a systematic mechanism for estimating the contribution of individual input features to a prediction. Its additive attribution formulation has been widely influential in explainable machine learning.
However, individual feature attribution does not necessarily capture interactions among features. In security analysis, multiple indicators may jointly contribute to a vulnerability even when their individual effects appear relatively insignificant. For example, insufficient input validation combined with unsafe string construction and an externally accessible execution pathway may create a security weakness that cannot be adequately explained by considering each indicator independently.
Interaction analysis therefore requires examining how combinations of features influence model behavior. Relevant techniques include interaction attribution, pairwise feature dependence, controlled ablation, activation patching, and causal intervention. These methods provide complementary perspectives on the relationships among model representations.
Mechanistic interpretability research has also demonstrated that latent features can participate in more complex computational structures rather than operating exclusively as independent units [13]. Such observations motivate examining feature relationships and their downstream effects.
Nevertheless, feature co-activation should not automatically be interpreted as causal interaction. Two features may activate together because they respond to the same input context, without one directly influencing the other. Establishing causal relationships requires interventions that manipulate individual or combined feature activations while controlling other relevant conditions.
A further challenge concerns the distinction between local explanations and globally valid behavioral interpretations. An explanation generated for one vulnerable code sample may not generalize to different programming languages, model architectures, or security contexts.
CRAFT-Sec therefore treats feature interaction analysis as a complementary interpretability component. Its objective is to investigate individual and combined security-relevant features, examine their relationships with generated code, and distinguish observational associations from experimentally supported causal effects.
2.9 Program Analysis Using AST, CFG, DFG, and Taint Analysis
Program analysis provides structural and semantic information that is essential for understanding how software vulnerabilities emerge. Several intermediate representations have been developed to capture different aspects of program behavior.
An Abstract Syntax Tree (AST) represents the hierarchical syntactic structure of source code. It captures relationships among statements, expressions, declarations, and operations. AST-based analysis is useful for identifying insecure coding constructs, unsafe API usage, and syntactic patterns associated with particular vulnerability categories. However, an AST alone does not fully represent execution order or data dependencies.
A Control Flow Graph (CFG) models the possible execution paths of a program through nodes representing statements or basic blocks and edges representing control transitions. CFG analysis helps identify conditional execution, branching behavior, loops, and potentially unreachable operations. It is particularly useful for investigating whether security checks are consistently executed before sensitive operations.
A Data Flow Graph (DFG) represents relationships through which values are transferred between program variables and operations. It can identify dependencies between variable definitions and their subsequent uses. This information is important for investigating vulnerabilities involving untrusted inputs, sensitive data, and unsafe operations.
Yamaguchi et al. [16] introduced the Code Property Graph (CPG), which combines concepts from ASTs, control-flow representations, and program dependence graphs into a unified representation. Their approach demonstrated how graph-based representations can support systematic vulnerability discovery through structural queries and graph traversals.
Taint analysis extends these techniques by tracking the propagation of potentially untrusted data from source locations to sensitive operations or sinks. For example, user-controlled input may propagate through several intermediate functions before reaching a database query, shell execution command, or dynamically constructed expression.
However, practical taint analysis must account for sanitization operations, interprocedural dependencies, aliasing, implicit data flows, and external library behavior. Incomplete modeling may produce false positives or overlook relevant vulnerabilities.
The individual representations offer complementary advantages. ASTs capture syntax, CFGs represent execution structure, DFGs describe data dependencies, and taint analysis investigates the propagation of potentially dangerous inputs.
Despite their usefulness, these representations generally provide limited information about the internal generation mechanisms of LLMs. CRAFT-Sec proposes using program-level structural and data-flow evidence alongside model-level interpretability to establish a more comprehensive security assessment.
2.10 Automated Program Repair
Automated Program Repair (APR) investigates methods for identifying and correcting software defects with limited manual intervention. Traditional approaches generally use predefined transformation rules, program synthesis, search-based optimization, or test-driven patch generation.
Weimer et al. [17] introduced GenProg, a search-based repair approach that uses genetic programming to generate program modifications satisfying existing test requirements. The method demonstrated that program variants could be automatically evolved to address defects while preserving tested functionality.
Subsequent approaches have investigated more precise patch-generation mechanisms. Long and Rinard [18] introduced Prophet, which uses learned models to rank candidate patches based on their likelihood of satisfying intended correctness properties. Such approaches illustrate the potential of combining automated patch generation with statistical guidance.
The emergence of LLMs has introduced additional possibilities for automated repair. Unlike traditional approaches that rely heavily on predefined transformations or search spaces, LLM-based systems can generate context-sensitive modifications from natural-language descriptions, code snippets, and diagnostic information.
Pearce et al. [1] investigated the use of Copilot Chat to repair security weaknesses identified in AI-generated code, demonstrating the potential of combining static-analysis warnings with LLM-based corrections.
Zhang et al. [19] evaluated LLMs on real-world C/C++ vulnerability repair tasks. Their investigation showed that repair effectiveness depends on vulnerability complexity, with relatively localized memory errors generally presenting fewer difficulties than vulnerabilities requiring reasoning across multiple program components.
Similarly, recent research on enhanced LLM-based vulnerability repair has investigated fine-tuned code models and security-oriented patch generation [20].
Despite these advances, automated vulnerability repair remains difficult for several reasons. First, a patch may remove the detected vulnerability without preserving the original program's intended functionality. Second, generated modifications may introduce additional weaknesses or regression defects. Third, complex vulnerabilities may require understanding interprocedural dependencies, program invariants, and external system behavior.
Consequently, evaluating repair quality solely through patch generation or successful compilation is insufficient. A reliable repair mechanism should incorporate vulnerability re-analysis, functional testing, regression testing, and, where appropriate, security-specific validation.
CRAFT-Sec adopts this validation-oriented perspective by connecting repair generation with the evidence produced by vulnerability localization, feature analysis, and static and dynamic program analysis.
2.11 Critical Research Gap Analysis
The reviewed literature demonstrates substantial progress in software vulnerability detection, LLM security evaluation, deep learning-based code analysis, mechanistic interpretability, and automated program repair. Nevertheless, these research directions expose several unresolved challenges that motivate an integrated security framework.
First, the separation between model-level and program-level security analysis remains an important limitation. Existing vulnerability detection systems primarily investigate generated source code, while mechanistic interpretability research generally investigates internal neural representations without directly connecting them to software security outcomes.
Second, the limited investigation of interacting security features restricts the ability of individual-feature approaches to explain vulnerabilities arising from combinations of programming patterns and internal model representations. More systematic investigation of feature relationships and controlled interventions is required.
Third, the application of SAE-based interpretability to security-oriented code generation remains an important research opportunity. Although SAEs have demonstrated their usefulness in recovering interpretable latent features, their ability to identify features associated with vulnerable code-generation behaviors requires dedicated experimental validation.
Fourth, existing vulnerability detection systems do not consistently provide sufficiently actionable explanations. Classification scores and suspicious-token indicators may identify potential problems without establishing the relationship between model behavior, program structure, vulnerable operations, and security consequences.
Fifth, the integration of complementary program-analysis techniques with mechanistic interpretability remains insufficiently explored in a unified framework. AST, CFG, DFG, and taint analysis provide valuable program-level evidence, but their combination with SAE-derived model-level representations may support a more comprehensive explanation of security weaknesses.
Sixth, automated repair requires stronger security and functional validation. Generating a candidate patch does not establish that the vulnerability has been eliminated or that the original program behavior has been preserved. A systematic repair-validation process is therefore essential.

III. RESEARCH PROBLEM AND RESEARCH OBJECTIVES
This section establishes the central research problem, scientific motivation, research objectives, research questions, and testable hypotheses underlying the proposed CRAFT-Sec framework. The research focuses on the development of an integrated security approach that connects internal LLM representations with program-level vulnerability analysis to support vulnerability detection, explanation, prevention, and automated repair.
3.1 Problem Statement
The rapid adoption of Large Language Models (LLMs) in software development has introduced new opportunities for automated programming, code completion, debugging, and software maintenance. However, despite their ability to generate syntactically valid and functionally plausible source code, LLMs may produce implementations containing security vulnerabilities. These weaknesses can originate from insecure programming patterns, inadequate input validation, improper data handling, unsafe API usage, and incorrect implementation of security-sensitive operations.
The central problem is that functional correctness does not necessarily imply security correctness. A generated program may successfully execute its intended functionality while remaining vulnerable to attacks such as SQL injection, cross-site scripting, command injection, path traversal, insecure deserialization, and improper access control.
Existing vulnerability detection approaches primarily rely on static analysis, dynamic analysis, machine learning classifiers, and pattern-based security rules. Although these techniques can identify suspicious code structures and potentially exploitable execution paths, they generally provide limited insight into the internal computational mechanisms responsible for vulnerable code generation.
Furthermore, conventional vulnerability detection systems frequently treat individual code characteristics independently. However, software vulnerabilities may emerge from interactions among multiple programming constructs, data dependencies, execution conditions, and security-sensitive operations. Consequently, isolated feature analysis may fail to capture complex vulnerability-inducing patterns.
Another important challenge concerns the interpretability of modern LLMs. Their internal representations are distributed across high-dimensional activation spaces, making it difficult to identify specific internal features associated with insecure code-generation behavior. Sparse Autoencoders (SAEs) provide a promising mechanism for decomposing neural activations into potentially interpretable latent features. Nevertheless, identifying individual features is insufficient without investigating their interactions and relationships with observable security outcomes.
Additionally, existing security analysis approaches often provide limited explanations connecting internal model behavior with specific vulnerable source-code locations. Developers require more than vulnerability labels or confidence scores; they need actionable information identifying the affected statements, relevant data flows, security conditions, and underlying causes.
Automated vulnerability repair introduces another challenge. Although LLMs can generate corrective code modifications, a generated patch does not automatically guarantee vulnerability elimination, functional correctness, or the absence of regression defects. Therefore, repair mechanisms must incorporate independent security validation and functional testing.
These challenges reveal the need for an integrated framework capable of connecting model-level interpretability with conventional program analysis and security-oriented repair.
To address this problem, this research proposes CRAFT-Sec, an explainable multi-feature security framework designed to investigate and mitigate vulnerabilities in LLM-generated source code.
The central research problem can therefore be formally expressed as follows:
How can security-relevant internal representations of large language models, interacting latent features, and complementary program-analysis techniques be integrated into a unified framework that can accurately detect, explain, localize, prevent, and repair vulnerabilities in LLM-generated code while maintaining functional correctness?
CRAFT-Sec will investigate this problem through seven interconnected research dimensions:
1. Identification of security-relevant source-code features for multi-feature vulnerability detection.
2. Extraction of interpretable latent representations from LLM activations using Sparse Autoencoders.
3. Investigation of relationships and interactions among security-relevant latent features.
4. Integration of neural interpretability with static and dynamic program analysis.
5. Explainable localization of vulnerabilities within generated source code.
6. Automated generation and validation of security-oriented patches.
7. Investigation of security-aware generation mechanisms to reduce vulnerability occurrence.
3.2 Research Motivation
The motivation for this research originates from the limitations of treating LLM-generated code security exclusively as a source-code classification problem.
First, the increasing dependence on AI-assisted programming makes it necessary to establish security evaluation mechanisms that extend beyond functional testing. Developers need assurance that generated programs satisfy relevant security requirements rather than merely producing expected outputs.
Second, existing vulnerability detection techniques generally examine observable program characteristics. Although they can identify suspicious code patterns, they provide limited understanding of the internal model representations associated with vulnerable generation. Investigating these representations may provide additional evidence for understanding how security-related behaviors emerge within LLMs.
Third, mechanistic interpretability, particularly SAE-based feature extraction, offers an opportunity to investigate internal model representations at a more granular level. By examining latent features and their interactions, this research aims to explore whether interpretable internal signals can contribute to vulnerability identification and prevention.
Fourth, combining neural interpretability with established program-analysis techniques may provide complementary evidence. SAE-derived features can offer information about internal model behavior, while Abstract Syntax Trees (ASTs), Control Flow Graphs (CFGs), Data Flow Graphs (DFGs), and taint analysis can provide structural and behavioral evidence about generated programs.
Fifth, vulnerability explanations should be actionable. Identifying a potentially vulnerable function is useful, but identifying the exact vulnerable operation, its relevant input sources, propagation paths, and security consequences provides more practical value to developers.
Finally, detection without remediation leaves developers responsible for manually correcting identified weaknesses. An integrated automated repair mechanism could reduce this gap by generating candidate patches and validating their security and functional correctness.
Accordingly, the primary scientific motivation of CRAFT-Sec is to investigate the relationship between internal neural representations and externally observable software vulnerabilities and determine whether this relationship can support a more explainable and effective security workflow.

IV. PROPOSED CRAFT-Sec FRAMEWORK AND SYSTEM ARCHITECTURE
4.1 Overview of the Proposed Framework
This research proposes CRAFT-Sec, an Explainable Multi-Feature Security Framework designed to detect, explain, prevent, and automatically repair vulnerabilities in Large Language Model (LLM)-generated source code. The framework aims to bridge the gap between internal neural representations of code-generating LLMs and conventional program-level security analysis.
Unlike traditional vulnerability detection systems that primarily examine observable source-code patterns, CRAFT-Sec investigates both the internal model features associated with code generation and the structural and behavioral characteristics of the resulting programs. This combination is intended to provide a more comprehensive understanding of potential security weaknesses.
The proposed architecture integrates sixteen interconnected components organized into six functional layers:
   1. Input and preprocessing layer: Receives LLM-generated code and prepares it for subsequent analysis.
   2. Neural vulnerability analysis layer: Investigates security-related model activations through multi-feature detection and Sparse Autoencoder (SAE)-based feature extraction.
   3. Feature interaction and program analysis layer: Examines latent feature relationships and source-code structures using AST, CFG, DFG, and taint analysis.
   4. Evidence fusion and risk assessment layer: Integrates complementary evidence and estimates vulnerability severity and confidence.
   5. Prevention and automated repair layer: Supports security-aware code generation and generates candidate vulnerability-remediation patches.
   6. Validation and reporting layer: Evaluates patch security and functional correctness and produces explainable security reports.
The framework follows a modular architecture in which individual components provide specialized analytical capabilities while sharing structured information through a common evidence representation.
An important design principle is that neural interpretability and conventional program analysis serve complementary purposes. SAE-derived features provide information about internal model representations, whereas static and dynamic program analysis provide evidence about observable source-code behavior. Neither source of evidence is assumed to be independently sufficient for establishing a vulnerability.
The overall architecture is designed to support both post-generation vulnerability analysis and security-aware generation. This allows CRAFT-Sec to investigate security weaknesses after code generation and explore mechanisms for reducing their occurrence during subsequent generation.
4.2 Overall System Architecture
The proposed CRAFT-Sec architecture is organized around the flow of information from code generation to security assessment, explanation, prevention, and repair.

Conceptually, the architecture receives source code generated by an LLM together with its generation context and, when accessible, the corresponding internal model activations. The source code undergoes preprocessing before being passed to the vulnerability detection and program-analysis components.
In parallel, the internal activations are processed through an SAE-based feature extraction mechanism. The resulting latent features are examined individually and through interaction analysis to identify representations associated with potentially insecure generation behaviors.
The program-analysis components independently examine the source code through AST construction, control-flow analysis, data-flow analysis, and taint propagation. Their outputs are combined with neural feature evidence through a multi-feature evidence fusion mechanism.
The resulting security assessment is used to identify potential vulnerabilities, estimate their severity, and generate explanations that associate internal feature evidence with specific source-code locations and program-level behavior.
Where vulnerabilities are identified, the framework can initiate security-aware prevention mechanisms or automated repair. Candidate patches are subsequently subjected to security re-analysis and functional validation before a final security report is generated.
The architecture is intended to operate iteratively: if a candidate repair fails validation, the repair process can generate or select another candidate rather than accepting an unsuccessful modification.

4.3.1 Component 1: LLM-Generated Code Input

Purpose: To normalize and prepare generated source code for consistent vulnerability detection and structural program analysis.

4.4 Overall System Workflow and Information Flow
The complete CRAFT-Sec workflow is organized as a sequence of interconnected analytical and corrective operations.
The process begins when an LLM generates source code in response to a programming prompt. The framework collects the generated program and its available contextual metadata. When access to internal model activations is supported, selected activations are also recorded for subsequent interpretability analysis.
The generated source code is passed through preprocessing, where it is normalized and transformed into representations suitable for vulnerability detection and structural analysis.
In parallel, the neural analysis pathway processes the collected activations through Sparse Autoencoders. The resulting latent features are examined through feature interaction analysis to investigate their relationships with security-related generation behavior.
Meanwhile, the program-analysis pathway constructs AST, CFG, and DFG representations and performs taint analysis to identify suspicious operations and potentially unsafe data propagation.
The outputs of the neural and program-analysis pathways are combined through multi-feature evidence fusion. The resulting evidence is used for vulnerability classification, localization, and security risk assessment.
When a vulnerability is identified, CRAFT-Sec generates an explanation linking the affected source-code region with supporting security evidence. The system then determines whether the vulnerability should be addressed through preventive generation controls, automated repair, or both.
Candidate repairs undergo independent patch validation. Successful candidates are retained as validated modifications, whereas unsuccessful candidates are returned to the repair process.
Finally, the framework produces an explainable security report containing the detection results, evidence, vulnerability locations, risk assessments, and repair-validation outcomes.

4.6 Operational Modes of CRAFT-Sec
The proposed architecture supports three complementary operational modes.
4.6.1 Post-Generation Security Analysis
This mode analyzes code after an LLM has generated it.
The process includes source-code preprocessing, multi-feature vulnerability detection, program analysis, evidence fusion, risk assessment, and explainable reporting.
It is the primary operational mode and does not require direct access to the internal model architecture.
4.6.2 White-Box Model Interpretability
This mode is available when the generating LLM provides access to intermediate activations.
It incorporates SAE-based feature extraction and feature interaction analysis to investigate internal representations associated with security-related code-generation behavior.
This mode supports deeper investigation of the relationship between internal neural representations and observable program vulnerabilities.
4.6.3 Security-Aware Generation and Repair
This mode uses previously identified security weaknesses and validated analytical evidence to guide subsequent generation and repair.
It incorporates security-aware generation constraints, contextual vulnerability feedback, candidate patch generation, and independent validation.
The three operational modes allow CRAFT-Sec to support different model-access conditions without making white-box interpretability a mandatory requirement for all vulnerability assessments.
4.7 Architectural Design Principles
The proposed architecture follows several principles to support scientific reliability and practical applicability.
1. Modularity: Each component performs a defined analytical function and communicates through structured intermediate representations.
2. Evidence-based detection: Vulnerability predictions should be supported by identifiable analytical evidence rather than relying exclusively on model confidence scores.
3. Interpretability: The framework should provide explanations connecting relevant neural features, source-code structures, and security findings.
4. Complementary analysis: Neural, static, and dynamic analysis should be treated as complementary sources of evidence.
5. Causal rigor: Feature correlations and co-activation patterns must be distinguished from experimentally supported causal effects.
6. Functional preservation: Automated repair should be evaluated against both security requirements and functional correctness.
7. Model independence: The program-level analysis pathway should remain operational even when internal activations are inaccessible.
8. Experimental reproducibility: Model versions, prompts, datasets, random seeds, analysis configurations, and validation outcomes should be recorded to support reproducible evaluation.
9. Human oversight: High-risk security findings and patches should support expert review, particularly when the available evidence is incomplete or ambiguous.
4.8 Summary of the Proposed Architecture
The proposed CRAFT-Sec architecture establishes an integrated approach to investigating vulnerabilities in LLM-generated source code.
Its central innovation is the proposed connection between interpretable internal model representations and observable program-level security characteristics. SAE-based feature extraction and feature interaction analysis provide a mechanism for investigating latent security-related behaviors, while AST, CFG, DFG, taint analysis, and dynamic execution provide complementary evidence about generated programs.
The evidence fusion and risk assessment components integrate these analytical results to support explainable vulnerability localization. Subsequently, security-aware generation and automated repair mechanisms investigate vulnerability prevention and remediation, with independent patch validation providing evidence of security improvement and functional preservation.
The framework therefore extends beyond conventional vulnerability classification by establishing a connected research architecture for detection, interpretation, prevention, and automated repair.
Importantly, these capabilities represent the proposed design and research objectives. Their effectiveness, computational feasibility, generalizability, and practical security benefits will be determined through the experimental methodology and evaluation presented in the subsequent sections.


V. RESEARCH METHODOLOGY
5.1 Research Design
This study adopts a quantitative, experimental, and comparative research design to develop and evaluate CRAFT-Sec, an explainable multi-feature security framework for vulnerability detection, prevention, and automated repair in large language model (LLM)-generated code. The methodology integrates neural representation analysis, sparse autoencoder (SAE)-based feature extraction, program-structural analysis, security-oriented evidence fusion, and automated program repair within a unified experimental pipeline.
The research is organized around three complementary analytical dimensions: (i) detection, which identifies potentially vulnerable code using multiple representations and program-analysis evidence; (ii) interpretability, which investigates vulnerability-associated internal model features and their interactions; and (iii) mitigation, which applies security-aware generation and automated repair followed by independent validation.
Let (\mathcal{C}) denote the set of source-code samples, (\mathcal{Y}) their ground-truth security labels, and (\mathcal{M}) the set of evaluated LLMs. For a code sample (c_i \in \mathcal{C}), the framework estimates a vulnerability prediction:
[
\hat{y}i = f{\theta}(c_i,\mathbf{x}_i,\mathbf{e}_i)
]
where (\hat{y}i \in [0,1]) is the predicted vulnerability probability, (f{\theta}) is the detection function parameterized by (\theta), (\mathbf{x}_i) is the multi-feature representation, and (\mathbf{e}_i) represents evidence obtained from neural and program-analysis components.
The research design compares CRAFT-Sec against appropriate baseline configurations, including conventional static analysis, individual feature-based classifiers, neural code representations, and selected combinations of these approaches. Ablation experiments are planned to estimate the contribution of individual components. Where internal activations are unavailable, the framework will operate through its source-code analysis pathway rather than treating missing neural evidence as evidence of security.
The experimental design will distinguish predictive association from causal evidence. In particular, correlations between SAE features and vulnerable code will be interpreted as associations unless supported by controlled interventions, such as feature ablation or activation manipulation. This distinction is necessary to avoid overstating the explanatory capability of neural representations.

5.3 Dataset Collection and Preprocessing
5.3.1 Dataset Selection
The evaluation will use established vulnerability datasets and, where appropriate, controlled LLM-generated code samples. Dataset selection will consider programming-language coverage, vulnerability diversity, source-code availability, label reliability, and the availability of vulnerable and corrected code pairs.
Candidate datasets may include Big-Vul, Devign, Draper VDISC, and other publicly documented vulnerability benchmarks. Their suitability will be assessed according to licensing, annotation quality, duplication, language distribution, and compatibility with the selected analysis tools. Dataset inclusion will not imply that all samples are directly comparable: differences in collection methodology and annotation granularity will be documented.
Let the initial dataset be:
[
\mathcal{D}={(c_i,y_i,w_i)}_{i=1}^{N}
]
where (c_i) is a code sample, (y_i \in {0,1}) is its vulnerability label, (w_i) denotes optional metadata such as CWE category, programming language, repository, or commit identifier, and (N) is the total number of samples.
Where available, vulnerability labels will be mapped to Common Weakness Enumeration (CWE) categories. Samples with uncertain or conflicting labels will be flagged for manual review or excluded from analyses requiring reliable ground truth. A static-analysis warning alone will not automatically establish that a sample contains an exploitable vulnerability.
5.3.2 Dataset Splitting
The dataset will be divided into training, validation, and test subsets:
[
\mathcal{D}=\mathcal{D}{train}\cup
\mathcal{D}{val}\cup\mathcal{D}_{test}
]
with mutually exclusive partitions. A proposed split is 70%, 15%, and 15%, respectively, subject to dataset size and class distribution. Splitting will be performed at an appropriate group level, such as repository, project, or vulnerability instance, to reduce leakage from duplicated functions, near-identical code, and related commits.
Where feasible, temporal or repository-level holdout experiments will be used to assess generalization beyond the training distribution. Stratification will preserve reasonable representation of vulnerability classes and programming languages without allowing related code instances to cross partitions.
5.3.3 Preprocessing
Preprocessing will include source-code decoding, language identification, syntax validation, duplicate detection, normalization, and metadata extraction. Comments and formatting may be normalized for selected experiments, but potentially security-relevant information will not be removed indiscriminately. String literals, constants, API calls, and data-flow relationships may carry important vulnerability evidence.
For each sample, preprocessing produces:
[
c_i' = P(c_i)
]
where (P) is the preprocessing function and (c_i') is the normalized representation. The process will preserve a source map:
[
M_i: \text{normalized positions}\rightarrow
\text{original source positions}
]
This mapping enables later explanations and patches to refer to the original source code.
Samples that fail parsing will not automatically be discarded from all experiments. They may remain eligible for lexical or token-level analysis while being marked as unavailable for AST- or graph-dependent components. Missing representations will be explicitly recorded.
5.4 LLM-Generated Code Acquisition
LLM-generated code will be acquired through controlled prompting of selected models. The model set will include open-weight models that expose internal activations and, where suitable, black-box models accessible through documented inference interfaces. Model selection will consider architecture, parameter scale, programming-language support, availability, and reproducibility.
For each programming task (t_j), a prompt (p_j) will be constructed with a defined specification, expected functionality, input constraints, and relevant security requirements. The model (m_k) generates a code sample:
[
c_{jk}=G(m_k,p_j,\tau,\pi)
]
where (G) is the generation process, (\tau) denotes decoding parameters such as temperature, and (\pi) represents other generation settings, including maximum output length and sampling configuration.
To reduce uncontrolled variation, prompts will be versioned and held constant across model comparisons where technically possible. Each generation record will contain the model identifier, model version, prompt identifier, timestamp, decoding parameters, programming language, and raw output. Repeated generations will be collected for selected prompts to estimate variability across sampling runs.
The acquisition protocol will include both general programming tasks and security-sensitive tasks involving categories such as injection, improper input validation, insecure deserialization, path traversal, authentication weaknesses, and memory-safety errors where applicable. The study will avoid equating the presence of a suspicious pattern with a confirmed vulnerability. Generated samples will be assessed against task specifications and security ground truth through independent analysis.
The output of this stage is:
[
\mathcal{C}{LLM}=
{(c{jk},m_k,p_j,\pi_{jk})}
]
where (\pi_{jk}) stores generation metadata. This collection will be analyzed alongside benchmark code to examine both naturally occurring benchmark vulnerabilities and vulnerabilities arising under controlled generation conditions.
5.5 Vulnerability Detection Method
CRAFT-Sec employs a multi-feature detection model that combines lexical, syntactic, semantic, structural, and security-related information. The objective is to avoid dependence on a single representation that may overlook vulnerabilities requiring contextual or cross-statement reasoning.
For a code sample (c_i'), the feature extractor constructs:
[
\mathbf{x}i=
[\mathbf{x}{lex};
\mathbf{x}{syn};
\mathbf{x}{sem};
\mathbf{x}{str};
\mathbf{x}{sec}]
]
where the components represent lexical token patterns, syntactic constructs, semantic representations, program structure, and security-specific indicators, respectively. The semicolon denotes vector concatenation.
The lexical representation may include token embeddings, API identifiers, operators, and security-sensitive keywords. Syntactic features may encode function calls, expressions, control structures, and declarations. Semantic features may be obtained from pretrained code encoders or model representations. Structural features may include function boundaries, control-flow relationships, and data dependencies. Security features may represent source-to-sink relationships, input validation, sanitization, privilege checks, and potentially dangerous API usage.
The detection model estimates:
[
p_i=P(y_i=1\mid\mathbf{x}i)
=\sigma(f{\theta}(\mathbf{x}_i))
]
where (f_{\theta}) is the learned scoring function and (\sigma(a)=1/(1+e^{-a})) is the logistic sigmoid. A threshold (\eta) determines the predicted class:
[
\hat{y}_i=
\begin{cases}
1,&p_i\geq\eta\
0,&p_i<\eta
\end{cases}
]
The threshold will be selected using validation data according to the intended operating objective, such as prioritizing recall or balancing precision and recall. It will not be optimized on the final test set.
For binary classification, a weighted cross-entropy objective may be used:
[
\mathcal{L}{det}=
-\frac{1}{N}\sum{i=1}^{N}
\left[
\omega_1y_i\log p_i+
\omega_0(1-y_i)\log(1-p_i)
\right]
]
where (\omega_1) and (\omega_0) are class weights used to address class imbalance. Model selection will be performed on the validation partition. Evaluation will consider precision, recall, F1-score, ROC-AUC, and PR-AUC, with particular attention to PR-AUC when vulnerable samples are relatively rare.
The method will be compared with single-modality and conventional baselines to determine whether combining multiple feature groups provides measurable improvements.
5.6 Sparse Autoencoder-Based Feature Extraction
SAEs will be used to investigate interpretable latent features in the internal activations of compatible open-weight LLMs. This component is intended to identify activation patterns associated with security-relevant behaviors, not to assume that individual neurons or latent features correspond directly to human-defined vulnerabilities.
Let (\mathbf{h}\in\mathbb{R}^{d}) be an activation vector extracted from a selected model layer and token position. An SAE encodes this vector into a higher-dimensional sparse representation:
[
\mathbf{z}=
\operatorname{ReLU}(\mathbf{W}{e}\mathbf{h}+\mathbf{b}{e})
]
where (\mathbf{W}{e}\in\mathbb{R}^{d_s\times d}) is the encoder matrix, (\mathbf{b}{e}\in\mathbb{R}^{d_s}) is the encoder bias, (d) is the activation dimension, (d_s) is the SAE feature dimension, and (\mathbf{z}\in\mathbb{R}^{d_s}) is the sparse latent representation.
The decoder reconstructs the original activation:
[
\hat{\mathbf{h}}=
\mathbf{W}{d}\mathbf{z}+\mathbf{b}{d}
]
where (\mathbf{W}{d}\in\mathbb{R}^{d\times d_s}) and (\mathbf{b}{d}\in\mathbb{R}^{d}). The SAE will be trained using a reconstruction and sparsity objective:
[
\mathcal{L}{SAE}=
\frac{1}{N_h}\sum{i=1}^{N_h}
|\mathbf{h}_i-\hat{\mathbf{h}}_i|_2^2+
\lambda|\mathbf{z}_i|_1
]
where (N_h) is the number of activation vectors and (\lambda) controls sparsity. Alternative training objectives, including sparsity penalties or activation-frequency constraints, may be examined if required by the selected SAE architecture.
Activation extraction will be controlled by specifying the model layer, token-selection strategy, pooling method, and inference configuration. For code sequences, activations may be collected at individual code tokens or aggregated over function-level spans. These choices will be documented because different extraction strategies can yield different feature interpretations.
The resulting feature vector (\mathbf{z}_i) will be examined for associations with vulnerability labels and CWE categories. Feature quality will be assessed through reconstruction error, sparsity, activation frequency, stability across random seeds, and interpretability analyses. A feature will not be called vulnerability-specific solely because it activates on a small set of vulnerable samples; its behavior must also be examined on relevant non-vulnerable controls.
SAE analysis is limited to models for which internal activations can be accessed and extracted. For black-box models, this component will be marked unavailable, and the source-code analysis pathway will remain operational.
5.7 Feature Interaction Analysis
Individual latent features may not adequately represent complex security behavior. CRAFT-Sec therefore examines both feature co-activation and controlled feature interactions.
For SAE features (z_i) and (z_j), their co-activation association may be measured using Pearson correlation:
[
\rho_{ij}=
\frac{\operatorname{Cov}(z_i,z_j)}
{\sigma_{z_i}\sigma_{z_j}}
]
where (\operatorname{Cov}) is covariance and (\sigma_{z_i}) and (\sigma_{z_j}) are standard deviations. Correlation is used as a screening measure, not as evidence that one feature causes another or that the pair causes a vulnerability.
To investigate interaction effects, a detection or behavior function (g) will be evaluated under controlled feature conditions. For a pair of features (i) and (j), a second-order interaction effect is:
[
\Delta_{ij}=
g(1,1)-g(1,0)-g(0,1)+g(0,0)
]
Here, (g(a,b)) denotes the model output under specified interventions on features (i) and (j), where 1 and 0 indicate the selected activation conditions. In continuous settings, feature values may instead be set to calibrated activation levels or manipulated through controlled scaling.
A non-zero (\Delta_{ij}) indicates a non-additive response under the intervention design. However, interpretation requires controls because activation manipulation may produce off-distribution internal states. Therefore, interventions will be compared with matched controls, such as activation-preserving transformations or interventions on unrelated features. Feature ablation, activation patching, and dose-response analyses may be used where supported by the model architecture.
The analysis will prioritize features that are stable across samples and associated with meaningful security contexts. Candidate interactions will be evaluated on held-out samples to reduce selection bias. Results will be described as causal evidence only when the intervention design supports that interpretation; otherwise, they will be reported as statistical associations.
5.8 Explainable Vulnerability Localization
After detecting a potentially vulnerable sample, CRAFT-Sec aims to identify the code regions and program elements contributing to the prediction. Localization is formulated as a ranking problem over source-code units, such as lines, statements, expressions, or functions.
Let (r_i) denote a source-code region. Its localization score is:
[
L(r_i)=
\alpha a_i+
\beta s_i+
\gamma t_i+
\delta n_i
]
where (a_i) represents model attribution, (s_i) static-analysis evidence, (t_i) taint or data-flow evidence, and (n_i) relevant neural-feature evidence. The coefficients (\alpha,\beta,\gamma,\delta) are non-negative parameters calibrated on validation data. If a modality is unavailable, its absence will be represented explicitly rather than assigned a zero score that could be misinterpreted as negative evidence.
Attribution may be estimated using gradient-based methods, perturbation-based importance, or feature ablation. For example, an input-gradient attribution for token (x_j) may be represented as:
[
A_j=
\left|
\frac{\partial f_{\theta}(\mathbf{x})}
{\partial \mathbf{x}_j}
\right|
]
where (\mathbf{x}_j) is the representation associated with token (j). Attribution scores will be aggregated to source-code regions using the source map produced during preprocessing.
A localization output will contain ranked regions, suspected weakness categories, supporting program-analysis evidence, and relevant model-feature associations. Localization performance will be evaluated using line-level or function-level precision, recall, F1-score, and top-(k) hit rate, depending on the granularity of available ground truth. Explanations will distinguish directly observed evidence from model-derived attribution.
5.9 Static and Dynamic Program Analysis
CRAFT-Sec integrates static and dynamic program analysis to complement neural detection. These methods provide evidence about code structure, data dependencies, and execution behavior that may not be reliably captured by learned representations alone.
5.9.1 Static Analysis
Static analysis examines source code without executing it. The proposed pipeline may construct abstract syntax trees (ASTs), control-flow graphs (CFGs), and data-flow graphs (DFGs).
An AST represents syntactic structure:
[
G_{AST}=(V_{AST},E_{AST})
]
where (V_{AST}) contains syntactic nodes and (E_{AST}) represents parent-child relationships. A CFG is represented as:
[
G_{CFG}=(V_{CFG},E_{CFG})
]
where nodes represent basic blocks and directed edges represent possible control transfers. A DFG is:
[
G_{DFG}=(V_{DFG},E_{DFG})
]
where nodes represent definitions and uses of program values and edges represent data dependencies.
Taint analysis will be used to examine whether untrusted sources can influence sensitive sinks without adequate validation or sanitization. Let (S) be the set of source nodes and (K) the set of security-sensitive sink nodes. A potential taint path exists if:
[
\exists s\in S,\ k\in K:
s\leadsto k
]
where (\leadsto) denotes a reachable data-flow path. Sanitization and validation operations will be considered when evaluating whether a path is potentially exploitable.
Static-analysis tools will be selected according to programming-language compatibility and documented rule coverage. Tool versions, configurations, rule identifiers, and suppression policies will be recorded. Static warnings will be treated as candidate evidence and reviewed against ground truth or independent validation.
5.9.2 Dynamic Analysis
Dynamic analysis executes code under controlled inputs and environments to observe runtime behavior. Let (P) be a program, (T) a test-input set, and (E) the execution environment. Dynamic observations are represented as:
[
\mathbf{h}{dyn}=F{dyn}(P,T,E)
]
The observation vector may include crashes, exceptions, assertion failures, sanitizer reports, unexpected outputs, resource-limit violations, or security-policy violations.
Where appropriate, test inputs will include normal cases, boundary cases, malformed inputs, and security-oriented test cases. Fuzzing may be applied to selected functions or interfaces when supported by the language and execution environment.
Dynamic analysis will use isolated execution environments, resource limits, controlled dependencies, and non-production data. A test that does not trigger a vulnerability cannot prove that the program is secure; it only provides evidence under the tested conditions. Similarly, a crash is not automatically a security vulnerability without contextual assessment.
5.10 Multi-Feature Evidence Fusion
The evidence-fusion component combines outputs from neural detection, SAE analysis, feature interactions, static analysis, and dynamic analysis. Its purpose is to produce a unified assessment while retaining the provenance and reliability of each evidence source.
For sample (c_i), define the evidence vector:
[
\mathbf{e}i=
[
e{neural},
e_{SAE},
e_{interaction},
e_{AST},
e_{CFG},
e_{DFG},
e_{taint},
e_{dynamic}
]
]
Each component represents a feature, score, or structured finding from the corresponding modality. Categorical and graph-based findings will be converted into suitable representations using modality-specific encoders rather than assuming that all raw outputs share a common numerical scale.
A fusion function produces:
[
\mathbf{h}{fusion}=F{\phi}(\mathbf{e}_i,\mathbf{m}_i)
]
where (F_{\phi}) is the fusion model, (\phi) denotes its parameters, and (\mathbf{m}_i) is an availability mask indicating which modalities were observed. The mask prevents unavailable evidence from being interpreted as negative evidence.
A weighted fusion baseline may be defined as:
[
S_i=
\frac{\sum_{j=1}^{J}m_{ij}w_jq_{ij}}
{\sum_{j=1}^{J}m_{ij}w_j}
]
where (q_{ij}) is the normalized evidence score for modality (j), (w_j) is its calibrated reliability weight, (m_{ij}\in{0,1}) indicates modality availability, and (J) is the number of modalities. If no modality is available, the score is undefined and the sample must be flagged for insufficient evidence.
The fused representation is mapped to a vulnerability probability through a calibrated prediction head. Calibration will be assessed on validation data using appropriate methods, such as temperature scaling or isotonic regression, where justified by sample size. The fusion model will be compared with individual modalities and simpler weighted baselines to determine whether the additional complexity provides measurable benefit.
5.11 Security Risk Assessment
Detection confidence and security risk are related but distinct. A high probability of vulnerability does not necessarily imply high operational severity. CRAFT-Sec therefore separates vulnerability likelihood from risk prioritization.
For a detected finding (v), a risk score may be defined as:
[
R(v)=
\alpha P(v)+
\beta S(v)+
\gamma E(v)+
\delta I(v)
]
where (P(v)) is the calibrated vulnerability probability, (S(v)) is a severity measure, (E(v)) represents exposure or exploitability evidence, and (I(v)) represents potential impact. The coefficients (\alpha,\beta,\gamma,\delta) are non-negative parameters selected using a documented calibration or decision policy.
Where applicable, CVSS scores may be used as an established severity reference. CVSS severity will not be treated as a substitute for vulnerability detection confidence, and the framework will not infer exploitability solely from a CWE label.
Risk categories may be defined through validation-informed thresholds:
[
C(v)=
\begin{cases}
\text{Critical},&R(v)\geq \tau_3\
\text{High},&\tau_2\leq R(v)<\tau_3\
\text{Medium},&\tau_1\leq R(v)<\tau_2\
\text{Low},&R(v)<\tau_1
\end{cases}
]
where (\tau_1,\tau_2,\tau_3) are predefined thresholds. These categories are intended to support prioritization, not to replace expert security review. Reports will preserve the underlying evidence, confidence, and uncertainty.
5.12 Security-Aware Vulnerability Prevention
The prevention component aims to reduce vulnerability introduction during code generation. It uses security requirements, identified risk patterns, and feedback from detection and program-analysis components to guide generation.
For a task prompt (p), the generation process receives a security constraint set (\mathcal{Q}):
[
c^*=G(m,p,\mathcal{Q},\pi)
]
where (m) is the selected model and (\pi) denotes generation parameters. The constraint set may include input-validation requirements, secure API usage, parameterized database access, safe deserialization, appropriate authorization checks, and relevant language-specific secure-coding rules.
A security-aware objective can be represented as:
[
\mathcal{J}{gen}=
\mathcal{L}{task}+
\lambda_s\mathcal{L}{security}+
\lambda_c\mathcal{L}{constraint}
]
where (\mathcal{L}{task}) measures deviation from functional requirements, (\mathcal{L}{security}) penalizes security violations, (\mathcal{L}_{constraint}) penalizes violations of explicit security constraints, and the (\lambda) parameters control their relative importance.
In an inference-only setting, these terms may be operationalized through prompt constraints, candidate generation, security feedback, and candidate selection rather than direct gradient-based model training. If model fine-tuning is performed, the training procedure and data will be documented separately.
The prevention experiment will compare unconstrained generation with security-aware generation under matched prompts and decoding configurations. Outcomes will include vulnerability incidence, functional correctness, task completion, and code quality. A reduction in detected vulnerabilities will not be considered sufficient if it results from generating incomplete, non-functional, or excessively restrictive code.
5.13 Automated Program Repair
The repair component generates candidate patches for findings that have sufficient evidence and a well-defined repair target. Given a vulnerable program (P), a localization result (L), and security constraints (\mathcal{Q}), the repair model generates a candidate patch:
[
P'=G_{repair}(P,L,\mathcal{Q},\pi_r)
]
where (\pi_r) represents repair-generation parameters. The repair context will include the relevant source region, surrounding function, vulnerability category, evidence summary, and applicable secure-coding constraints.
The repair objective is multi-dimensional:
[
\mathcal{L}{repair}=
\lambda_s\mathcal{L}{sec}+
\lambda_f\mathcal{L}{func}+
\lambda_r\mathcal{L}{reg}+
\lambda_d\mathcal{L}_{diff}
]
where (\mathcal{L}{sec}) measures residual security weaknesses, (\mathcal{L}{func}) measures functional deviations, (\mathcal{L}{reg}) measures regression failures, and (\mathcal{L}{diff}) penalizes unnecessary changes. The (\lambda) terms are objective weights, not experimentally established constants.
The repair process may generate multiple candidates using different prompts or decoding seeds. Candidates will be ranked according to security evidence, functional test results, patch size, and compatibility with the original specification. The framework will preserve the original program and maintain patch provenance to support rollback and review.
A generated patch will be considered a candidate repair only. It will not be labeled successful until it passes the validation and verification procedure described in Section 4.14.
5.14 Patch Validation and Verification
Patch validation is essential because a syntactically valid patch may introduce new vulnerabilities or break intended functionality. CRAFT-Sec therefore applies a staged validation procedure to each candidate patch.
First, syntax and compilation checks determine whether the patched program is structurally valid. Second, functional tests assess whether the original requirements remain satisfied. Third, regression tests examine whether previously supported behavior has been preserved. Fourth, security analysis is repeated on the patched code using the relevant detection and program-analysis components. Finally, dynamic security tests are executed where appropriate.
Let (P) be the original program and (P') a candidate patched program. Define:
[
V(P')=
V_{syntax}(P')
\land V_{func}(P,P')
\land V_{reg}(P,P')
\land V_{security}(P')
]
where each term is a Boolean validation condition. A patch is accepted only when all required conditions are satisfied:
[
Accept(P')=
\begin{cases}
1,&V(P')=1\
0,&V(P')=0
\end{cases}
]
The functional validation term checks whether the patched program satisfies the original task specification and relevant tests. The security validation term checks whether the targeted weakness has been mitigated and whether the patch introduces new security findings. The criteria will be defined before final evaluation to avoid selectively accepting favorable patches.
Repair effectiveness will be measured using metrics such as valid-patch rate, security-fix rate, regression rate, functional test pass rate, and patch minimality. The valid-patch rate is:
[
VPR=
\frac{N_{accepted}}{N_{generated}}
]
where (N_{accepted}) is the number of candidate patches satisfying the acceptance criteria and (N_{generated}) is the total number of candidate patches. Security-fix rate will use only cases with independently established vulnerable ground truth as its denominator. Failed patches will be retained in the evaluation record to prevent survivorship bias.
5.15 Experimental Implementation
The implementation will be organized into modular components corresponding to the CRAFT-Sec architecture. The data layer will manage datasets, source-code samples, labels, metadata, and train-validation-test partitions. The model layer will implement code encoders, vulnerability classifiers, and compatible SAE architectures. The program-analysis layer will integrate parsers, graph construction, static-analysis tools, taint analysis, and controlled dynamic execution. The mitigation layer will implement security-aware generation, repair generation, and patch validation. The reporting layer will aggregate predictions, explanations, risk scores, and validation outcomes.
A consistent experimental configuration will be maintained for each run. Let:
[
\Omega=
(M,D,L,\theta,\tau,\lambda,s)
]
represent an experiment configuration, where (M) denotes the model, (D) the dataset, (L) the selected analysis layer or representation, (\theta) the learned parameters, (\tau) the decision threshold, (\lambda) the relevant regularization or loss weights, and (s) the random seed.
The implementation will use version-controlled code and configuration files. Model inference settings, hardware environment, software dependencies, analysis-tool versions, and dataset preprocessing parameters will be recorded. Where model APIs or hosted services are used, their model identifiers and accessible version information will be documented because provider-side changes may affect reproducibility.
The experimental evaluation will include the following groups:
                        1. Detection experiments: compare CRAFT-Sec with individual feature groups, conventional static analysis, and selected learned baselines.
                        2. SAE experiments: evaluate reconstruction quality, sparsity, feature stability, and association with vulnerability categories.
                        3. Interaction experiments: compare co-activation analysis with controlled feature interventions and appropriate controls.
                        4. Localization experiments: measure whether explanations identify independently annotated vulnerable regions.
                        5. Evidence-fusion experiments: compare full fusion with modality-specific and ablated configurations.
                        6. Prevention experiments: compare unconstrained and security-aware generation under matched task conditions.
                        7. Repair experiments: assess candidate repair generation, patch validity, security-fix rate, and regression behavior.
The evaluation will use repeated runs and multiple random seeds where stochastic training or generation is involved. Comparisons will be paired by task, sample, or prompt wherever possible. Confidence intervals and effect sizes will accompany performance estimates. Statistical tests will be selected according to the distribution and pairing structure of the observations, with correction for multiple comparisons when multiple hypotheses or model configurations are evaluated.
The primary classification metrics will include precision, recall, F1-score, ROC-AUC, and PR-AUC. Calibration may be evaluated using Brier score and expected calibration error. Localization will be evaluated using line- or function-level metrics. Prevention and repair will be evaluated using vulnerability incidence, functional correctness, accepted-patch rate, and regression frequency. Results will also be stratified by programming language, CWE category, dataset, and model to reveal performance differences that aggregate metrics may conceal.
Ablation studies will remove or disable individual components, such as SAE features, interaction evidence, taint analysis, dynamic analysis, or evidence fusion. These experiments will estimate the marginal contribution of each component under the evaluated conditions. They will not automatically establish that a component is universally necessary or sufficient.
5.16 Reproducibility Considerations
Reproducibility will be addressed through explicit documentation of datasets, code versions, prompts, model configurations, preprocessing operations, analysis settings, and experimental seeds. Dataset identifiers, licensing information, source references, label definitions, and exclusion criteria will be recorded. When redistribution of source code is restricted, sample identifiers and acquisition procedures will be provided where legally and ethically permissible.
For each experiment, the following information will be preserved:
                        * Dataset version, partitioning strategy, and sample identifiers.
                        * Model name, version, inference settings, and accessible architecture details.
                        * Prompt templates, generation parameters, and repeated-generation identifiers.
                        * SAE architecture, extraction layer, activation-selection strategy, and training configuration.
                        * Static- and dynamic-analysis tool versions, rules, and execution settings.
                        * Fusion parameters, thresholds, calibration procedure, and missing-modality policy.
                        * Repair prompts, candidate-generation settings, validation tests, and patch outcomes.
                        * Random seeds, software dependencies, hardware specifications, and run logs.
Where stochastic operations are used, random seeds will be fixed and repeated trials will be conducted to estimate variability. Deterministic execution will be used where supported, while nondeterministic operations and hardware-dependent behavior will be documented. For hosted LLMs, exact reproducibility may not be guaranteed because model versions and service implementations can change. Such limitations will be reported explicitly.
Data leakage will be mitigated through repository- or project-level splitting, duplicate detection, and separation of prompt templates or related code instances where appropriate. Thresholds and hyperparameters will be selected using training and validation data only. The test set will be reserved for final evaluation. Manual annotations will use documented criteria, and inter-annotator agreement will be measured where multiple reviewers are available.
The study will also address construct validity, internal validity, external validity, and conclusion validity. Construct validity concerns whether the selected datasets and labels adequately represent real security weaknesses. Internal validity concerns leakage, confounding variables, and uncontrolled model or generation settings. External validity concerns generalization across languages, models, repositories, and vulnerability categories. Conclusion validity concerns statistical power, uncertainty, multiple testing, and the reliability of the selected metrics.
5.17 Methodological Alignment with the Research Questions
The methodology is designed to address the research questions through complementary experimental procedures.
RQ1—Multi-feature vulnerability detection: Sections 4.3–4.5 and 4.10 evaluate whether combining lexical, syntactic, semantic, structural, and security-related representations improves vulnerability detection compared with individual feature groups and selected baselines.
RQ2—SAE-based feature extraction: Section 4.6 examines whether sparse latent representations capture interpretable activation patterns associated with vulnerability-related code behavior. Reconstruction, sparsity, stability, and association analyses provide measurable evaluation criteria.
RQ3—Feature interactions: Section 4.7 investigates relationships between latent features and tests selected interactions using controlled interventions. This design distinguishes co-activation from evidence of causal influence.
RQ4—Integration of neural and program analysis: Sections 4.9 and 4.10 evaluate how neural representations, AST/CFG/DFG structures, taint analysis, and dynamic observations contribute to unified vulnerability assessment.
RQ5—Explainable localization: Section 4.8 evaluates whether combined attribution and program-analysis evidence can identify vulnerable lines, statements, or functions with measurable localization accuracy.
RQ6—Automated repair: Sections 4.13 and 4.14 examine candidate patch generation and determine whether proposed repairs remove the targeted weakness while preserving required functionality and avoiding regressions.
RQ7—Security-aware generation: Section 4.12 compares security-constrained generation with an unconstrained baseline under controlled prompting and evaluates both security outcomes and functional correctness.
RQ8—Overall framework effectiveness: Sections 4.15 and 4.16 establish the comparative, ablation, statistical, and reproducibility procedures required to evaluate CRAFT-Sec across models, datasets, programming languages, and CWE categories.
Overall, the proposed methodology treats CRAFT-Sec as an integrated but modular security framework. Its central methodological principle is that vulnerability detection, neural interpretability, program analysis, and automated repair should provide complementary and independently assessable evidence. By preserving modality provenance, separating predictive association from causal intervention, and requiring independent patch validation, the methodology establishes a rigorous basis for evaluating the framework without presupposing its effectiveness or claiming experimental findings before they are obtained.


V. MATHEMATICAL FORMULATION OF CRAFT-Sec
The mathematical formulation of CRAFT-Sec establishes a unified representation of source code, vulnerability classification, neural interpretability, program analysis, evidence integration, security risk assessment, and automated repair. The framework combines established mathematical foundations from machine learning, sparse representation learning, graph theory, program analysis, and optimization with several proposed formulations designed specifically for the integration of these components.
To maintain mathematical rigor, the formulations are distinguished as follows:
                        * Established formulations: Mathematical structures already used in machine learning, sparse autoencoders, graph theory, attribution methods, data-flow analysis, and software verification.
                        * Proposed formulations: New framework-level definitions introduced to connect the established techniques within CRAFT-Sec. Their effectiveness must be established experimentally rather than assumed.
The objective is to formulate vulnerability detection and remediation as a connected process in which a source-code sample is represented, assessed for security weaknesses, explained through interpretable evidence, and transformed into a candidate patch subject to functional and security verification.
5.1 Source Code Representation
Source code contains several complementary forms of information, including lexical patterns, syntactic structures, semantic dependencies, and security-relevant operations. A representation based exclusively on token sequences may fail to capture structural relationships, whereas graph-based representations alone may not preserve all contextual information. CRAFT-Sec therefore adopts a multi-view representation.
Let  denote a source-code sample. Its tokenized representation is:



where  is the -th token and  is the number of tokens.
A token encoder maps each token into a continuous vector:

5.3 Sparse Autoencoder Encoding
To investigate interpretable internal representations of LLMs, CRAFT-Sec employs a Sparse Autoencoder (SAE). An SAE maps high-dimensional model activations into a sparse latent feature space.
Let:
\[ \mathbf{h}\in\mathbb{R}^{d} \]
denote an activation vector extracted from a selected LLM layer and token position.
The encoder is defined as:
\[ \boxed{ \mathbf{z}= \operatorname{ReLU} (\mathbf{W}_{e}\mathbf{h}+\mathbf{b}_{e}) } \tag{5} \]
where:
                              * \(\mathbf{W}_{e}\in\mathbb{R}^{d_s\times d}\) is the encoder weight matrix.
                              * \(\mathbf{b}_{e}\in\mathbb{R}^{d_s}\) is the encoder bias.
                              *  is the original activation dimension.
                              *  is the SAE latent dimension.
                              * \(\mathbf{z}\in\mathbb{R}^{d_s}\) is the sparse latent representation.
                              * \(\operatorname{ReLU}(u)=\max(0,u)\) is the rectified linear activation function.
The decoder reconstructs the original activation:
\[ \hat{\mathbf{h}}= \mathbf{W}_{d}\mathbf{z}+\mathbf{b}_{d} \tag{6} \]
where \(\mathbf{W}_{d}\in\mathbb{R}^{d\times d_s}\) and \(\mathbf{b}_{d}\in\mathbb{R}^{d}\).
The SAE objective is:
\[ \boxed{ \mathcal{L}_{SAE}= \frac{1}{N_h} \sum_{i=1}^{N_h} \|\mathbf{h}_i-\hat{\mathbf{h}}_i\|_2^2 + \lambda\|\mathbf{z}_i\|_1 } \tag{7} \]
where  is the number of activation vectors,  controls the sparsity penalty, and \(\|\cdot\|_1\) denotes the L1 norm.
The first term minimizes reconstruction error, while the second encourages sparse latent activations.
Theoretical foundation. Equations (5)–(7) follow established autoencoder and sparse representation learning principles.
Computational interpretation. The encoder decomposes an activation vector into a set of latent features. The decoder reconstructs the original activation from these features. Sparse optimization encourages a relatively small subset of features to activate for a given input.
Role in CRAFT-Sec. SAE representations provide a mechanism for examining whether internal model features are associated with security-relevant code patterns. They also provide the feature space used in subsequent interaction and attribution analyses.
The SAE does not automatically establish that a latent feature represents a particular vulnerability. Feature interpretation requires activation analysis, contextual examination, and suitable controls.
Formulation status: The SAE architecture and sparsity objective are established. Their use for vulnerability-oriented representation analysis within CRAFT-Sec is a proposed application.

5.5 Feature Interaction Strength
A vulnerability-related behavior may involve multiple latent features acting jointly. Consequently, examining features independently may fail to capture non-additive relationships.
First, statistical co-activation between two SAE features is measured using Pearson correlation:
\[ \rho_{ij}= \frac{ \operatorname{Cov}(z_i,z_j) }{ \sigma_i\sigma_j } \tag{11} \]
where \(\operatorname{Cov}(z_i,z_j)\) is the covariance between features  and , and  are their standard deviations.
However, correlation measures association rather than causal interaction. CRAFT-Sec therefore proposes a controlled second-order interaction measure:
\[ \boxed{ I_{ij}= g(1,1)-g(1,0)-g(0,1)+g(0,0) } \tag{12} \]
where  denotes the selected model output under controlled interventions on features  and . The values 1 and 0 represent the specified intervention states, such as enabling or suppressing a feature relative to a defined reference condition.
For continuous activations, the intervention states may instead represent calibrated activation levels. A more general formulation is:
\[ I_{ij}(a,b)= g(z_i=a,z_j=b) -g(z_i=a,z_j=0) -g(z_i=0,z_j=b) +g(z_i=0,z_j=0) \tag{13} \]
where  and  are intervention magnitudes.
A non-zero interaction indicates a non-additive change in model output under the specified intervention conditions. It does not automatically demonstrate that the features cause an exploitable software vulnerability. Activation interventions may also introduce distribution shifts, which must be examined through matched controls and activation-preserving comparisons.
Theoretical foundation. Equation (11) is an established correlation measure. Equations (12) and (13) are based on established factorial interaction and finite-difference principles, adapted to SAE feature interventions.
Computational interpretation. The method compares the model response when two features are manipulated jointly against the responses when each is manipulated independently.
Role in CRAFT-Sec. Feature interaction analysis helps investigate whether combinations of latent representations provide additional information about vulnerability-related model behavior.
Formulation status: Correlation and second-order interaction principles are established. Their specific operationalization for CRAFT-Sec SAE interventions is proposed.
5.6 Feature Attribution
Feature attribution identifies which input elements or latent features contribute to a model prediction. CRAFT-Sec uses attribution to connect vulnerability predictions with interpretable source-code regions and neural representations.
For a differentiable detection function , the gradient attribution of input feature  is:
\[ A_j= \left| \frac{\partial f_{\theta}(\mathbf{x})} {\partial x_j} \right| \tag{14} \]
where  is the local sensitivity of the prediction to input feature .
For an input representation with a baseline , Integrated Gradients can be expressed as:
\[ IG_j(\mathbf{x})= (x_j-x'_j) \int_0^1 \frac{\partial f_{\theta} (\mathbf{x}'+\alpha(\mathbf{x}-\mathbf{x}'))} {\partial x_j} \,d\alpha \tag{15} \]
where  is the reference input and  indexes points along the interpolation path from the baseline to the actual input.
For SAE features, attribution may similarly be computed with respect to latent dimensions:
\[ A_j^{SAE}= \left| \frac{\partial f_{\theta}(\mathbf{z})} {\partial z_j} \right| \tag{16} \]
where  is the activation of SAE feature .
Theoretical foundation. Gradient attribution and Integrated Gradients are established explainable-AI techniques.
Computational interpretation. These formulations quantify local prediction sensitivity or accumulated contribution relative to a baseline. Token-level or feature-level attribution values can be aggregated into statements, lines, functions, or latent feature groups.
Role in CRAFT-Sec. Attribution provides a model-oriented explanation that can be compared with AST, CFG, DFG, and taint-analysis evidence. It helps identify code regions associated with a vulnerability prediction.
Attribution must not be interpreted as proof of causality or exploitability. Its reliability will be examined using perturbation tests, stability analysis, and comparison with independently annotated vulnerable regions.
Formulation status: Equations (14)–(16) are established attribution formulations or direct adaptations of them.

5.10 Security Risk Scoring
Vulnerability probability alone is insufficient for determining operational security priority. A vulnerability with a high predicted probability may have limited impact, while a less certain finding may concern a highly exposed critical component.
CRAFT-Sec therefore proposes a risk score that combines detection confidence, severity, exposure, and impact:
\[ \boxed{ R(v)= \alpha P(v)+ \beta S(v)+ \gamma E(v)+ \delta I(v) } \tag{28} \]
where:
                                       *  is the calibrated probability that finding  represents a vulnerability.
                                       *  is the normalized severity measure.
                                       *  is the normalized exposure or exploitability evidence.
                                       *  is the normalized potential impact.
                                       *  are non-negative weighting parameters.
The input variables must be normalized to compatible ranges before aggregation. The weights should be selected through a documented calibration or decision policy rather than arbitrary assignment.
The resulting score may be mapped to priority categories:
\[ C(v)= \begin{cases} \text{Critical},&R(v)\geq\tau_3\\ \text{High},&\tau_2\leq R(v)<\tau_3\\ \text{Medium},&\tau_1\leq R(v)<\tau_2\\ \text{Low},&R(v)<\tau_1 \end{cases} \tag{29} \]
where  are predefined thresholds.
Theoretical foundation. Equation (28) is a proposed linear multi-criteria risk aggregation model. Equation (29) is an established threshold-based categorization principle.
Computational interpretation. Each vulnerability finding receives a priority score based on its likelihood and security context. The score supports ranking and remediation scheduling.
Role in CRAFT-Sec. Risk scoring determines which findings should receive priority for human review, prevention, or automated repair.
CVSS may be used as an external severity reference where appropriate, but it should not be combined with the same underlying impact factors twice. The risk score is a prioritization mechanism, not a replacement for formal vulnerability validation.
Formulation status: The weighted risk equation is newly proposed for CRAFT-Sec. Threshold categorization is established.

5.12 Patch Correctness
A generated patch is not considered correct merely because it compiles or passes a limited number of tests. Patch correctness requires preservation of intended program behavior and satisfaction of the relevant specification.
Let  be the original program,  the patched program, and  a test set. Functional test preservation is defined as:
\[ \operatorname{Pass}_{func}(P',\mathcal{T})= \frac{ \sum_{t\in\mathcal{T}} \mathbb{I}[P'(t)=o_t] }{ |\mathcal{T}| } \tag{34} \]
where  is the expected output for test , and  is the number of tests.
The test-based functional correctness condition is:
\[ V_{func}(P')= \mathbb{I} [ \operatorname{Pass}_{func}(P',\mathcal{T})=1 ] \tag{35} \]
This condition means that all required tests pass under the selected test suite. It does not prove correctness for all possible inputs.
Where a formal specification is available, stronger correctness can be expressed through Hoare logic:
\[ \boxed{ \{\mathcal{P}\}\ P'\ \{\mathcal{Q}\} } \tag{36} \]
where  is the precondition,  is the patched program, and  is the required postcondition.
Theoretical foundation. Equations (34)–(35) follow established software testing principles. Equation (36) follows Hoare logic and formal program verification.
Computational interpretation. Test-based correctness checks whether the patch preserves expected behavior on a defined test set. Formal verification, where feasible, checks whether the patch satisfies specified preconditions and postconditions.
Role in CRAFT-Sec. Patch correctness prevents the repair component from accepting security modifications that break the intended functionality of the original program.
Formulation status: Test-based validation and Hoare logic are established. Their use as acceptance conditions in CRAFT-Sec is a proposed integration.
5.13 Security Preservation
Functional correctness alone does not guarantee that a patch is secure. A patch may preserve expected outputs while introducing a new vulnerability or leaving the original weakness unresolved.
Let  denote the set of independently validated vulnerabilities in program . The targeted vulnerability-removal condition is:
\[ \mathcal{V}_{target}(P') \cap \mathcal{V}_{target}(P) = \varnothing \tag{37} \]
where  is the set of targeted vulnerability instances in the original program and  is the corresponding set after patching. In practice, correspondence between findings must be established using vulnerability identifiers, code locations, and relevant analysis evidence.
A broader security-preservation condition is:
\[ \boxed{ \mathcal{V}(P') \setminus \mathcal{V}(P) = \varnothing } \tag{38} \]
where set difference identifies vulnerabilities present after patching but not identified in the original program.
Equation (38) expresses the ideal requirement that the patch introduces no new vulnerabilities. Because practical vulnerability detectors are imperfect, this condition can only be approximated using the available validation methods and should not be claimed as formally established unless supported by suitable verification.
The overall patch acceptance function is therefore:
\[ \boxed{ Accept(P')= V_{syntax}(P') \land V_{func}(P') \land V_{reg}(P') \land V_{security}(P') } \tag{39} \]
where  checks syntactic validity,  checks functional correctness,  checks regression behavior, and  checks mitigation of the targeted weakness and the absence of identified new security findings.
Theoretical foundation. Equations (37)–(39) are proposed framework-level acceptance conditions based on set theory, software testing, and security verification principles.
Computational interpretation. The patch is accepted only after the targeted vulnerability has been re-evaluated, functional tests have passed, and security analysis has not identified new findings that violate the acceptance policy.
Role in CRAFT-Sec. Security preservation ensures that automated repair is evaluated as a security transformation rather than merely a code-generation task.

VI. ALGORITHMS AND PSEUDOCODE
6.1 Introduction
This section formalizes the proposed CRAFT-Sec framework through nine interrelated algorithms covering vulnerability detection, sparse autoencoder (SAE)-based security feature extraction, latent feature interaction analysis, explainable vulnerability localization, multi-feature evidence fusion, security-aware vulnerability prevention, automated vulnerability repair, and patch validation. The algorithms operationalize the mathematical formulations introduced in Section V and establish a reproducible computational description of the proposed methodology.
CRAFT-Sec follows a modular architecture in which neural representations, source-code structures, program dependencies, and security-analysis results contribute complementary evidence. Its algorithmic design distinguishes three principal processing stages: (i) vulnerability identification and evidence extraction, (ii) explainable risk assessment and vulnerability prevention, and (iii) repair generation and independent patch verification.
An important architectural consideration is that internal model activations are not available for every LLM. Accordingly, SAE-based feature extraction and interaction analysis are conditionally executed when the target model exposes suitable internal representations. When such representations are unavailable, CRAFT-Sec continues through source-code analysis, including lexical, syntactic, semantic, structural, and security-related feature extraction. Missing neural evidence is explicitly represented during evidence fusion rather than being interpreted as evidence of security.
The algorithms are proposed procedures. Their pseudocode defines the intended implementation and evaluation protocol; it does not establish that the procedures have already been implemented or experimentally validated.

6.3 Algorithm 1: Overall CRAFT-Sec Security Framework
Purpose: To coordinate the complete CRAFT-Sec pipeline, integrating source-code preprocessing, multi-feature vulnerability detection, SAE-based interpretability, program analysis, evidence fusion, risk assessment, prevention, repair, and patch verification.
Input:
                                             * (c): LLM-generated source code.
                                             * (m): Target LLM, if available.
                                             * (\mathcal{Q}): Functional and regression test suite.
                                             * (\Theta): Configured detection, fusion, and risk-assessment parameters.
                                             * (\mathcal{C}): Analysis configuration, including available static and dynamic analysis tools.
                                             * (\mathcal{G}): Optional security-aware generation configuration.
Output:
                                             * (\mathcal{R}): Explainable security assessment report.
                                             * (c^*): Verified repaired code, if an acceptable repair is identified.
                                             * (\mathcal{E}): Consolidated vulnerability evidence.
                                             * (s): Final processing status.
Initialization:
Initialize the source-code representation, structural graphs, neural feature representations, vulnerability evidence, risk scores, and repair candidates. Set unavailable analysis components to (\bot). Initialize the final status as ANALYSIS_COMPLETED_WITHOUT_REPAIR.
Pseudocode:
Algorithm 1: Overall CRAFT-Sec Security Framework


Input:
    Source code c
    Target model m
    Test suite Q
    Parameters Θ
    Analysis configuration C
    Generation configuration G


Output:
    Security report R
    Verified code c*
    Consolidated evidence E
    Processing status s


1:  Initialize E ← ∅
2:  Initialize c* ← c
3:  Initialize R ← ∅
4:  Initialize s ← ANALYSIS_COMPLETED_WITHOUT_REPAIR


5:  c_pre ← PREPROCESS_CODE(c)


6:  X ← EXTRACT_SOURCE_FEATURES(c_pre)
7:  G_AST ← BUILD_AST(c_pre)
8:  G_CFG ← BUILD_CFG(c_pre)
9:  G_DFG ← BUILD_DFG(c_pre)


10: E_static ← STATIC_SECURITY_ANALYSIS(
        c_pre, G_AST, G_CFG, G_DFG, C)


11: E_dynamic ← DYNAMIC_SECURITY_ANALYSIS(c_pre, Q, C)


12: if INTERNAL_ACTIVATIONS_AVAILABLE(m) then
13:     H ← EXTRACT_MODEL_ACTIVATIONS(m, c_pre)
14:     Z ← SAE_FEATURE_EXTRACTION(H)
15:     F ← IDENTIFY_SECURITY_RELEVANT_FEATURES(Z)
16:     I ← FEATURE_INTERACTION_ANALYSIS(F, H)
17:     E_neural ← BUILD_NEURAL_EVIDENCE(Z, F, I)
18: else
19:     E_neural ← MISSING_EVIDENCE
20: end if


21: E_detection ← VULNERABILITY_DETECTION(
        X, E_static, E_dynamic, E_neural, Θ)


22: E ← MULTI_FEATURE_EVIDENCE_FUSION(
        E_detection, E_static, E_dynamic, E_neural, Θ)


23: L ← EXPLAINABLE_VULNERABILITY_LOCALIZATION(
        c_pre, E, G_AST, G_CFG, G_DFG)


24: V ← IDENTIFY_VULNERABILITIES(E, L)


25: for each vulnerability v in V do
26:     RISK[v] ← SECURITY_RISK_ASSESSMENT(v, E, Θ)
27: end for


28: R ← GENERATE_SECURITY_REPORT(V, RISK, L, E)


29: if GENERATION_MODE_ENABLED(G) then
30:     c_prevent ← SECURITY_AWARE_PREVENTION(
            c_pre, V, RISK, G)
31:     if c_prevent ≠ ⊥ then
32:         E_prevent ← REANALYZE_SECURITY(c_prevent, C)
33:         if SECURITY_CRITERIA_SATISFIED(
                c_prevent, E_prevent, Θ) then
34:             c* ← c_prevent
35:             s ← PREVENTION_VERIFIED
36:         end if
37:     end if
38: end if


39: if V ≠ ∅ and s ≠ PREVENTION_VERIFIED then
40:     C_repair ← AUTOMATED_VULNERABILITY_REPAIR(
            c_pre, V, RISK, L, Q, C)
41:     c_valid ← PATCH_VALIDATION(
            c_pre, C_repair, V, Q, C, Θ)


42:     if c_valid ≠ ⊥ then
43:         c* ← c_valid
44:         s ← REPAIR_VERIFIED
45:     else
46:         s ← HUMAN_REVIEW_REQUIRED
47:     end if
48: end if


49: if V = ∅ then
50:     s ← NO_VULNERABILITY_DETECTED
51: end if


52: R ← UPDATE_REPORT(R, c*, E, s)
53: return R, c*, E, s
Mathematical explanation:
Algorithm 1 represents CRAFT-Sec as a composition of modular functions:
\mathcal{A}_{CRAFT}
(c,m,\mathcal{Q},\Theta,\mathcal{C},\mathcal{G})
]
The processing pipeline can be expressed as:
[
c
\xrightarrow{\text{Preprocessing}}
\mathbf{x}(c)
\xrightarrow{\text{Analysis}}
\mathcal{E}
\xrightarrow{\text{Fusion}}
\mathcal{E}{f}
\xrightarrow{\text{Localization}}
\mathcal{L}
\xrightarrow{\text{Risk Assessment}}
\mathcal{R}{v}
]
The resulting vulnerability assessment is then used by the prevention or repair module. A candidate output is retained only after the required security and functional verification procedures.
The framework is conditionally multimodal. If internal activations are unavailable, the neural analysis component returns missing evidence, while the source-code analysis pathway remains operational. Therefore, the overall procedure does not require SAE access to function.
Computational complexity:
Let:
                                             * (n) be the number of source-code tokens.
                                             * (V_g) and (E_g) be the number of nodes and edges in the program-analysis graph.
                                             * (C_{static}) and (C_{dynamic}) denote the costs of static and dynamic analysis.
                                             * (C_{SAE}) denote the SAE processing cost.
                                             * (C_{fusion}) denote the evidence-fusion cost.
                                             * (C_{repair}) denote the total repair-generation and validation cost.
The approximate overall complexity is:
[
\begin{aligned}
C_{CRAFT} = O(&n + V_g + E_g + C_{static}\
&+ C_{dynamic} + C_{SAE}\
&+ C_{fusion} + C_{localization}\
&+ C_{repair})
\end{aligned}
]
This is a compositional complexity expression rather than a universal polynomial bound. In particular, dynamic analysis, model inference, and LLM-based repair may have costs that depend on execution environments, token limits, and generation configurations.
Role in CRAFT-Sec:
Algorithm 1 serves as the orchestration procedure. It establishes the execution order and dependencies among the remaining algorithms, manages unavailable analysis modalities, and enforces the principle that generated or repaired code must undergo independent security verification before acceptance.

6.4 Algorithm 2: Vulnerability Detection
Purpose: To identify potential vulnerabilities in LLM-generated code through complementary lexical, syntactic, semantic, structural, and security-related representations, supported by static and dynamic analysis evidence.
Input:
                                             * (c): Preprocessed source code.
                                             * (\mathbf{x}(c)): Multi-view source-code representation.
                                             * (\mathcal{E}_{static}): Static-analysis findings.
                                             * (\mathcal{E}_{dynamic}): Dynamic-analysis findings.
                                             * (\mathcal{E}_{neural}): Optional neural evidence.
                                             * (\theta_d): Trained vulnerability-detection parameters.
                                             * (\tau_d): Decision threshold.
Output:
                                             * (\mathcal{V}_{cand}): Candidate vulnerability findings.
                                             * (\mathbf{p}): Predicted vulnerability probabilities.
                                             * (\mathcal{E}_{det}): Detection evidence.
Initialization:
Initialize the candidate finding set as empty. Configure the trained detection model and initialize the evidence vector. Define a consistent mapping between predicted findings and source-code locations.
Pseudocode:
Algorithm 2: Vulnerability Detection


Input:
    Source code c
    Multi-view features X
    Static evidence E_static
    Dynamic evidence E_dynamic
    Optional neural evidence E_neural
    Detection parameters θ_d
    Threshold τ_d


Output:
    Candidate vulnerabilities V_cand
    Prediction probabilities p
    Detection evidence E_det


1:  Initialize V_cand ← ∅
2:  Initialize E_det ← ∅


3:  X_lex ← EXTRACT_LEXICAL_FEATURES(c)
4:  X_syn ← EXTRACT_SYNTACTIC_FEATURES(c)
5:  X_sem ← EXTRACT_SEMANTIC_FEATURES(c)
6:  X_str ← EXTRACT_STRUCTURAL_FEATURES(c)
7:  X_sec ← EXTRACT_SECURITY_FEATURES(c)


8:  X_all ← CONCATENATE(
        X_lex, X_syn, X_sem, X_str, X_sec)


9:  p ← DETECTION_MODEL(X_all, θ_d)


10: for each code unit u in c do
11:     p_u ← PREDICT_VULNERABILITY(u, X_all, θ_d)


12:     if p_u ≥ τ_d then
13:         v ← CREATE_CANDIDATE_FINDING(u, p_u)
14:         ADD(V_cand, v)
15:     end if
16: end for


17: for each finding e in E_static do
18:     MAP_FINDING_TO_CODE(e, c)
19:     ADD(E_det, e)
20: end for


21: for each finding e in E_dynamic do
22:     MAP_FINDING_TO_CODE(e, c)
23:     ADD(E_det, e)
24: end for


25: if E_neural is available then
26:     ADD(E_det, E_neural)
27: end if


28: for each v in V_cand do
29:     evidence_v ← COLLECT_SUPPORTING_EVIDENCE(v, E_det)
30:     UPDATE_FINDING(v, evidence_v)
31: end for


32: return V_cand, p, E_det
Mathematical explanation:
The detection model estimates the probability that a code unit contains a vulnerability:
\sigma(f_{\theta_d}(\mathbf{x}_u))
]
where:
                                             * (y_u\in{0,1}) is the vulnerability label.
                                             * (\mathbf{x}_u) is the multi-view feature representation of code unit (u).
                                             * (f_{\theta_d}) is the trained detection function.
                                             * (\sigma(\cdot)) is the sigmoid function.
The candidate prediction is:
[
\hat{y}_u=
\begin{cases}
1, & P(y_u=1\mid\mathbf{x}_u)\geq\tau_d,\
0, & \text{otherwise}.
\end{cases}
]
The five feature categories represent complementary information:
[
\mathbf{x}u=
[
\mathbf{x}{lex};
\mathbf{x}{syn};
\mathbf{x}{sem};
\mathbf{x}{str};
\mathbf{x}{sec}
]
]
Lexical features capture potentially relevant tokens and API usage; syntactic features describe grammatical and language constructs; semantic features represent program behavior; structural features encode relationships between statements and program components; and security-related features capture properties such as input validation, authorization, sanitization, and resource handling.
Static and dynamic findings supplement the learned prediction. However, a prediction above the threshold is a candidate finding, not automatically a confirmed vulnerability. Confirmation depends on evidence quality and subsequent analysis.
Computational complexity:
Let (n) be the number of tokens, (d_x) the dimensionality of the extracted feature representation, and (C_f(n,d_x)) the cost of evaluating the detection model. For a linear classifier, the inference cost is approximately:
[
O(nd_x)
]
For a general neural detector, the cost depends on its architecture and can be represented as:
[
O(C_f(n,d_x))
]
Feature extraction contributes an additional cost that depends on the parser, language, and semantic analysis tools. The final thresholding and candidate collection require (O(U)) operations, where (U) is the number of analyzed code units.
Role in CRAFT-Sec:
Algorithm 2 provides the initial vulnerability prediction stage. It combines multi-view code representations with external analysis findings to identify candidate weaknesses. Its output supplies the evidence required by localization, evidence fusion, and risk assessment.

6.5 Algorithm 3: SAE-Based Security Feature Extraction
Purpose: To extract sparse latent representations from internal LLM activations and identify candidate security-relevant features that may be associated with vulnerable or secure code-generation behavior.
Input:
                                             * (\mathbf{H}): Internal model activation matrix.
                                             * (\mathbf{W}_e,\mathbf{b}_e): SAE encoder parameters.
                                             * (\mathbf{W}_d,\mathbf{b}_d): SAE decoder parameters.
                                             * (\mathcal{D}_{label}): Optional labeled activation dataset.
                                             * (\tau_z): Feature activation threshold.
Output:
                                             * (\mathbf{Z}): Sparse latent activation matrix.
                                             * (\hat{\mathbf{H}}): Reconstructed activation matrix.
                                             * (\mathcal{F}_{sec}): Candidate security-relevant SAE features.
                                             * (\mathcal{M}_{SAE}): Feature metadata.
Initialization:
Load a trained SAE or initialize its parameters for training. Configure the selected model layer, activation extraction procedure, latent dimensionality, sparsity criterion, and feature-selection threshold.
Pseudocode:
Algorithm 3: SAE-Based Security Feature Extraction


Input:
    Activation matrix H
    Encoder parameters W_e, b_e
    Decoder parameters W_d, b_d
    Optional labeled dataset D_label
    Activation threshold τ_z


Output:
    Sparse activations Z
    Reconstructed activations H_hat
    Security-related features F_sec
    Feature metadata M_SAE


1:  Initialize F_sec ← ∅
2:  Initialize M_SAE ← ∅


3:  H_norm ← NORMALIZE_ACTIVATIONS(H)


4:  for each activation vector h_i in H_norm do
5:      z_i ← ReLU(W_e h_i + b_e)
6:      h_hat_i ← W_d z_i + b_d
7:  end for


8:  Z ← STACK(z_1, z_2, ..., z_N)
9:  H_hat ← STACK(h_hat_1, h_hat_2, ..., h_hat_N)


10: reconstruction_error ← COMPUTE_RECONSTRUCTION_ERROR(
        H_norm, H_hat)


11: sparsity_score ← COMPUTE_SPARSITY(Z)


12: if reconstruction_error exceeds configured limit then
13:     FLAG_SAE_QUALITY_WARNING()
14: end if


15: for each latent feature j in Z do
16:     a_j ← COMPUTE_FEATURE_ACTIVATION_STATISTICS(Z[:, j])


17:     if a_j satisfies FEATURE_ACTIVITY_CRITERIA then
18:         association ← ANALYZE_SECURITY_LABEL_ASSOCIATION(
                Z[:, j], D_label)


19:         if association satisfies FEATURE_SELECTION_CRITERIA then
20:             ADD(F_sec, j)
21:             ADD(M_SAE, FEATURE_METADATA(j, a_j, association))
22:         end if
23:     end if
24: end for


25: return Z, H_hat, F_sec, M_SAE
Mathematical explanation:
For an activation vector (\mathbf{h}_i\in\mathbb{R}^{d}), the SAE encoder generates a latent representation:
[
\mathbf{z}_i=
\operatorname{ReLU}
(\mathbf{W}_e\mathbf{h}_i+\mathbf{b}_e)
]
where (\mathbf{z}_i\in\mathbb{R}^{k}) and (k) is the SAE dictionary size. The decoder reconstructs the original activation:
[
\hat{\mathbf{h}}_i=
\mathbf{W}_d\mathbf{z}_i+\mathbf{b}_d
]
A conventional sparse reconstruction objective is:
\frac{1}{N}
\sum_{i=1}^{N}
\left|
\mathbf{h}_i-\hat{\mathbf{h}}_i
\right|2^2
+
\lambda
\frac{1}{N}
\sum{i=1}^{N}
|\mathbf{z}_i|_1
]
The first term encourages reconstruction fidelity, while the second encourages sparse latent representations. The regularization parameter (\lambda) controls the reconstruction–sparsity trade-off.
A latent feature is not automatically a security feature merely because it activates on vulnerable code. Its relevance must be evaluated using independent evidence, such as activation differences between labeled secure and vulnerable examples, association with specific CWE categories, and consistency across samples.
For example, a feature-level activation difference can be estimated as:
\mathbb{E}[z_j\mid y=0]
]
where (y=1) represents vulnerable samples and (y=0) represents secure samples. A statistically supported association may motivate further investigation, but it does not independently establish that the feature causes vulnerability-related behavior.
Computational complexity:
Let:
                                             * (N) be the number of activation vectors.
                                             * (d) be the activation dimension.
                                             * (k) be the SAE latent dimension.
Dense encoding and decoding require approximately:
[
O(Ndk)
]
operations each, giving an overall dense SAE inference complexity of:
[
O(Ndk)
]
up to constant factors. If sparse computation is implemented using only (s) active latent units per activation, the practical cost may be reduced, although the initial dense encoder computation may still be required. Feature statistics and selection generally require (O(Nk)) operations, excluding statistical tests and repeated validation.
Role in CRAFT-Sec:
Algorithm 3 provides the neural interpretability component of CRAFT-Sec. It transforms high-dimensional model activations into sparse latent representations that can be examined for security-related patterns. This algorithm is applicable only when the target LLM exposes the required internal activations or when an appropriate activation dataset is otherwise available.

6.6 Algorithm 4: Feature Interaction Analysis
Purpose: To identify relationships among security-relevant SAE features and investigate whether combinations of latent features provide additional explanatory information beyond their individual activation patterns.
Input:
                                             * (\mathbf{Z}): SAE latent activation matrix.
                                             * (\mathcal{F}_{sec}): Selected security-relevant features.
                                             * (g(\cdot)): Model output or vulnerability-related response function.
                                             * (\tau_{corr}): Association threshold.
                                             * (\tau_{int}): Interaction-effect threshold.
                                             * (\mathcal{P}): Selected feature-pair intervention configuration.
Output:
                                             * (\mathcal{I}_{assoc}): Associated feature pairs.
                                             * (\mathcal{I}_{interact}): Candidate interaction effects.
                                             * (\mathcal{E}_{int}): Interaction evidence.
Initialization:
Initialize the association and interaction sets. Identify eligible feature pairs from the selected security-relevant feature set. Define the intervention procedure and baseline activation configuration.
Pseudocode:
Algorithm 4: Feature Interaction Analysis


Input:
    SAE activation matrix Z
    Security feature set F_sec
    Output function g
    Association threshold τ_corr
    Interaction threshold τ_int
    Intervention configuration P


Output:
    Associated feature pairs I_assoc
    Interaction effects I_interact
    Interaction evidence E_int


1:  Initialize I_assoc ← ∅
2:  Initialize I_interact ← ∅
3:  Initialize E_int ← ∅


4:  F ← SELECT_ELIGIBLE_FEATURES(F_sec)


5:  for each unordered pair (i, j) in F do
6:      ρ_ij ← CORRELATION(Z[:, i], Z[:, j])


7:      if |ρ_ij| ≥ τ_corr then
8:          ADD(I_assoc, (i, j, ρ_ij))
9:      end if
10: end for


11: Pairs ← SELECT_INTERVENTION_PAIRS(I_assoc, P)


12: for each pair (i, j) in Pairs do
13:     y_00 ← EVALUATE_OUTPUT(g, i=0, j=0)
14:     y_10 ← EVALUATE_OUTPUT(g, i=1, j=0)
15:     y_01 ← EVALUATE_OUTPUT(g, i=0, j=1)
16:     y_11 ← EVALUATE_OUTPUT(g, i=1, j=1)


17:     interaction_ij ← y_11 - y_10 - y_01 + y_00


18:     if |interaction_ij| ≥ τ_int then
19:         ADD(I_interact, (i, j, interaction_ij))
20:     end if


21:     control ← RUN_INTERVENTION_CONTROLS(i, j)
22:     ADD(E_int, interaction_ij, control)
23: end for


24: return I_assoc, I_interact, E_int
Mathematical explanation:
The initial screening step estimates the association between two latent features using Pearson correlation:
[
\rho_{ij}=
\frac{
\operatorname{Cov}(z_i,z_j)
}{
\sigma_i\sigma_j
}
]
where (\sigma_i) and (\sigma_j) are the standard deviations of the corresponding feature activations.
Correlation identifies co-activation patterns but does not demonstrate a functional interaction. To investigate interaction effects, CRAFT-Sec uses a second-order contrast:
g(1,1)-g(1,0)-g(0,1)+g(0,0)
]
Here, (g(a,b)) represents the model output under specified interventions on features (i) and (j). A non-zero contrast indicates that the joint intervention changes the output beyond the additive combination of the two individual interventions under the chosen intervention definition.
For continuous activations, the corresponding local interaction can be expressed as:
\frac{\partial^2 g}
{\partial z_i\partial z_j}
]
This derivative measures local non-additivity when the output function is sufficiently differentiable.
Intervention-based estimates require additional controls. The intervention values must be defined consistently, and the resulting activation patterns should be checked for plausibility. Ablation, activation replacement, or patching may introduce distribution shifts. Therefore, controls should compare intervention results with unmodified activations, random or unrelated feature interventions, and alternative intervention magnitudes where appropriate.
Computational complexity:
Let (k_s=|\mathcal{F}_{sec}|) be the number of selected features and (N) the number of activation samples.
Pairwise correlation screening requires:
[
O(Nk_s^2)
]
for a direct implementation.
If (P) feature pairs are selected for intervention and each intervention requires one model evaluation of cost (C_g), the intervention cost is approximately:
[
O(4PC_g)
]
for the four configurations in the second-order contrast, excluding additional control evaluations. The total complexity is therefore dominated by pairwise screening and intervention-based model evaluation.
Role in CRAFT-Sec:
Algorithm 4 investigates whether security-related latent features operate independently or exhibit non-additive relationships. It provides evidence for feature interaction analysis and supports the interpretation of complex model behavior. Its output must distinguish statistical co-activation from interaction effects established through controlled interventions.

6.7 Algorithm 5: Explainable Vulnerability Localization
Purpose: To identify the source-code statements, expressions, functions, or dependency paths most relevant to a detected vulnerability and produce an evidence-supported explanation.
Input:
                                             * (c): Source code.
                                             * (\mathcal{E}): Fused vulnerability evidence.
                                             * (G_{AST}): Abstract Syntax Tree.
                                             * (G_{CFG}): Control Flow Graph.
                                             * (G_{DFG}): Data Flow Graph.
                                             * (\mathbf{a}): Available attribution scores.
                                             * (\tau_l): Localization threshold.
Output:
                                             * (\mathcal{L}): Ranked vulnerable code locations.
                                             * (\mathcal{P}_{dep}): Relevant dependency paths.
                                             * (\mathcal{X}): Explanatory evidence.
Initialization:
Initialize the localization candidate set and explanatory evidence. Map all analysis findings to their source-code positions. Establish a common location representation, such as file, function, statement, and token range.
Pseudocode:
Algorithm 5: Explainable Vulnerability Localization


Input:
    Source code c
    Fused evidence E
    AST G_AST
    CFG G_CFG
    DFG G_DFG
    Attribution scores a
    Localization threshold τ_l


Output:
    Ranked locations L
    Dependency paths P_dep
    Explanatory evidence X


1:  Initialize L ← ∅
2:  Initialize P_dep ← ∅
3:  Initialize X ← ∅


4:  Candidates ← EXTRACT_RELEVANT_CODE_UNITS(c, E)


5:  for each candidate unit u in Candidates do
6:      s_neural ← GET_ATTRIBUTION_SCORE(u, a)
7:      s_ast ← COMPUTE_AST_RELEVANCE(u, G_AST)
8:      s_cfg ← COMPUTE_CFG_RELEVANCE(u, G_CFG)
9:      s_dfg ← COMPUTE_DFG_RELEVANCE(u, G_DFG)
10:     s_sec ← GET_SECURITY_EVIDENCE_SCORE(u, E)


11:     s_loc ← LOCALIZATION_SCORING_FUNCTION(
            s_neural, s_ast, s_cfg, s_dfg, s_sec)


12:     if s_loc ≥ τ_l then
13:         ADD(L, (u, s_loc))
14:     end if
15: end for


16: for each localized unit u in L do
17:     paths ← TRACE_RELEVANT_DEPENDENCIES(
            u, G_CFG, G_DFG)


18:     ADD(P_dep, paths)
19:     explanation ← GENERATE_EVIDENCE_EXPLANATION(
            u, paths, E, G_AST)
20:     ADD(X, explanation)
21: end for


22: SORT_DESCENDING(L, localization_score)


23: return L, P_dep, X
Mathematical explanation:
Localization combines multiple sources of evidence to estimate the relevance of a code unit (u) to a candidate vulnerability (v). A general scoring formulation is:
\sum_{r=1}^{M}
\alpha_r e_r(u,v)
]
where:
                                             * (M) is the number of available localization evidence sources.
                                             * (e_r(u,v)) is the normalized evidence score from source (r).
                                             * (\alpha_r) is the corresponding weight.
The weights should be calibrated on validation data and should account for unavailable modalities. A normalized version is:
\frac{
\sum_{r=1}^{M}m_r\alpha_r e_r(u,v)
}{
\sum_{r=1}^{M}m_r\alpha_r
}
]
where (m_r\in{0,1}) indicates whether evidence source (r) is available. If the denominator is zero, localization should return an insufficient-evidence status rather than an arbitrary score.
For example, a potential SQL injection may be localized by tracing an externally controlled input through data dependencies to a database query construction statement. The relevant source, transformation, and sink statements provide a more informative explanation than a vulnerability label alone.
The localization score is an evidence-ranking mechanism, not necessarily a calibrated probability. The final explanation should preserve the provenance of each supporting signal.
Computational complexity:
Let (V_g) and (E_g) denote the number of graph nodes and edges. Scoring (U) candidate code units using a fixed number of evidence sources requires (O(UM)) operations. Standard graph traversal over the CFG or DFG requires:
[
O(V_g+E_g)
]
per traversal in the worst case. If dependency tracing is repeated for multiple locations, the total cost depends on the number of candidates and traversed subgraphs.
Attribution computation may dominate localization cost. For integrated gradients with (q) interpolation steps, its approximate cost is:
[
O(qC_f)
]
where (C_f) is the cost of one forward and backward model evaluation. For discrete source-code inputs, attribution should be computed through a suitable embedding-space representation or a validated perturbation-based alternative.
Role in CRAFT-Sec:
Algorithm 5 transforms vulnerability evidence into actionable source-code explanations. It identifies relevant statements and dependency paths, supporting human review, security reporting, and repair-context construction.

6.8 Algorithm 6: Multi-Feature Evidence Fusion
Purpose: To integrate neural, lexical, syntactic, semantic, structural, static, and dynamic evidence into a unified vulnerability assessment while accounting for missing modalities and differences in evidence reliability.
Input:
                                             * (\mathcal{E}_{lex}): Lexical evidence.
                                             * (\mathcal{E}_{syn}): Syntactic evidence.
                                             * (\mathcal{E}_{sem}): Semantic evidence.
                                             * (\mathcal{E}_{str}): Structural evidence.
                                             * (\mathcal{E}_{sec}): Security-related evidence.
                                             * (\mathcal{E}_{neural}): Optional SAE-derived evidence.
                                             * (\mathcal{E}_{static}): Static-analysis evidence.
                                             * (\mathcal{E}_{dynamic}): Dynamic-analysis evidence.
                                             * (\boldsymbol{\alpha}): Fusion weights.
                                             * (F_{\phi}): Trained fusion function.
Output:
                                             * (\mathbf{e}_{f}): Fused evidence representation.
                                             * (P_f(v)): Fused vulnerability probability or calibrated score.
                                             * (\mathbf{m}): Modality-availability vector.
                                             * (\mathcal{E}_{provenance}): Evidence provenance information.
Initialization:
Initialize the evidence vector, modality mask, and provenance records. Normalize available modality representations using transformations estimated from training data. Preserve missing modalities explicitly.
Pseudocode:
Algorithm 6: Multi-Feature Evidence Fusion


Input:
    Lexical evidence E_lex
    Syntactic evidence E_syn
    Semantic evidence E_sem
    Structural evidence E_str
    Security evidence E_sec
    Optional neural evidence E_neural
    Static evidence E_static
    Dynamic evidence E_dynamic
    Fusion weights α
    Fusion function F_phi


Output:
    Fused representation e_f
    Fused vulnerability score P_f
    Availability mask m
    Evidence provenance E_provenance


1:  Initialize evidence vector e ← ∅
2:  Initialize availability mask m ← ∅
3:  Initialize E_provenance ← ∅


4:  Modalities ← {
        E_lex, E_syn, E_sem, E_str,
        E_sec, E_neural, E_static, E_dynamic
    }


5:  for each modality E_r in Modalities do
6:      if E_r is available then
7:          e_r ← NORMALIZE_EVIDENCE(E_r)
8:          m_r ← 1
9:      else
10:         e_r ← MISSING_VALUE
11:         m_r ← 0
12:     end if


13:     APPEND(e, e_r)
14:     APPEND(m, m_r)
15:     RECORD_PROVENANCE(E_provenance, E_r)
16: end for


17: if no modality is available then
18:     return INSUFFICIENT_EVIDENCE
19: end if


20: e_f ← F_phi(e, m, α)


21: P_f ← CALIBRATED_VULNERABILITY_SCORE(e_f)


22: return e_f, P_f, m, E_provenance
Mathematical explanation:
Let the available evidence modalities be represented by:
[
\mathbf{e}{lex};
\mathbf{e}{syn};
\mathbf{e}{sem};
\mathbf{e}{str};
\mathbf{e}{sec};
\mathbf{e}{neural};
\mathbf{e}{static};
\mathbf{e}{dynamic}
]
]
A modality-availability vector is defined as:
[
\mathbf{m}=[m_1,m_2,\ldots,m_M],
\qquad m_r\in{0,1}
]
where (m_r=1) indicates that modality (r) is available.
A simple weighted evidence-fusion baseline is:
[
S_f=
\frac{
\sum_{r=1}^{M}m_r\alpha_r s_r
}{
\sum_{r=1}^{M}m_r\alpha_r
}
]
where (s_r) is a normalized evidence score and (\alpha_r) is its weight. The denominator must be positive; otherwise, the system returns insufficient evidence.
For the proposed framework, a learned fusion function can be expressed as:
[
\mathbf{e}f=F{\phi}(\mathbf{e},\mathbf{m})
]
and the final score as:
[
P_f(v)=\sigma(f_{\phi}(\mathbf{e}_f))
]
If the output is interpreted as a probability, the fusion model must be trained and calibrated using appropriate validation data. Otherwise, the output should be reported as a risk or evidence score rather than a probability.
The fusion function should preserve evidence provenance so that a high score can be traced to its contributing sources. This is important because two samples may receive similar scores for different reasons, such as strong static-analysis evidence in one case and strong neural evidence in another.
Computational complexity:
Let (M) be the number of modalities and (d_e) the total dimensionality of the normalized evidence vector. Constructing the evidence vector and availability mask requires approximately:
[
O(d_e+M)
]
A linear fusion model requires (O(d_e)) inference operations. For a neural fusion model, complexity depends on the architecture and is denoted by (O(C_{F_{\phi}})).
Role in CRAFT-Sec:
Algorithm 6 is the central evidence-integration mechanism. It combines heterogeneous security signals without requiring every analysis modality to be present. It supports more comprehensive assessment while maintaining traceability and avoiding the incorrect assumption that missing neural evidence implies secure code.

6.9 Algorithm 7: Security-Aware Vulnerability Prevention
Purpose: To reduce the introduction of security weaknesses during code generation by incorporating vulnerability-specific constraints, secure coding requirements, and iterative security feedback into the LLM generation process.
Input:
                                             * (m): Target LLM.
                                             * (p): Original generation prompt or task specification.
                                             * (\mathcal{V}_{known}): Known vulnerability patterns or security constraints.
                                             * (\mathcal{S}_{req}): Functional and security requirements.
                                             * (\mathcal{C}_{sec}): Security policy and coding constraints.
                                             * (B): Maximum number of generation attempts.
                                             * (\mathcal{Q}): Functional test suite.
                                             * (\tau_{sec}): Security acceptance criteria.
Output:
                                             * (c_{safe}): Security-verified generated code, if available.
                                             * (\mathcal{H}): Generation and validation history.
                                             * (s_{prev}): Prevention status.
Initialization:
Initialize the generation history and candidate code. Construct a security-aware prompt by incorporating relevant security requirements, vulnerability-specific constraints, and expected functional behavior. Set the attempt counter to zero.
Pseudocode:
Algorithm 7: Security-Aware Vulnerability Prevention


Input:
    Target LLM m
    Original prompt p
    Known vulnerability patterns V_known
    Requirements S_req
    Security constraints C_sec
    Maximum attempts B
    Functional test suite Q
    Security criteria τ_sec


Output:
    Verified code c_safe
    Generation history H
    Prevention status s_prev


1:  Initialize H ← ∅
2:  Initialize c_safe ← ⊥
3:  Initialize attempt ← 0
4:  Initialize s_prev ← PREVENTION_NOT_VERIFIED


5:  p_sec ← CONSTRUCT_SECURITY_AWARE_PROMPT(
        p, V_known, S_req, C_sec)


6:  while attempt < B do
7:      attempt ← attempt + 1


8:      c_candidate ← GENERATE_CODE(m, p_sec)


9:      if c_candidate = ⊥ then
10:         RECORD_FAILURE(H, attempt, GENERATION_FAILURE)
11:         continue
12:     end if


13:     E_static ← STATIC_SECURITY_ANALYSIS(c_candidate)
14:     E_dynamic ← DYNAMIC_SECURITY_ANALYSIS(
            c_candidate, Q)


15:     E_detect ← VULNERABILITY_DETECTION(
            c_candidate, E_static, E_dynamic)


16:     if SECURITY_CRITERIA_SATISFIED(
            c_candidate, E_detect, τ_sec)
        and FUNCTIONAL_TESTS_PASS(c_candidate, Q) then


17:         c_safe ← c_candidate
18:         s_prev ← PREVENTION_VERIFIED
19:         RECORD_SUCCESS(H, attempt, E_detect)
20:         break
21:     end if


22:     feedback ← GENERATE_SECURITY_FEEDBACK(
            E_detect, E_static, E_dynamic)


23:     p_sec ← UPDATE_PROMPT_WITH_FEEDBACK(
            p_sec, feedback, S_req, C_sec)


24:     RECORD_ATTEMPT(H, attempt, c_candidate, feedback)
25: end while


26: if c_safe = ⊥ then
27:     s_prev ← PREVENTION_NOT_VERIFIED
28: end if


29: return c_safe, H, s_prev
Mathematical explanation:
Security-aware prevention modifies the generation process by conditioning the target model on functional and security requirements:
[
c_t\sim P_m(c\mid p_t,\mathcal{S}{req},\mathcal{C}{sec})
]
where:
                                             * (c_t) is the candidate generated at attempt (t).
                                             * (p_t) is the current prompt.
                                             * (\mathcal{S}_{req}) represents functional requirements.
                                             * (\mathcal{C}_{sec}) represents security constraints.
                                             * (P_m) is the conditional generation distribution of model (m).
After generating a candidate, the framework evaluates it using a combined acceptance condition:
[
A(c_t)=
A_{sec}(c_t)
\land
A_{func}(c_t)
]
where (A_{sec}) indicates whether the candidate satisfies the defined security criteria and (A_{func}) indicates whether the functional tests pass.
The iterative process updates the generation prompt using observed security feedback:
[
p_{t+1}=
\Psi(p_t,\mathcal{E}t,\mathcal{S}{req},
\mathcal{C}_{sec})
]
where (\Psi) is the prompt-update function and (\mathcal{E}_t) contains the security findings from attempt (t).
The procedure is bounded by (B), preventing unbounded generation and feedback loops. If no candidate satisfies the acceptance criteria, the algorithm returns a prevention-not-verified status.
Passing the configured checks does not prove that the generated code is free of all vulnerabilities. The result indicates that the candidate satisfied the specified verification criteria under the available analysis configuration.
Computational complexity:
Let:
                                             * (B) be the maximum number of attempts.
                                             * (C_{gen}) be the cost of one LLM generation.
                                             * (C_{sec}) be the cost of security analysis.
                                             * (C_{test}) be the cost of functional testing.
                                             * (C_{feedback}) be the cost of generating and applying security feedback.
The worst-case computational cost is:
[
O\left(
B(C_{gen}+C_{sec}+C_{test}+C_{feedback})
\right)
]
The actual cost depends on generation length, analysis tools, test execution, and the number of attempts before acceptance or termination.
Role in CRAFT-Sec:
Algorithm 7 introduces a proactive security mechanism. Rather than analyzing vulnerabilities only after code generation, it incorporates security constraints into the generation process and uses analysis feedback to refine subsequent attempts. This makes prevention a distinct process from post-generation vulnerability repair.

6.10 Algorithm 8: Automated Vulnerability Repair
Purpose: To generate candidate patches for identified vulnerabilities using vulnerability localization, security evidence, program dependencies, and functional requirements.
Input:
                                             * (c): Original vulnerable source code.
                                             * (\mathcal{V}): Identified vulnerabilities.
                                             * (\mathcal{L}): Ranked vulnerability locations.
                                             * (\mathcal{E}): Consolidated vulnerability evidence.
                                             * (m_r): Repair-capable LLM or repair model.
                                             * (\mathcal{Q}): Functional and regression test suite.
                                             * (N): Maximum number of repair candidates.
                                             * (\mathcal{C}_{repair}): Repair constraints.
Output:
                                             * (\mathcal{C}_{cand}): Set of generated repair candidates.
                                             * (\mathcal{D}_{patch}): Patch differences and associated metadata.
                                             * (s_{repair}): Repair-generation status.
Initialization:
Initialize the candidate patch set and patch metadata. Rank vulnerabilities by their assessed priority. Construct a repair context containing the vulnerable code region, relevant dependency paths, vulnerability classification, and required functional behavior.
Pseudocode:
Algorithm 8: Automated Vulnerability Repair


Input:
    Original code c
    Vulnerability set V
    Ranked locations L
    Evidence E
    Repair model m_r
    Test suite Q
    Maximum candidates N
    Repair constraints C_repair


Output:
    Repair candidates C_cand
    Patch metadata D_patch
    Repair status s_repair


1:  Initialize C_cand ← ∅
2:  Initialize D_patch ← ∅
3:  Initialize s_repair ← NO_CANDIDATE_GENERATED


4:  V_ranked ← RANK_VULNERABILITIES(V)


5:  for each vulnerability v in V_ranked do
6:      location ← GET_LOCALIZATION(v, L)
7:      evidence_v ← GET_EVIDENCE(v, E)


8:      context ← BUILD_REPAIR_CONTEXT(
            c, v, location, evidence_v, Q, C_repair)


9:      attempt ← 0


10:     while attempt < N do
11:         attempt ← attempt + 1


12:         patch ← GENERATE_REPAIR(m_r, context)


13:         if patch = ⊥ then
14:             continue
15:         end if


16:         c_candidate ← APPLY_PATCH(c, patch)


17:         if PATCH_APPLICATION_FAILED(c_candidate) then
18:             continue
19:         end if


20:         if SYNTAX_CHECK(c_candidate) = PASS then
21:             ADD(C_cand, c_candidate)
22:             metadata ← RECORD_PATCH_METADATA(
                    v, location, patch, attempt)
23:             ADD(D_patch, metadata)
24:         end if
25:     end while
26: end for


27: if C_cand ≠ ∅ then
28:     s_repair ← CANDIDATES_GENERATED
29: end if


30: return C_cand, D_patch, s_repair
Mathematical explanation:
Automated repair is formulated as a constrained candidate-generation problem:
G(m_r,c,\mathcal{V},\mathcal{L},
\mathcal{E},\mathcal{Q},\mathcal{C}_{repair})
]
where (G) is the repair-generation procedure.
A candidate patch (p) produces modified code:
[
c'=Apply(c,p)
]
The repair objective can be expressed as:
[
p^*=
\arg\min_{p\in\mathcal{P}}
\mathcal{L}_{repair}(p)
]
with:
[
\begin{aligned}
\mathcal{L}{repair}(p)
={}&
\lambda_s L{security}(c')
+\lambda_f L_{function}(c,c')\
&+\lambda_r L_{regression}(c,c')
+\lambda_d L_{diff}(c,c')
\end{aligned}
]
where:
                                             * (L_{security}) measures the remaining security weaknesses.
                                             * (L_{function}) measures deviation from the intended functional behavior.
                                             * (L_{regression}) measures failures in existing behavior.
                                             * (L_{diff}) penalizes unnecessary code modifications.
                                             * (\lambda_s,\lambda_f,\lambda_r,\lambda_d) are configurable objective weights.
In practice, an LLM may generate candidate patches rather than directly solving this optimization problem. The equation therefore describes the desired repair objective, not a guarantee that the generator finds a global optimum.
The repair process should preserve the original code and maintain a reproducible patch representation. Candidate generation and candidate acceptance remain separate stages: Algorithm 8 generates syntactically applicable patches, whereas Algorithm 9 determines whether a patch satisfies the verification criteria.
Computational complexity:
Let:
                                             * (K=|\mathcal{V}|) be the number of vulnerabilities.
                                             * (N) be the maximum repair attempts per vulnerability.
                                             * (C_{gen}) be the cost of one repair-model generation.
                                             * (C_{apply}) be the cost of applying and checking a patch.
                                             * (C_{syntax}) be the syntax-validation cost.
The approximate worst-case cost is:
[
O\left(
KN(C_{gen}+C_{apply}+C_{syntax})
\right)
]
This expression assumes that each vulnerability is processed independently. If vulnerabilities interact or patches are generated jointly, additional coordination and conflict-resolution costs may arise.
Role in CRAFT-Sec:
Algorithm 8 provides the corrective component of CRAFT-Sec. It uses explainable vulnerability locations and evidence to generate targeted patches, with the objective of mitigating identified weaknesses while minimizing unnecessary changes. It does not independently certify the correctness or security of any generated patch.

6.11 Algorithm 9: Patch Validation and Security Verification
Purpose: To independently verify candidate patches by assessing syntactic validity, functional correctness, regression behavior, removal of targeted vulnerabilities, and the introduction of new security weaknesses.
Input:
                                             * (c): Original source code.
                                             * (\mathcal{C}_{cand}): Candidate repaired code.
                                             * (\mathcal{V}_{target}): Original targeted vulnerabilities.
                                             * (\mathcal{Q}): Functional and regression test suite.
                                             * (\mathcal{C}_{analysis}): Security-analysis configuration.
                                             * (\tau_{test}): Minimum required test criteria.
                                             * (\tau_{sec}): Security acceptance criteria.
Output:
                                             * (c_{verified}): Accepted repaired code, if any.
                                             * (\mathcal{V}_{remaining}): Remaining identified vulnerabilities.
                                             * (\mathcal{V}_{new}): Newly identified vulnerabilities.
                                             * (s_{validation}): Validation result and rejection reason, if applicable.
Initialization:
Initialize the verified-code output as unavailable. Preserve the original source code and establish a record of validation results for each candidate. Configure the syntax, functional, regression, and security verification procedures.
Pseudocode:
Algorithm 9: Patch Validation and Security Verification


Input:
    Original code c
    Candidate patches C_cand
    Target vulnerabilities V_target
    Test suite Q
    Analysis configuration C_analysis
    Test criteria τ_test
    Security criteria τ_sec


Output:
    Verified code c_verified
    Remaining vulnerabilities V_remaining
    New vulnerabilities V_new
    Validation status s_validation


1:  Initialize c_verified ← ⊥
2:  Initialize V_remaining ← ∅
3:  Initialize V_new ← ∅
4:  Initialize s_validation ← NO_PATCH_ACCEPTED


5:  for each candidate c' in C_cand do


6:      if SYNTAX_CHECK(c') = FAIL then
7:          RECORD_REJECTION(c', SYNTAX_FAILURE)
8:          continue
9:      end if


10:     if BUILD_OR_TYPE_CHECK(c') = FAIL then
11:         RECORD_REJECTION(c', BUILD_FAILURE)
12:         continue
13:     end if


14:     test_result ← EXECUTE_TEST_SUITE(c', Q)


15:     if not TEST_CRITERIA_SATISFIED(
                test_result, τ_test) then
16:         RECORD_REJECTION(c', FUNCTIONAL_OR_REGRESSION_FAILURE)
17:         continue
18:     end if


19:     E_before ← SECURITY_REANALYSIS(c, C_analysis)
20:     E_after ← SECURITY_REANALYSIS(c', C_analysis)


21:     V_before ← EXTRACT_FINDINGS(E_before)
22:     V_after ← EXTRACT_FINDINGS(E_after)


23:     V_remaining ← MATCH_FINDINGS(
            V_target, V_after)


24:     V_new ← IDENTIFY_NEW_FINDINGS(
            V_before, V_after)


25:     if TARGET_VULNERABILITIES_MITIGATED(
                V_target, V_remaining)
        and NO_UNACCEPTABLE_NEW_FINDINGS(V_new, τ_sec)
        and SECURITY_CRITERIA_SATISFIED(
                c', E_after, τ_sec) then


26:         c_verified ← c'
27:         s_validation ← PATCH_ACCEPTED
28:         RECORD_ACCEPTANCE(
                c', test_result, V_remaining, V_new)
29:         break


30:     else
31:         RECORD_REJECTION(
                c', SECURITY_VERIFICATION_FAILURE)
32:     end if


33: end for


34: if c_verified = ⊥ then
35:     s_validation ← HUMAN_REVIEW_REQUIRED
36: end if


37: return c_verified, V_remaining, V_new, s_validation
Mathematical explanation:
Patch validation is formulated as a conjunction of independent acceptance conditions:
[
A(c')=
A_{syntax}(c')
\land
A_{func}(c')
\land
A_{reg}(c')
\land
A_{target}(c')
\land
A_{new}(c')
]
where:
                                             * (A_{syntax}) indicates syntactic validity.
                                             * (A_{func}) indicates satisfaction of functional requirements.
                                             * (A_{reg}) indicates that regression criteria are satisfied.
                                             * (A_{target}) indicates that the targeted vulnerability has been mitigated.
                                             * (A_{new}) indicates that no unacceptable new security findings have been identified.
Functional correctness can be estimated through the test-pass ratio:
[
P_{test}(c')=
\frac{
\sum_{i=1}^{T}\mathbb{1}[q_i(c')=\text{pass}]
}{
T
}
]
where (T) is the number of test cases and (q_i) is the result of test (i). A minimum test criterion may be expressed as:
[
P_{test}(c')\geq\tau_{test}
]
However, a high test-pass ratio alone does not establish security correctness. The patch must also undergo security re-analysis.
Let (\mathcal{V}{before}) and (\mathcal{V}{after}) denote the findings identified before and after repair, respectively. The remaining targeted vulnerabilities are:
Match(\mathcal{V}{target},\mathcal{V}{after})
]
Potential new findings are:
\mathcal{V}{after}
\setminus
Match(\mathcal{V}{after},\mathcal{V}_{before})
]
The matching operation is important because source locations may change after patching. Finding comparison should therefore use appropriate identifiers and contextual attributes, such as CWE classification, affected operation, data-flow path, and vulnerability semantics, rather than relying exclusively on line numbers.
The final acceptance condition can be written as:
[
\begin{aligned}
Accept(c')={}&
SyntaxValid(c')
\land FunctionalValid(c')\
&\land RegressionValid(c')
\land TargetMitigated(c')\
&\land NoUnacceptableNewFindings(c')
\end{aligned}
]
This condition represents operational acceptance under the configured verification procedures. It does not constitute a formal proof that the patched program is free from all vulnerabilities. Such a claim would require stronger guarantees, potentially including formal verification or exhaustive analysis under explicitly defined assumptions.
Computational complexity:
Let:
                                             * (N) be the number of candidate patches.
                                             * (T) be the number of test cases.
                                             * (C_{test}) be the average execution cost per test.
                                             * (C_{sec}) be the cost of one security-analysis execution.
                                             * (C_{match}) be the cost of matching vulnerability findings.
For each candidate, the approximate validation cost is:
[
O\left(
TC_{test}+2C_{sec}+C_{match}
\right)
]
The factor of two represents security analysis of the original and patched versions. Across all (N) candidates, the worst-case cost is:
[
O\left(
N(TC_{test}+2C_{sec}+C_{match})
\right)
]
The actual cost may be reduced by caching the original-code analysis, provided that the analysis configuration and source version remain unchanged.
Role in CRAFT-Sec:
Algorithm 9 is the final quality-control mechanism. It prevents unverified patches from being treated as successful repairs and ensures that functional testing and security re-analysis are both considered. If no candidate satisfies the configured criteria, the algorithm returns a human-review-required status instead of silently accepting a potentially unsafe patch.

6.13 Computational Considerations
The computational cost of CRAFT-Sec depends on the target model, source-code size, selected analysis tools, number of candidate vulnerabilities, and number of repair attempts. No single complexity expression fully characterizes every implementation because several components invoke external tools or model inference procedures.
For a high-level estimate, let:
                                             * (n) denote the source-code token count.
                                             * (d) denote the hidden-state dimension.
                                             * (k) denote the SAE latent dimension.
                                             * (V_g) and (E_g) denote the number of graph nodes and edges.
                                             * (P) denote the number of selected feature pairs.

Dynamic analysis and LLM-based generation or repair are particularly dependent on execution conditions. Their costs should therefore be measured empirically during implementation rather than assigned unsupported asymptotic bounds.
6.14 Algorithmic Reliability and Scientific Considerations
The proposed algorithms incorporate several safeguards to support scientific validity and reproducibility.
First, association is distinguished from causation. SAE activation differences and feature correlations identify candidate explanatory patterns. Causal interpretations require controlled interventions, appropriate controls, and assessment of distribution shifts caused by activation manipulation.
Second, missing evidence is explicitly represented. A black-box model may not expose internal activations. In this case, the SAE-related algorithms are skipped, and the evidence-fusion procedure operates using the available source-code and program-analysis modalities.
Third, candidate predictions are distinguished from confirmed vulnerabilities. A model prediction indicates a potential weakness. Static analysis, dynamic testing, dependency tracing, and other independent verification procedures provide additional evidence, but the strength of confirmation depends on the methods and assumptions used.
Fourth, vulnerability localization is treated as an evidence-ranking problem. A high localization score identifies a code region that deserves investigation; it does not automatically establish that every statement in that region is vulnerable.
Fifth, repair acceptance requires independent verification. Compilation and functional tests are necessary checks in many settings, but they are not sufficient to establish security. The patched code must undergo security re-analysis to identify unresolved and potentially introduced weaknesses.
Sixth, experimental reproducibility must be maintained. Implementations should record model versions, SAE checkpoints, selected activation layers, random seeds, thresholds, fusion weights, tool versions, generation parameters, test-suite versions, and patch-validation outcomes. These records are necessary for comparing experimental runs and reproducing reported findings.
6.15 Summary
This section formalizes the proposed CRAFT-Sec framework through nine algorithms covering the complete lifecycle of security analysis and mitigation for LLM-generated code. Algorithm 1 coordinates the overall workflow. Algorithms 2–6 establish the detection, interpretability, localization, and evidence-fusion procedures. Algorithm 7 addresses proactive vulnerability prevention during code generation. Algorithms 8 and 9 provide candidate repair generation and independent patch verification.
The algorithms collectively integrate neural representations, SAE-based latent feature analysis, source-code structures, static and dynamic program analysis, evidence fusion, and security-aware repair. Their modular design supports both white-box and black-box LLM settings, while explicit evidence handling and verification conditions help prevent unsupported claims about vulnerability detection, causal interpretation, and repair correctness.
The proposed pseudocode provides an implementation-oriented foundation for the subsequent experimental evaluation. Actual effectiveness, computational efficiency, interpretability, and generalizability must be established through controlled experiments using appropriate datasets, baselines, statistical tests, and reproducible evaluation procedures.


VII. EXPERIMENTAL SETUP
7.1 Experimental Objectives
The experimental design of CRAFT-Sec is intended to evaluate its effectiveness as an integrated framework for vulnerability detection, explainability, security-aware prevention, and automated vulnerability repair in Large Language Model (LLM)-generated source code. The evaluation will investigate both the individual components and the overall framework to determine whether combining neural representations, program analysis, and explainable evidence provides measurable benefits over conventional and learning-based security approaches.
The experiments are organized around the following objectives.
EO1: Multi-feature vulnerability detection. Evaluate whether combining lexical, syntactic, semantic, structural, and security-related representations improves vulnerability detection compared with individual feature categories and established learning-based methods.
EO2: SAE-based security feature extraction. Investigate whether Sparse Autoencoders (SAEs) can extract sparse and reproducible latent representations associated with security-relevant behaviors in accessible LLMs.
EO3: Feature interaction analysis. Examine whether combinations of latent features provide additional explanatory information beyond individual feature activations. Controlled interventions will be used to investigate interaction effects rather than interpreting co-activation as evidence of causality.
EO4: Explainable vulnerability localization. Evaluate whether combining SAE-based attribution with Abstract Syntax Tree (AST), Control Flow Graph (CFG), Data Flow Graph (DFG), and taint-analysis evidence improves the identification of vulnerable source-code locations.
EO5: Multi-feature evidence fusion. Determine whether integrating neural, static, and dynamic analysis evidence improves detection reliability and risk assessment compared with individual evidence sources.
EO6: Security-aware vulnerability prevention. Investigate whether incorporating security constraints into code-generation prompts and generation procedures reduces the occurrence of vulnerabilities while preserving functional requirements.
EO7: Automated vulnerability repair. Evaluate whether CRAFT-Sec can generate patches that address identified vulnerabilities while preserving program functionality and avoiding the introduction of additional security weaknesses.
EO8: Generalization and robustness. Assess the framework across multiple datasets, programming languages, vulnerability categories, model families, and evaluation configurations.
The experimental evaluation will distinguish between the following outcomes:
                                             1. Vulnerability detection performance.
                                             2. Vulnerability localization accuracy.
                                             3. Latent feature reconstruction and interpretability.
                                             4. Feature interaction and intervention effects.
                                             5. Evidence-fusion effectiveness.
                                             6. Security-aware generation effectiveness.
                                             7. Patch correctness and security preservation.
                                             8. Computational efficiency and resource requirements.
The primary evaluation will use independently held-out test data. Additional experiments will examine cross-dataset and cross-model generalization to reduce the possibility that the observed performance is attributable to dataset-specific characteristics.
7.2 Dataset Selection
Dataset selection is a critical consideration because vulnerability detection performance can be strongly influenced by dataset construction, labeling procedures, duplication, class distribution, and project-level similarities. Existing vulnerability datasets differ substantially in their origins and intended purposes. Consequently, no single dataset is sufficient to evaluate all components of CRAFT-Sec.
This study proposes using six established resources: CodeXGLUE, Big-Vul, Devign, Juliet Test Suite, DiverseVul, and PrimeVul. Each dataset serves a different experimental purpose.
7.2.1 CodeXGLUE
CodeXGLUE is a benchmark for evaluating machine-learning approaches to code understanding and generation. It includes multiple tasks and datasets, including defect detection based on the Devign dataset [1].
The CodeXGLUE defect-detection task formulates source-code security classification as a binary prediction problem. Its samples are labeled as either insecure or secure, making it suitable for comparing CRAFT-Sec with established code representation and classification models.
The official defect-detection configuration uses an 80%/10%/10% training, validation, and testing split. This provides a reproducible benchmark configuration for comparing against established baselines.
Suitability:
                                             * Provides an established defect-detection benchmark.
                                             * Supports comparison with CodeBERT and other code-oriented models.
                                             * Provides a reproducible train-validation-test configuration.
                                             * Supports function-level vulnerability classification.
Limitations:
                                             * The defect-detection component is based on Devign and must not be treated as an independent dataset from Devign.
                                             * Its vulnerability coverage is narrower than that of larger multi-CWE datasets.
                                             * Its original task is not specifically designed to evaluate LLM-generated source code.
                                             * Its project distribution and original data construction can introduce generalization limitations.
For these reasons, CodeXGLUE will primarily serve as a benchmark reproduction and baseline-comparison configuration rather than an independent external dataset.
7.2.2 Big-Vul
Big-Vul is a real-world C/C++ vulnerability dataset constructed by collecting vulnerability-related code changes from open-source repositories and linking them with CVE information. The original dataset contains 3,754 code vulnerabilities spanning 91 vulnerability types and 348 GitHub projects [2].
The dataset connects vulnerable code versions with associated vulnerability-fixing changes and CVE descriptions. This makes it useful for investigating vulnerability detection, localization, and repair-related tasks.
Suitability:
                                             * Provides real-world vulnerability examples.
                                             * Includes CVE-related metadata.
                                             * Supports vulnerability classification and vulnerability-related code analysis.
                                             * Provides vulnerable and corrected code information useful for patch-related experiments.
                                             * Supports investigation of security weaknesses in C/C++ programs.
Limitations:
                                             * Vulnerability labels are derived partly from commit-based mining procedures and may contain noisy or incomplete annotations.
                                             * The presence of a vulnerability-fixing commit does not guarantee that every modified function is independently vulnerable.
                                             * Class imbalance can substantially affect detection metrics.
                                             * Repeated code and related project histories can create data leakage if samples are randomly divided without grouping.
                                             * Its original data is not specifically generated by LLMs.
Big-Vul will therefore be used as a major real-world benchmark, with duplicate detection, label-quality checks, and project-aware partitioning applied before training and evaluation.
7.2.3 Devign
Devign is a vulnerability-detection dataset introduced by Zhou et al. [3]. It was constructed from manually labeled source-code samples collected from four open-source C projects. The associated research introduced a graph neural network approach that learns program semantics using multiple code representations.
The dataset is particularly relevant to CRAFT-Sec because its graph-oriented representation provides a useful basis for evaluating the contribution of structural and semantic program information.
Suitability:
                                             * Contains real-world C source-code examples.
                                             * Supports function-level vulnerability classification.
                                             * Provides a foundation for graph-based vulnerability-detection comparisons.
                                             * Is relevant to AST, CFG, and data-flow-oriented analysis.
                                             * Enables comparison with the original Devign architecture.
Limitations:
                                             * Its project coverage is limited compared with larger vulnerability datasets.
                                             * Its original vulnerability categories are less comprehensive than those of multi-CWE datasets.
                                             * Function-level labels do not necessarily provide precise vulnerable-line annotations.
                                             * Its project-specific characteristics may limit generalization to unseen repositories.
                                             * It is not an LLM-generated-code benchmark.
Devign will be used as a structural vulnerability-detection benchmark. Its original dataset and the corresponding CodeXGLUE release will be treated as the same underlying data source for independent-dataset counting and leakage control.
7.2.4 Juliet Test Suite
The Juliet Test Suite was developed by the National Security Agency's Center for Assured Software and is distributed through the National Institute of Standards and Technology's Software Assurance Reference Dataset (NIST SARD).
Juliet provides synthetic test programs containing known software weaknesses and corresponding non-vulnerable examples. Version 1.3 includes 64,099 C/C++ test cases covering 118 CWE categories. Its Java version contains 28,881 test cases [4], [5].
The suite provides controlled vulnerability examples, making it suitable for evaluating whether CRAFT-Sec can identify known weakness patterns and distinguish vulnerable code from corresponding safe examples.
Suitability:
                                             * Provides explicitly organized CWE-based test cases.
                                             * Includes vulnerable and non-vulnerable examples.
                                             * Supports controlled experiments for vulnerability classification.
                                             * Is useful for evaluating static analysis, taint propagation, and security-rule coverage.
                                             * Supports reproducible vulnerability-specific evaluation.
Limitations:
                                             * Synthetic examples may not represent the complexity of real-world software.
                                             * Some examples contain simplified control and data-flow structures.
                                             * Similarity between generated test cases can lead to inflated performance when related cases are distributed across training and testing partitions.
                                             * Synthetic code patterns may differ from vulnerabilities produced by contemporary LLMs.
Juliet will therefore be treated as a controlled security-analysis benchmark rather than the primary indicator of real-world vulnerability-detection performance. Related test-case families will be grouped during data partitioning.
7.2.5 DiverseVul
DiverseVul was introduced by Chen et al. [6] as a large-scale vulnerable source-code dataset designed to improve project and vulnerability diversity. It contains 18,945 vulnerable functions and 330,492 non-vulnerable functions, collected from 7,514 vulnerability-related commits across a broad collection of open-source projects. The dataset covers 150 CWE categories.
Suitability:
                                             * Provides substantial project diversity.
                                             * Includes a broad range of vulnerability categories.
                                             * Supports cross-project generalization experiments.
                                             * Enables evaluation of multi-CWE detection.
                                             * Provides real-world C/C++ vulnerability examples.
Limitations:
                                             * The vulnerable and non-vulnerable classes are highly imbalanced.
                                             * Vulnerability labels depend on mining and labeling procedures.
                                             * The distribution of vulnerability categories is not uniform.
                                             * A large number of examples does not automatically guarantee high annotation quality.
                                             * Its original samples are not specifically generated by LLMs.
DiverseVul will be used as an external generalization benchmark and for CWE-stratified evaluation. Project-aware splitting and duplicate detection will be applied to reduce leakage.
7.2.6 PrimeVul
PrimeVul was introduced by Ding et al. as a dataset for evaluating code language models in more realistic vulnerability-detection settings [7]. It contains approximately 6,968 vulnerable functions and 228,800 non-vulnerable functions from real-world C/C++ projects, covering approximately 140 CWE categories.
An important characteristic of PrimeVul is its emphasis on improved labeling procedures, data deduplication, and chronological data splitting. These design choices address several limitations identified in earlier vulnerability benchmarks.
Suitability:
                                             * Provides a comparatively rigorous evaluation setting.
                                             * Includes real-world vulnerability examples.
                                             * Supports multi-CWE vulnerability classification.
                                             * Provides temporal evaluation information.
                                             * Reduces the risk of certain forms of duplicate-based and temporal data leakage.
                                             * Is particularly relevant for evaluating code language models.
Limitations:
                                             * Its programming-language coverage is primarily C/C++.
                                             * Its vulnerable examples represent a minority of the complete dataset.
                                             * Its chronological distribution may make the task more challenging than conventional random splitting.
                                             * It is not specifically an LLM-generated-code dataset.
                                             * Its original labels and task definitions still require careful interpretation when adapting the dataset to different detection granularities.
PrimeVul will serve as the primary benchmark for realistic vulnerability-detection evaluation. Its official partitioning and evaluation protocol will be preserved where possible.

7.2.8 Proposed Dataset Roles
To avoid inappropriate aggregation of datasets with different characteristics, the evaluation will follow three complementary tracks.
Track A: Benchmark reproduction.
CodeXGLUE/Devign and the relevant published configurations will be used to reproduce established vulnerability-detection comparisons.
Track B: Real-world generalization.
PrimeVul, Big-Vul, and DiverseVul will be used to investigate performance across real-world projects, vulnerability categories, and dataset distributions.
Track C: Controlled security analysis.
Juliet will be used for controlled CWE-specific evaluation, particularly for examining the behavior of static analysis, taint analysis, vulnerability localization, and detection of known weakness patterns.
The same underlying source code will not be counted as multiple independent test observations merely because it appears in different dataset releases.
7.3 Dataset Preprocessing
Dataset preprocessing will be performed using a consistent and documented pipeline to improve data quality, preserve source-code semantics, and reduce data leakage. Preprocessing will be applied independently to each dataset before the construction of training, validation, and testing partitions.
7.3.1 Data Collection and Verification
Each dataset will be obtained from its official repository, publication-associated release, or recognized distribution source.
The following metadata will be recorded:
                                             * Dataset name and release version.
                                             * Original source and download date.
                                             * Programming language.
                                             * Dataset license and usage conditions.
                                             * Original sample identifier.
                                             * Project and repository identifier, where available.
                                             * CVE and CWE identifiers, where available.
                                             * Original vulnerability label.
                                             * Associated commit or patch information.
                                             * Original training, validation, and testing partitions.
Checksums will be calculated for downloaded archives and processed data files to support reproducibility.
7.3.2 Source-Code Normalization
The source-code preprocessing pipeline will apply the following operations:
                                             1. Decode source files using appropriate character encodings.
                                             2. Normalize line endings and remove invalid encoding artifacts.
                                             3. Preserve meaningful indentation and language-specific syntax.
                                             4. Remove duplicated whitespace only where doing so does not change program semantics.
                                             5. Preserve comments when they contain security-relevant information or are required for vulnerability analysis.
                                             6. Preserve identifiers, function calls, operators, and control-flow constructs.
                                             7. Retain original line numbers and source offsets through source mapping.
Variable renaming, aggressive comment removal, or identifier normalization will not be applied indiscriminately because such transformations can remove information relevant to vulnerability detection and explanation.
7.3.3 Duplicate Detection
Duplicate detection is necessary because repeated or near-identical source-code samples can inflate performance when similar examples occur in both training and testing partitions.
Three levels of duplication analysis are proposed:
Exact duplication: Detect identical source-code functions using cryptographic hashes after conservative normalization.
Near duplication: Identify highly similar functions using token-based similarity or normalized structural fingerprints.
Semantic similarity: Where computationally feasible, investigate structurally similar functions using AST-based or code-embedding-based similarity.
Duplicate clusters will be assigned to a single partition wherever the dataset metadata allows. For overlapping datasets, cross-dataset duplicate analysis will also be conducted before cross-dataset evaluation.
7.3.4 Label Verification
Labels will be checked against available vulnerability metadata, associated CVE records, fixing commits, CWE descriptions, and paired corrected versions.
The following cases will receive special attention:
                                             * Identical source code with conflicting labels.
                                             * Missing or inconsistent CWE identifiers.
                                             * Functions modified by a vulnerability-fixing commit without direct evidence that the function itself contains the weakness.
                                             * Corrected functions that retain unrelated vulnerabilities.
                                             * Incomplete or non-compilable examples.
                                             * Samples with insufficient source-code context.
Ambiguous examples will be flagged rather than automatically treated as confirmed vulnerabilities. A predefined exclusion or adjudication policy will be applied consistently.
7.3.5 Function and Line-Level Representation
The primary detection task will use function-level classification because several selected datasets provide function-level labels.
Where vulnerable-line annotations or reliable patch-based localization information are available, line-level evaluation will also be performed.
Source-code functions will be represented using:
                                             * Original token sequences.
                                             * AST node information.
                                             * CFG nodes and edges.
                                             * DFG relationships.
                                             * Taint-source and taint-sink relationships.
                                             * Relevant vulnerability metadata.
                                             * SAE latent representations when model activations are accessible.
The original source code will be preserved for final explanation and patch generation.
7.3.6 Class Imbalance Handling
The selected datasets have different vulnerable-to-non-vulnerable class distributions. Class imbalance will be handled using training-only procedures.
Potential techniques include:
                                             * Class-weighted loss functions.
                                             * Training-set resampling.
                                             * Focal loss as an alternative classification objective.
                                             * Threshold calibration on validation data.
The original test-set class distribution will be preserved. Oversampling, undersampling, or synthetic sample generation will not be applied to the final test partition.
Performance will be reported using precision, recall, F1-score, Matthews Correlation Coefficient (MCC), and area under the precision-recall curve (AUPRC), in addition to accuracy.
7.3.7 Leakage Prevention
Data leakage will be controlled through the following procedures:
                                             1. Split data before fitting learned preprocessing components.
                                             2. Fit normalization parameters and feature-selection procedures using training data only.
                                             3. Train SAE dictionaries without using held-out test activations for parameter fitting.
                                             4. Prevent source-code duplicates and related samples from crossing partitions.
                                             5. Preserve official temporal splits where available.
                                             6. Prevent test-set labels from influencing threshold selection.
                                             7. Separate prompt templates and generated-code evaluation examples from training data.
                                             8. Record any overlap between training corpora and evaluation datasets where such information is available.
These measures are intended to provide a more reliable estimate of generalization performance.
7.4 Programming Languages
The programming-language configuration will reflect the coverage of the selected datasets and the requirements of the proposed framework.
C and C++ will be the primary languages because Big-Vul, Devign, PrimeVul, and DiverseVul predominantly contain C/C++ examples. These languages are particularly useful for investigating memory-safety vulnerabilities, unsafe pointer operations, resource management errors, and other low-level security weaknesses.
Java will be included as a secondary language, primarily through the Juliet Test Suite and controlled LLM-generated examples. Python will be considered for supplementary LLM-generation experiments because it is widely used in application development and has a different vulnerability profile from C/C++.

7.5 LLM Selection
LLM selection is important because CRAFT-Sec investigates both vulnerabilities in generated code and latent representations associated with code-generation behavior.
The proposed model configuration will include open-weight models that permit internal activation extraction and, where technically supported, controlled interventions. A separate black-box evaluation configuration may be included to examine the framework's applicability when internal model parameters are inaccessible.
7.5.1 Open-Weight Models
The following models are proposed as candidate experimental models:
Qwen2.5-Coder. Qwen2.5-Coder provides code-oriented models in multiple parameter sizes and supports code generation, completion, reasoning, and repair-related tasks [8]. A 7B checkpoint is a practical primary candidate for activation-based experiments, subject to hardware and checkpoint availability.
StarCoder2. StarCoder2 provides open code models in 3B, 7B, and 15B parameter sizes and supports code completion and fill-in-the-middle tasks [9]. Its architecture and accessible weights make it a candidate for investigating latent code-generation representations.
Code Llama. Code Llama provides foundation, Python-specialized, and instruction-following variants in multiple parameter sizes [10]. Its code-oriented training and publicly described architecture make it suitable as an additional model family for comparative experiments.
DeepSeek-Coder. DeepSeek-Coder provides open code-oriented models at multiple parameter sizes and supports code generation and infilling [11]. It may be included as an additional model family if the selected checkpoint and activation-capture implementation are compatible with the experimental environment.
The primary model set should contain at least two distinct open-weight model families. A third family is recommended when computational resources permit. Model selection will be finalized after confirming checkpoint availability, license requirements, architecture compatibility, and activation access.
7.5.2 Black-Box Models
A supplementary black-box model may be selected for evaluating the source-code analysis pathway when model internals are unavailable.
The black-box evaluation will use a fixed model identifier or dated API snapshot where available. Prompt templates, generation parameters, API settings, and response metadata will be recorded.
Black-box models will not be included in experiments that require direct internal activation extraction or SAE intervention.
7.5.3 Model Selection Criteria

                                             * Support for the target programming languages.
                                             * Access to internal activations for white-box experiments.
                                             * Compatibility with SAE extraction and intervention procedures.
                                             * Reproducibility of model inference.
                                             * Model size and computational feasibility.
                                             * License and research-use requirements.

7.5.4 Controlled Code Generation
To construct a corpus specifically representing LLM-generated code, each selected model will receive standardized programming tasks.
The generation procedure will include:
                                             1. Define a programming task and its functional requirements.
                                             2. Define the programming language and execution constraints.
                                             3. Generate code using a fixed prompt template.
                                             4. Store the model identifier and generation parameters.
                                             5. Preserve the original generated source code.
                                             6. Compile or execute the code where feasible.
                                             7. Evaluate the code against functional tests.
                                             8. Perform independent security analysis.
                                             9. Record vulnerability labels and evidence.
                                             10. Retain rejected or invalid outputs with explicit status information.
Prompts will include ordinary programming tasks and security-sensitive tasks. The latter will be designed to investigate whether insecure implementations arise under realistic development requirements, rather than instructing the model to produce exploitable code unnecessarily.
Generated examples will not automatically receive vulnerability labels based only on model predictions. Independent static analysis, dynamic analysis, test cases, and expert adjudication will be used where applicable.
5.6 Baseline Methods
CRAFT-Sec will be compared against conventional static-analysis methods, machine-learning classifiers, code-oriented pretrained models, graph-based vulnerability detectors, and ablated versions of the proposed framework.
Baseline methods will be selected according to their compatibility with the dataset, programming language, and evaluation granularity.
5.6.1 Traditional Machine-Learning Baselines
The following conventional classifiers are proposed:
                                             * TF-IDF with Logistic Regression.
                                             * TF-IDF with Support Vector Machine.
                                             * Random Forest using extracted source-code features.
                                             * Gradient-boosted decision trees using structured code features.
These methods will establish whether CRAFT-Sec provides benefits beyond conventional feature-based classification.
5.6.2 Deep Learning Baselines
The following models are proposed:
BiLSTM: A sequence-based model that learns contextual representations from token sequences.
TextCNN: A convolutional architecture for extracting local token-pattern information.
CodeBERT: A pretrained model designed to learn representations from programming and natural language [12].
Graph-based vulnerability detection: The original Devign architecture will be included where its implementation and dataset configuration can be reproduced [3].
GraphCodeBERT: A code representation model that incorporates data-flow information and can serve as a complementary pretrained baseline.
These baselines will be trained and evaluated using compatible data partitions. Their input representations and available metadata will be documented.
5.6.3 Static and Dynamic Analysis Baselines
Conventional program-analysis systems will be included to assess the contribution of program-level evidence.
Proposed tools include:
                                             * CodeQL for query-based source-code security analysis.
                                             * Semgrep for rule-based static analysis.
                                             * Joern for code property graph construction and program analysis.
                                             * Clang Static Analyzer for applicable C/C++ analysis.
                                             * AddressSanitizer and UndefinedBehaviorSanitizer for applicable runtime error detection.
                                             * Language-specific testing and security tools where supported.
The tools will be treated as independent analysis baselines and evidence sources. Their findings will be mapped to the common vulnerability representation where possible.
5.6.4 LLM-Based Baselines
The selected code-generation models will also be evaluated without CRAFT-Sec's additional security components.
The comparison configurations will include:
                                             1. Direct LLM vulnerability classification using a standardized prompt.
                                             2. LLM classification with a structured vulnerability-reporting prompt.
                                             3. LLM-generated repair without evidence-fusion guidance.
                                             4. LLM-generated code using a security-aware prompt without SAE-based analysis.
                                             5. LLM-generated code using security-aware prompting with conventional static-analysis feedback.
These configurations will help distinguish the contribution of CRAFT-Sec from the general capabilities of the underlying LLM.

5.8 Training and Testing Configuration
The training and testing configuration will be designed to preserve independent evaluation and minimize information leakage.
5.8.1 Dataset Partitioning
For datasets without a mandatory official split, the proposed partitioning strategy is:
                                             * Training set: 70%.
                                             * Validation set: 15%.
                                             * Testing set: 15%.
Partitioning will be performed using project-aware grouping and label stratification where the available metadata permits. Related functions, commits, or duplicate clusters will not be distributed across different partitions.
The official CodeXGLUE/Devign split will be preserved for benchmark reproduction. PrimeVul's official temporal partitioning will be preserved for its primary realistic evaluation.
For Juliet, related test-case families and paired vulnerable/non-vulnerable variants will be grouped to prevent structurally related examples from appearing in different partitions.
5.8.2 Training Configuration
The proposed training configuration will include:
                                             1. Initialize the selected model or classifier.
                                             2. Load the training partition.
                                             3. Construct source-code and program-analysis representations.
                                             4. Apply training-only class imbalance handling.
                                             5. Train the model using the selected optimization procedure.
                                             6. Evaluate performance on the validation partition.
                                             7. Select the checkpoint using a predefined validation criterion.
                                             8. Calibrate the classification threshold using validation data.
                                             9. Evaluate the selected checkpoint once on the held-out test partition.
The primary model-selection criterion will be validation macro-F1 or validation AUPRC, depending on the evaluation task and class distribution. Accuracy alone will not be used as the checkpoint-selection criterion for highly imbalanced datasets.
5.8.3 SAE Training Configuration
SAEs will be trained using internal activations obtained from the selected open-weight models.
The activation collection procedure will specify:
                                             * Model checkpoint and revision.
                                             * Transformer layer.
                                             * Token-selection policy.
                                             * Activation normalization.
                                             * Activation sampling procedure.
                                             * SAE latent dimension.
                                             * Sparsity regularization.
                                             * Training and validation activation partitions.
SAE training data will be derived from the training partition or a separate training-only calibration corpus. Test-set activations will not be used to optimize the SAE dictionary or select SAE hyperparameters.
SAE evaluation will include reconstruction error, latent sparsity, feature stability, and security-related feature associations.
5.8.4 Testing Configuration
The held-out testing phase will evaluate:
                                             * Binary vulnerability detection.
                                             * Multi-class CWE prediction where labels permit.
                                             * Vulnerable-line localization where ground truth is available.
                                             * Feature-attribution quality.
                                             * Evidence-fusion performance.
                                             * Security-aware generation.
                                             * Automated repair.
                                             * Patch validation.
                                             * Runtime and memory consumption.
The test partition will remain unchanged during model selection and hyperparameter optimization.
For LLM-generated code, generated examples will be separated by task and prompt family to reduce overlap between training and testing conditions. Repeated outputs from the same task or closely related prompts will be grouped to prevent leakage.

5.9.1 Hyperparameter Selection Procedure
Hyperparameter selection will follow a consistent procedure:
                                             1. Define a bounded search space for each component.
                                             2. Train candidate configurations using training data.
                                             3. Evaluate candidates on validation data.
                                             4. Select the configuration using a predefined validation metric.
                                             5. Record the selected parameters and model checkpoint.
                                             6. Freeze the configuration before final testing.
Hyperparameter searches will not use the test partition. For SAE models, feature stability and reconstruction quality will be considered alongside sparsity rather than selecting a configuration solely because it produces highly sparse activations.
5.10 Repeated Experimental Trials
Repeated trials will be used to measure variability arising from random initialization, data ordering, training procedures, and model-generation behavior.
For trainable detection models and SAE configurations, at least five independent random-seed runs are proposed where computational resources permit.
Each trial will use:
                                             * The same dataset partitions.
                                             * A documented random seed.
                                             * The same hyperparameter configuration.
                                             * The same evaluation procedure.
                                             * The same model checkpoint initialization policy.
                                             * Independent training initialization where applicable.
For deterministic baselines, repeated execution may produce identical results. In such cases, unnecessary duplicate runs will not be interpreted as independent evidence.
LLM-generation experiments will also consider output variability. For each task and model, multiple generations may be collected under predefined decoding configurations. The number of generations per task will be fixed before evaluation.
The following measures will be reported:
                                             * Mean and standard deviation.
                                             * Median and interquartile range where appropriate.
                                             * 95% confidence intervals.
                                             * Per-seed performance.
                                             * Per-model performance.
                                             * Per-dataset performance.
                                             * Per-CWE performance where sample sizes permit.
For repair experiments, the unit of analysis will be the original vulnerable program or vulnerability instance, not each generated patch independently. Multiple patches from the same vulnerability will be treated as related candidate outcomes.

5.13 CWE-Level Evaluation
CRAFT-Sec will be evaluated at the Common Weakness Enumeration (CWE) level to determine whether the framework performs consistently across different vulnerability categories.
Binary vulnerability detection alone cannot reveal whether a framework performs well across individual weakness types. For this reason, CWE-level evaluation will be conducted using datasets that provide sufficiently reliable category annotations.
5.13.1 CWE Selection
The initial CWE analysis will focus on categories represented in the selected datasets and supported by the relevant programming languages.
Potential categories include:
                                             * CWE-20: Improper Input Validation.
                                             * CWE-22: Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal').
                                             * CWE-78: Improper Neutralization of Special Elements used in an OS Command ('OS Command Injection').
                                             * CWE-79: Improper Neutralization of Input During Web Page Generation ('Cross-site Scripting').
                                             * CWE-89: Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection').
                                             * CWE-119: Improper Restriction of Operations within the Bounds of a Memory Buffer.
                                             * CWE-125: Out-of-bounds Read.
                                             * CWE-787: Out-of-bounds Write.
                                             * CWE-416: Use After Free.
                                             * CWE-476: NULL Pointer Dereference.
                                             * CWE-190: Integer Overflow or Wraparound.
                                             * CWE-362: Concurrent Execution using Shared Resource with Improper Synchronization.
The final CWE list will be determined by the intersection of dataset coverage, annotation reliability, programming-language compatibility, and sufficient evaluation sample counts. The presence of a CWE in a dataset does not imply that it is sufficiently represented for statistically reliable conclusions.
5.13.2 CWE-Level Classification
For each supported CWE category, the framework will be evaluated using binary and, where appropriate, multi-class classification.
For a vulnerability category (k), the category-specific F1-score is defined as:
[
F1_k=\frac{2P_kR_k}{P_k+R_k}
]
Here, (P_k) and (R_k) denote precision and recall for category (k), respectively.
Macro-averaged performance will be calculated as:
[
F1_{macro}=\frac{1}{K}\sum_{k=1}^{K}F1_k
]
Here, (K) represents the number of evaluated CWE categories.
Micro-averaged metrics will also be reported where appropriate, because they provide an aggregate view weighted by the number of evaluated instances.
5.13.3 CWE-Level Localization
For categories with line-level or statement-level annotations, localization will be evaluated using:
                                             * Line-level precision.
                                             * Line-level recall.
                                             * Line-level F1-score.
                                             * Top-k localization accuracy.
                                             * Intersection over Union where a ground-truth vulnerable region is available.
                                             * Mean reciprocal rank for ranked localization outputs, where applicable.
For datasets that provide only function-level labels, precise vulnerable-line localization will not be claimed as ground-truth accuracy. Such cases will be reported separately as localization predictions requiring independent verification.
5.13.4 CWE-Level Risk Assessment
The risk-assessment component will be evaluated by examining whether detected vulnerability categories are assigned risk levels consistent with the selected security policy.
Severity information will be distinguished from model confidence. Where CVSS metadata is available, it may be used as an external severity reference, but CVSS severity and vulnerability probability will not be treated as interchangeable quantities.
5.13.5 Statistical Reporting
For each CWE category, the evaluation will report the number of vulnerable and non-vulnerable examples, the number of projects where available, and the corresponding performance metrics.
Categories with insufficient sample counts will be identified explicitly. Their results will be treated as descriptive rather than as strong statistical evidence.
5.14 Ablation Experiment Configuration
Ablation experiments will investigate the contribution of individual CRAFT-Sec components to the overall framework. Each ablation will remove or disable one component while keeping the remaining experimental conditions as consistent as possible.
The full CRAFT-Sec configuration will serve as the reference system.
5.14.1 Proposed Ablation Configurations
Ablation A1: Without SAE-based feature extraction.
Remove SAE-derived latent representations while preserving source-code representations and program-analysis evidence. This configuration evaluates the contribution of SAE-based neural interpretability.
Ablation A2: Without feature interaction analysis.
Retain SAE feature extraction but remove feature co-activation and intervention-based interaction analysis. This experiment evaluates whether interaction analysis provides additional detection or explanation value.
Ablation A3: Without AST analysis.
Disable AST-derived structural information while preserving the remaining analysis components.
Ablation A4: Without CFG analysis.
Remove control-flow information to assess the contribution of execution-path representations.
Ablation A5: Without DFG and taint analysis.
Disable data-flow and taint-propagation evidence to examine the contribution of source-to-sink reasoning.
Ablation A6: Without multi-feature evidence fusion.
Replace the fusion mechanism with an individual evidence source or a predefined single-modality classifier. This configuration evaluates the benefit of combining heterogeneous evidence.
Ablation A7: Without explainable vulnerability localization.
Retain vulnerability detection but remove the localization and explanation components. This experiment investigates the contribution of fine-grained explanations to downstream repair.
Ablation A8: Without security-aware prevention.
Use ordinary generation prompts without the additional security constraints and feedback procedures. This configuration provides a comparison for prevention effectiveness.
Ablation A9: Without automated repair validation.
Generate repair candidates but do not apply the complete security and regression validation procedure. This configuration is intended to demonstrate why patch generation alone is insufficient to establish successful repair.
Ablation A10: Without dynamic analysis.
Remove runtime evidence while retaining neural and static analysis. This experiment evaluates the contribution of dynamic testing.
Ablation A11: Without neural evidence.
Disable SAE-based evidence and evaluate the framework using the source-code analysis pathway. This configuration is particularly important for examining black-box applicability.

To ensure that the experimental findings can be independently assessed, all experimental configurations will be documented before the final evaluation.
The following artifacts are intended to be retained and made available where licensing and security restrictions permit:
                                             1. Dataset identifiers, versions, and checksums.
                                             2. Dataset preprocessing scripts.

                                             4. Model checkpoint identifiers and revisions.

                                             8. Static-analysis and dynamic-analysis tool versions.

                                             10. Vulnerability annotation and adjudication procedures.

The evaluation will distinguish between model predictions, tool-generated findings, independently confirmed vulnerabilities, and successfully validated repairs. A predicted vulnerability will not automatically be considered a confirmed security defect, and a generated patch will not be considered successful merely because it modifies the original code or passes compilation.
Similarly, successful execution of functional tests will not independently establish security correctness. Patch acceptance will require the predefined combination of functional correctness, regression testing, and security re-analysis.
The proposed setup is designed to evaluate CRAFT-Sec under both controlled and realistic conditions. By combining benchmark reproduction, cross-dataset testing, CWE-level analysis, model-specific interpretability experiments, and component ablation, the experimental design aims to provide a comprehensive assessment of the framework's detection, explanation, prevention, and repair capabilities. The actual effectiveness of CRAFT-Sec will be determined only after the proposed experiments have been executed and their results have been statistically analyzed.


VII. EVALUATION METRICS
7.1 Overview of Evaluation Metrics
The effectiveness of CRAFT-Sec will be evaluated through five complementary categories: vulnerability detection, explainability, vulnerability localization, automated repair, and vulnerability prevention. These categories correspond to the principal operational objectives of the proposed framework and provide a systematic basis for comparing CRAFT-Sec with conventional vulnerability-detection methods, code-oriented learning models, program-analysis tools, and alternative LLM-based security configurations.
Each category measures a distinct aspect of framework performance. Vulnerability detection metrics quantify the ability to distinguish vulnerable from non-vulnerable code. Explainability metrics assess whether the generated explanations faithfully represent the model's decision process and remain stable under controlled variations. Vulnerability localization metrics measure the accuracy with which the framework identifies the source-code regions responsible for security weaknesses. Automated repair metrics evaluate whether generated patches compile, preserve functionality, and eliminate targeted vulnerabilities without introducing additional weaknesses. Finally, vulnerability prevention metrics examine whether security-aware generation reduces the occurrence of vulnerabilities while maintaining functional correctness.
The evaluation will use ground-truth annotations, independently verified vulnerability evidence, and predefined functional and security test suites wherever applicable. The metrics will be computed on held-out test data or controlled evaluation tasks. Hyperparameter selection and threshold calibration will be performed using validation data rather than the final test set.
The five evaluation categories are defined as follows:
                                             1. Vulnerability Detection Metrics: Evaluate classification performance and the ability to identify vulnerable code.
                                             2. Explainability Metrics: Evaluate the faithfulness and stability of explanations produced by CRAFT-Sec.
                                             3. Vulnerability Localization Metrics: Evaluate whether identified vulnerable lines, statements, or code regions correspond to the ground-truth vulnerable regions.
                                             4. Automated Repair Metrics: Evaluate compilation, functional correctness, patch success, and security regression after repair.
                                             5. Vulnerability Prevention Metrics: Evaluate the reduction of vulnerabilities during security-aware code generation and the preservation of functional requirements.
The following subsections define the mathematical formulation, interpretation, relevance, and limitations of each metric.
7.2 Vulnerability Detection Metrics
Vulnerability detection is the primary classification task of CRAFT-Sec. Given a source-code unit, the framework predicts whether the code contains a vulnerability. Depending on dataset annotations, the classification may be performed at function, file, or code-unit level.
For binary vulnerability detection, the following confusion-matrix quantities are defined:
                                             * True Positive (TP): Number of vulnerable samples correctly classified as vulnerable.
                                             * True Negative (TN): Number of non-vulnerable samples correctly classified as non-vulnerable.
                                             * False Positive (FP): Number of non-vulnerable samples incorrectly classified as vulnerable.
                                             * False Negative (FN): Number of vulnerable samples incorrectly classified as non-vulnerable.
These quantities form the basis of the classification metrics described below.
7.2.1 Accuracy
Accuracy measures the proportion of all evaluated samples that are correctly classified.
[
Accuracy=\frac{TP+TN}{TP+TN+FP+FN}
]
Variable definitions:
                                             * (TP): True positives.
                                             * (TN): True negatives.
                                             * (FP): False positives.
                                             * (FN): False negatives.
Scientific meaning: Accuracy represents the overall correctness of the classifier across both vulnerable and non-vulnerable samples.
Relevance to CRAFT-Sec: It provides an intuitive summary of the framework's classification performance and enables comparison with conventional vulnerability-detection baselines.
Limitations: Accuracy can be misleading when the dataset is highly imbalanced. For example, a classifier that predicts every sample as non-vulnerable may achieve high accuracy when vulnerable samples are rare. Therefore, accuracy will not be interpreted independently of precision, recall, F1-score, MCC, and PR-AUC.
7.2.2 Precision
Precision measures the proportion of predicted vulnerable samples that are actually vulnerable.
[
Precision=\frac{TP}{TP+FP}
]
Variable definitions:
                                             * (TP): Correctly identified vulnerable samples.
                                             * (FP): Non-vulnerable samples incorrectly identified as vulnerable.
Scientific meaning: Precision quantifies the reliability of positive vulnerability predictions.
Relevance to CRAFT-Sec: High precision reduces unnecessary security alerts and minimizes the burden of manually reviewing false-positive findings. This is particularly important when CRAFT-Sec combines neural predictions with static and dynamic analysis evidence.
Limitations: Precision does not indicate how many actual vulnerabilities were missed. A classifier can achieve high precision by predicting only a small number of highly confident vulnerabilities while failing to detect many other vulnerable samples. Precision also depends on the prevalence of vulnerabilities in the evaluated population.
7.2.3 Recall
Recall, also referred to as sensitivity or true positive rate, measures the proportion of actual vulnerable samples correctly identified.
[
Recall=\frac{TP}{TP+FN}
]
Variable definitions:
                                             * (TP): Correctly detected vulnerable samples.
                                             * (FN): Vulnerable samples incorrectly classified as non-vulnerable.
Scientific meaning: Recall indicates the detection coverage of the framework.
Relevance to CRAFT-Sec: High recall is important because missed vulnerabilities may remain in generated source code and subsequently enter software systems. It is particularly relevant when evaluating security weaknesses with potentially serious consequences.
Limitations: Recall does not account for false-positive predictions. A classifier that labels nearly every sample as vulnerable may achieve high recall but produce an impractical number of incorrect alerts. Therefore, recall must be considered alongside precision and other classification measures.
7.2.4 F1-Score
The F1-score is the harmonic mean of precision and recall.
[
F1=\frac{2\times Precision\times Recall}
{Precision+Recall}
]
Equivalently:
[
F1=\frac{2TP}{2TP+FP+FN}
]
Variable definitions:
                                             * (TP): True positives.
                                             * (FP): False positives.
                                             * (FN): False negatives.
                                             * (Precision): Positive prediction reliability.
                                             * (Recall): Vulnerability detection coverage.
Scientific meaning: F1-score provides a balanced measure of precision and recall.
Relevance to CRAFT-Sec: It is useful for comparing vulnerability-detection configurations when both missed vulnerabilities and false-positive alerts are important.
Limitations: F1-score does not incorporate true negatives and does not directly represent the operational cost of different error types. It can also conceal differences between precision and recall. Macro-F1 and class-specific F1-scores should therefore be reported when evaluating multiple CWE categories.
7.2.5 Matthews Correlation Coefficient (MCC)
Matthews Correlation Coefficient measures the correlation between actual and predicted binary classifications.
[
MCC=
\frac{TP\times TN-FP\times FN}
{\sqrt{(TP+FP)(TP+FN)(TN+FP)(TN+FN)}}
]
Variable definitions:
                                             * (TP): True positives.
                                             * (TN): True negatives.
                                             * (FP): False positives.
                                             * (FN): False negatives.
Scientific meaning: MCC evaluates classification quality using all four confusion-matrix quantities.
Its value ranges from (-1) to (+1):
                                             * (+1): Perfect classification.
                                             * (0): No correlation between predictions and actual labels.
                                             * (-1): Complete disagreement between predictions and actual labels.
Relevance to CRAFT-Sec: MCC is particularly useful for imbalanced vulnerability datasets, such as PrimeVul and DiverseVul, because it incorporates both positive and negative classification outcomes.
Limitations: MCC can be undefined when a prediction or ground-truth class is absent, producing a zero denominator. Such cases must be handled explicitly and reported. MCC also does not provide a direct measure of probability calibration or vulnerability severity.
7.2.6 Receiver Operating Characteristic Area Under the Curve (ROC-AUC)
ROC-AUC evaluates the ability of a classifier to distinguish vulnerable from non-vulnerable samples across different classification thresholds.
The true positive rate is:
[
TPR=\frac{TP}{TP+FN}
]
The false positive rate is:
[
FPR=\frac{FP}{FP+TN}
]
ROC-AUC is calculated as the area under the ROC curve:
[
ROC\text{-}AUC=\int_0^1 TPR(FPR),d(FPR)
]
Variable definitions:
                                             * (TPR): True positive rate.
                                             * (FPR): False positive rate.
                                             * (TP), (TN), (FP), and (FN): Confusion-matrix quantities calculated at a particular threshold.
Scientific meaning: ROC-AUC measures how effectively a classifier ranks vulnerable samples above non-vulnerable samples across possible thresholds.
Relevance to CRAFT-Sec: It enables threshold-independent comparisons among multi-feature classifiers, SAE-enhanced configurations, and conventional code-analysis baselines.
Limitations: ROC-AUC can appear favorable under severe class imbalance even when the precision of positive predictions is low. It also does not identify the best operational threshold. Therefore, ROC-AUC will be reported together with PR-AUC and threshold-dependent metrics.
7.2.7 Precision-Recall Area Under the Curve (PR-AUC)
PR-AUC measures the area under the precision-recall curve and focuses on positive-class detection performance.
[
PR\text{-}AUC=\int_0^1 Precision(Recall),d(Recall)
]
Variable definitions:
                                             * (Precision): Proportion of predicted vulnerabilities that are actual vulnerabilities.
                                             * (Recall): Proportion of actual vulnerabilities successfully detected.
Scientific meaning: PR-AUC evaluates the trade-off between precision and recall over different classification thresholds.
Relevance to CRAFT-Sec: Vulnerability datasets frequently contain substantially more non-vulnerable samples than vulnerable samples. PR-AUC is therefore an important metric for determining whether CRAFT-Sec can identify vulnerabilities without generating excessive false-positive findings.
Limitations: PR-AUC depends on the positive-class prevalence of the evaluation dataset. Comparisons across datasets with different vulnerability proportions must be interpreted carefully. The interpolation and numerical integration method must also be specified consistently. The positive-class prevalence should be reported as a reference baseline.
7.2.8 Multi-Class and CWE-Level Detection Metrics
When CRAFT-Sec predicts multiple CWE categories, class-specific and aggregated metrics will be reported.
For (K) vulnerability categories, macro-averaged F1-score is:
[
F1_{macro}=\frac{1}{K}\sum_{k=1}^{K}F1_k
]
Here, (F1_k) is the F1-score for vulnerability category (k).
Micro-averaged precision is:
[
Precision_{micro}=
\frac{\sum_{k=1}^{K}TP_k}
{\sum_{k=1}^{K}(TP_k+FP_k)}
]
Micro-averaged recall is:
[
Recall_{micro}=
\frac{\sum_{k=1}^{K}TP_k}
{\sum_{k=1}^{K}(TP_k+FN_k)}
]
Scientific meaning: Macro-averaging gives equal importance to each evaluated category, while micro-averaging aggregates classification outcomes across all categories.
Relevance to CRAFT-Sec: These metrics reveal whether the framework performs consistently across common and less frequent vulnerability categories.
Limitations: Macro-averaged metrics can be unstable for categories with very few examples. Micro-averaged metrics can be dominated by frequent categories. The number of evaluated samples per CWE must therefore accompany the reported results.
7.3 Explainability Metrics
Explainability is a central component of CRAFT-Sec because the framework is designed not only to detect vulnerabilities but also to provide interpretable evidence about why a code unit is considered insecure.
The explainability evaluation will focus on two principal properties:
                                             1. Faithfulness: Whether the explanation accurately reflects the behavior of the underlying prediction model.
                                             2. Stability: Whether the explanation remains consistent under small, semantically preserving changes to the input or controlled variations in the analysis process.
SAE feature interpretability and explanation faithfulness are related but distinct. A latent feature may be understandable to a human without being important to a particular prediction. Conversely, a feature may influence a prediction without having an easily interpretable semantic description.
7.3.1 Explanation Faithfulness
Explanation faithfulness measures the extent to which an explanation corresponds to the actual behavior of the model being explained.
For CRAFT-Sec, a primary faithfulness evaluation will use controlled feature-ablation experiments. Let (f(x)) denote the model's vulnerability score for input representation (x). Let (A_k) denote the top-(k) features selected by the explanation method.
The comprehensiveness score is defined as:
[
Comp_k(x)=f(x)-f(x\setminus A_k)
]
Here, (x\setminus A_k) denotes the input representation after the selected features have been removed or appropriately ablated.
A larger positive value indicates that removing the features identified as important by the explanation produces a larger reduction in the vulnerability score.
The sufficiency score is defined as:
[
Suff_k(x)=f(x)-f(x_{A_k})
]
Here, (x_{A_k}) represents an input retaining only the selected explanatory features under a predefined masking or reconstruction procedure.
A smaller sufficiency score indicates that the selected features retain more of the original model score.
Variable definitions:
                                             * (f(x)): Original vulnerability prediction score.
                                             * (A_k): Set of the top-(k) explanatory features.
                                             * (x\setminus A_k): Input after removal or ablation of the selected features.
                                             * (x_{A_k}): Input retaining only the selected features.
                                             * (k): Number of selected explanatory features.
Scientific meaning: Comprehensiveness examines how much the selected explanatory features contribute to the original prediction. Sufficiency examines whether those features alone retain the prediction.
Relevance to CRAFT-Sec: These metrics can evaluate whether SAE features and other explanatory signals genuinely contribute to vulnerability predictions rather than merely appearing correlated with them.
Limitations: Feature removal can create out-of-distribution representations or unrealistic source code. The resulting score change may therefore reflect the intervention procedure rather than the original feature's true importance. The masking, replacement, or activation-ablation strategy must be documented. Faithfulness scores are model-relative and do not independently establish that the model has learned a correct security concept.
7.3.2 Attribution Faithfulness
A complementary approach evaluates the relationship between feature attribution scores and prediction changes under controlled interventions.
Let (a_i) denote the attribution assigned to feature (i), and let (\Delta_i) denote the absolute change in the model's prediction score after intervening on that feature.
The attribution faithfulness correlation is:
[
AF=\operatorname{SpearmanCorr}
\left(
{|a_i|}{i=1}^{n},
{|\Delta_i|}{i=1}^{n}
\right)
]
Variable definitions:
                                             * (a_i): Attribution value for feature (i).
                                             * (\Delta_i): Prediction-score change caused by the predefined intervention on feature (i).
                                             * (n): Number of evaluated features.
                                             * (\operatorname{SpearmanCorr}): Spearman rank correlation.
Scientific meaning: A higher positive correlation indicates that features assigned larger attribution values tend to produce larger prediction changes under the selected intervention.
Relevance to CRAFT-Sec: This metric can test whether SAE-based explanations identify features that meaningfully influence the vulnerability classifier.
Limitations: Correlation does not establish causality, and the result depends on the intervention design. Strongly correlated features may substitute for one another. The evaluation must therefore consider grouped interventions and feature redundancy. A high score does not establish that the attributed feature represents a semantically correct security concept.
7.3.3 Attribution Stability
Attribution stability measures whether explanations remain consistent under small, controlled changes to the input or analysis configuration.
Let (a(x)) denote the attribution vector for the original input and (a(\tilde{x})) denote the attribution vector for a perturbed but semantically equivalent input.
The rank-based attribution stability is:
[
AS_{rank}=
\operatorname{SpearmanCorr}(a(x),a(\tilde{x}))
]
Variable definitions:
                                             * (a(x)): Attribution vector for the original code.
                                             * (a(\tilde{x})): Attribution vector for the perturbed code.
                                             * (\tilde{x}): Semantically preserving variation of the original input.
Scientific meaning: A higher value indicates that the relative ranking of explanatory features remains similar after the controlled transformation.
Relevance to CRAFT-Sec: It is useful for evaluating whether explanations are robust to changes such as formatting, non-semantic identifier renaming, or harmless code restructuring.
Limitations: Spearman correlation measures ranking consistency rather than exact attribution-value agreement. It may also be misleading when many attribution values are tied or close to zero. Perturbations must preserve program behavior; otherwise, explanation changes may be legitimate rather than instability.
A complementary top-(k) stability measure is:
[
AS_{top-k}=
\frac{|A_k(x)\cap A_k(\tilde{x})|}
{|A_k(x)\cup A_k(\tilde{x})|}
]
Here, (A_k(x)) and (A_k(\tilde{x})) denote the top-(k) attributed features for the two inputs.
This Jaccard similarity ranges from zero to one, where one indicates identical top-(k) feature sets.
Limitations: Top-(k) stability ignores attribution magnitude and the ordering within the selected set. It can also be affected by the selected value of (k).
7.3.4 SAE Feature Stability
SAE feature stability measures whether comparable latent features are consistently identified across independent SAE training runs or controlled model configurations.
For two learned feature dictionaries, the cosine similarity between normalized decoder vectors can be used to identify matching features.
[
Sim(i,j)=
\frac{\mathbf{d}_i^{T}\mathbf{d}_j}
{|\mathbf{d}_i|_2|\mathbf{d}_j|_2}
]
Here, (\mathbf{d}_i) and (\mathbf{d}_j) represent decoder directions from two feature dictionaries.
A feature-matching procedure can identify the most similar feature in another dictionary, subject to a predefined matching threshold.
Scientific meaning: High similarity indicates that independently learned dictionaries contain features with similar decoder directions.
Relevance to CRAFT-Sec: It helps assess whether security-related SAE features are reproducible rather than artifacts of one training initialization.
Limitations: SAE feature matching is difficult when features split, merge, or represent overlapping concepts. Similar decoder directions do not guarantee identical activation behavior or semantic interpretation. Feature stability must therefore be evaluated together with activation patterns and behavioral tests.
7.4 Vulnerability Localization Metrics
Vulnerability localization evaluates whether CRAFT-Sec identifies the specific source-code region responsible for a detected security weakness.
The evaluation will use line-level, statement-level, or token-level annotations where reliable ground-truth information is available. Function-level vulnerability labels alone are insufficient to establish precise line-level localization accuracy.
Let:
                                             * (L_{GT}): Set of ground-truth vulnerable source-code lines.
                                             * (L_{Pred}): Set of lines predicted as vulnerable by CRAFT-Sec.
                                             * (TP_L): Number of correctly localized vulnerable lines.
                                             * (FP_L): Number of incorrectly localized lines.
                                             * (FN_L): Number of ground-truth vulnerable lines not localized.
7.4.1 Localization Precision
Localization precision measures the proportion of predicted vulnerable lines that overlap with the ground-truth vulnerable region.
[
Precision_L=
\frac{TP_L}{TP_L+FP_L}
]
Scientific meaning: It indicates the accuracy of the lines selected by the localization component.
Relevance to CRAFT-Sec: High localization precision reduces the amount of irrelevant code that developers must inspect.
Limitations: A high precision value can be obtained by identifying only a small portion of the vulnerable region. It does not measure complete vulnerability coverage.
7.4.2 Localization Recall
Localization recall measures the proportion of ground-truth vulnerable lines successfully identified.
[
Recall_L=
\frac{TP_L}{TP_L+FN_L}
]
Scientific meaning: It measures how much of the known vulnerable region is recovered by the localization method.
Relevance to CRAFT-Sec: It is important when vulnerabilities involve multiple statements or data-flow paths, because identifying only one statement may be insufficient for understanding the complete weakness.
Limitations: A method that marks a large portion of the source code as vulnerable may achieve high recall while producing poor precision.
7.4.3 Localization F1-Score
Localization F1-score balances localization precision and recall.
[
F1_L=
\frac{2\times Precision_L\times Recall_L}
{Precision_L+Recall_L}
]
Scientific meaning: It provides a balanced measure of vulnerable-region identification.
Relevance to CRAFT-Sec: It allows comparison of localization configurations that use SAE attribution, AST analysis, CFG analysis, DFG analysis, and taint propagation.
Limitations: It treats all evaluated lines equally and does not represent the semantic importance of individual statements. It may also be affected by annotation granularity and differences in how vulnerable regions are defined.
7.4.4 Localization Accuracy
For a binary line-level labeling task, localization accuracy is:
[
Accuracy_L=
\frac{TP_L+TN_L}
{TP_L+TN_L+FP_L+FN_L}
]
Here, (TN_L) denotes correctly identified non-vulnerable lines.
Scientific meaning: It measures the proportion of source-code lines correctly classified as vulnerable or non-vulnerable.
Relevance to CRAFT-Sec: It provides a supplementary measure of line-level classification quality.
Limitations: Source code usually contains many more non-vulnerable lines than vulnerable lines. Consequently, localization accuracy can be artificially high when the method predicts most lines as non-vulnerable. Localization precision, recall, and F1-score will therefore be prioritized.
7.4.5 Intersection over Union (IoU)
Intersection over Union measures the overlap between predicted and ground-truth vulnerable regions.
[
IoU=
\frac{|L_{Pred}\cap L_{GT}|}
{|L_{Pred}\cup L_{GT}|}
]
Variable definitions:
                                             * (L_{Pred}): Predicted vulnerable line set.
                                             * (L_{GT}): Ground-truth vulnerable line set.
                                             * (\cap): Intersection of the two sets.
                                             * (\cup): Union of the two sets.
Scientific meaning: IoU measures the degree of spatial overlap between the predicted and actual vulnerable regions.
Relevance to CRAFT-Sec: It is useful when the localization output consists of a contiguous or non-contiguous region rather than an individual line.
Limitations: IoU does not distinguish between different types of localization errors. A small boundary mismatch can substantially reduce the score for a short vulnerable region. It also requires reliable ground-truth region annotations.
7.4.6 Top-k Localization Accuracy
Top-(k) localization accuracy evaluates whether the actual vulnerable region appears among the top-(k) source-code locations ranked by the explanation system.
For vulnerability instance (i), define:
[
Hit@k_i=
\begin{cases}
1, & \text{if the ground-truth region is identified within top-}k\
0, & \text{otherwise}
\end{cases}
]
The aggregate measure is:
[
Hit@k=
\frac{1}{N}\sum_{i=1}^{N}Hit@k_i
]
Variable definitions:
                                             * (k): Number of top-ranked locations considered.
                                             * (N): Number of evaluated vulnerability instances.
                                             * (Hit@k_i): Indicator showing whether the relevant ground-truth location is found within the top-(k) predictions.
Scientific meaning: It measures how effectively the localization method ranks relevant source-code regions near the top.
Relevance to CRAFT-Sec: It is useful for developer-facing explanations, where inspecting a small number of highly ranked statements is preferable to reviewing an entire function.
Limitations: The metric depends on the chosen value of (k), the granularity of the ranked locations, and the quality of the ground-truth annotations. It does not measure the completeness of the localized region.
7.4.7 Mean Reciprocal Rank (MRR)
Mean Reciprocal Rank evaluates the position of the first correctly identified vulnerable location.
[
MRR=
\frac{1}{N}\sum_{i=1}^{N}\frac{1}{rank_i}
]
Variable definitions:
                                             * (N): Number of evaluated vulnerability instances.
                                             * (rank_i): Rank of the first relevant ground-truth location for instance (i).
If no relevant location is found within the evaluated ranking, its reciprocal rank is assigned zero.
Scientific meaning: MRR rewards localization systems that place the correct vulnerable region near the top of their ranked outputs.
Relevance to CRAFT-Sec: It is relevant to the explainable localization component because developers generally benefit when the most important vulnerable statement is presented early.
Limitations: MRR considers only the first relevant result and ignores additional vulnerable statements. It should therefore complement, rather than replace, localization F1-score and IoU.
7.5 Automated Repair Metrics
Automated repair evaluation determines whether CRAFT-Sec can transform vulnerable source code into a corrected version while maintaining the intended program behavior.
A repair candidate will not be considered successful solely because it is generated, compiles, or passes a limited number of tests. The evaluation must separately consider compilation, functional correctness, regression behavior, and security preservation.
Let:
                                             * (N_V): Number of original vulnerability instances selected for repair.
                                             * (N_P): Number of repair candidates generated.
                                             * (N_C): Number of candidates that compile successfully.
                                             * (N_T): Number of candidates that pass the predefined functional test suite.
                                             * (N_S): Number of candidates that satisfy the complete predefined repair-acceptance criteria.
                                             * (N_R): Number of evaluated repaired candidates that introduce at least one independently verified new security regression.
The experimental protocol will specify whether a metric is calculated per generated patch, per original vulnerability, or per accepted repair. These units must not be mixed.
7.5.1 Patch Generation Rate
Patch generation rate measures the proportion of original vulnerability instances for which at least one repair candidate is successfully produced.
[
PGR=
\frac{N_G}{N_V}
]
Here:
                                             * (N_G): Number of original vulnerability instances for which a non-empty repair candidate is generated.
                                             * (N_V): Number of original vulnerability instances submitted for repair.
Scientific meaning: It measures the operational coverage of the repair-generation component.
Relevance to CRAFT-Sec: It indicates whether the repair module can produce candidate modifications for detected vulnerabilities.
Limitations: Generating a patch does not establish that the patch is correct, secure, or compilable. Therefore, patch generation rate must not be interpreted as repair success.
7.5.2 Compilation Success Rate
Compilation success rate measures the proportion of generated patches that compile successfully under the specified compiler and build configuration.
[
CSR=
\frac{N_C}{N_P}
]
Variable definitions:
                                             * (N_C): Number of generated patches that compile successfully.
                                             * (N_P): Total number of generated patches evaluated for compilation.
Scientific meaning: It evaluates whether the repair output is syntactically and structurally acceptable to the relevant compiler or build system.
Relevance to CRAFT-Sec: A patch that does not compile cannot normally be deployed as a replacement for the original program.
Limitations: Compilation does not prove functional correctness or security. Some languages and runtime environments do not require a traditional compilation stage. For interpreted languages, an appropriate syntax or loading check should be reported separately rather than incorrectly treating compilation as applicable.
7.5.3 Test Pass Rate
Test pass rate measures the proportion of evaluated patches that pass the predefined functional test suite.
[
TPR_{patch}=
\frac{N_T}{N_P}
]
Here:
                                             * (N_T): Number of generated patches that pass all required functional tests.
                                             * (N_P): Number of generated patches evaluated.
For additional diagnostic reporting, the conditional test pass rate among compilable patches may be calculated:
[
TPR_{compiled}=
\frac{N_T}{N_C}
]
Scientific meaning: The first measure evaluates the end-to-end proportion of generated patches that pass functional testing. The second measures test performance conditional on successful compilation.
Relevance to CRAFT-Sec: Functional testing determines whether a repair preserves expected program behavior under the specified test conditions.
Limitations: Passing a finite test suite does not prove complete functional correctness. The result depends on test coverage, test quality, environmental assumptions, and the representativeness of test inputs. The unconditional and conditional measures must be clearly distinguished.
7.5.4 Functional Correctness
Functional correctness measures the proportion of repaired programs that satisfy the predefined functional requirements.
For repair candidate (j), define:
[
FC_j=
\begin{cases}
1, & \text{if all required functional tests pass}\
0, & \text{otherwise}
\end{cases}
]
The aggregate functional correctness rate is:
[
FC=
\frac{1}{N_P}\sum_{j=1}^{N_P}FC_j
]
Variable definitions:
                                             * (N_P): Number of evaluated repair candidates.
                                             * (FC_j): Functional correctness indicator for candidate (j).
Scientific meaning: It measures the extent to which the repaired program preserves the expected functionality under the specified acceptance tests.
Relevance to CRAFT-Sec: A security repair that breaks required program behavior is not an acceptable repair.
Limitations: Functional correctness is only as strong as the requirements and test suite used to evaluate it. Passing tests cannot establish correctness for all possible inputs or execution environments. This metric is related to test pass rate; it should not be counted as an independent success dimension when both use exactly the same test outcomes.
7.5.5 Patch Success Rate
Patch success rate measures the proportion of original vulnerability instances for which at least one generated patch satisfies all predefined acceptance criteria.
For original vulnerability instance (i), define:
[
Success_i=
\begin{cases}
1, & \text{if at least one candidate satisfies all acceptance criteria}\
0, & \text{otherwise}
\end{cases}
]
The patch success rate is:
[
PSR=
\frac{1}{N_V}\sum_{i=1}^{N_V}Success_i
]
Variable definitions:
                                             * (N_V): Number of original vulnerability instances submitted for repair.
                                             * (Success_i): Indicator that instance (i) has at least one accepted repair.
A patch will be considered successful only if it satisfies the following conditions:
                                             1. The targeted vulnerability is no longer confirmed by the predefined security verification procedure.
                                             2. The patch passes the required functional tests.
                                             3. The patch satisfies the applicable compilation or syntax validation requirement.
                                             4. No new security regression is identified by the specified verification process.
                                             5. The patch satisfies the predefined regression and compatibility requirements.
Scientific meaning: Patch success rate measures the practical ability of the repair system to resolve vulnerability instances rather than merely generate code modifications.
Relevance to CRAFT-Sec: It is the principal outcome metric for evaluating the complete automated repair pipeline.
Limitations: Patch success depends on the reliability and coverage of the functional and security validation procedures. A patch that passes all available tests may still contain undiscovered defects. The acceptance criteria must therefore be reported transparently.
7.5.6 Security Regression Rate
Security regression rate measures the proportion of evaluated repaired programs that introduce at least one new, independently verified security weakness.
[
SRR=
\frac{N_R}{N_E}
]
Here:
                                             * (N_R): Number of evaluated repaired programs that introduce at least one new security regression.
                                             * (N_E): Number of repaired programs subjected to the defined security regression evaluation.
Scientific meaning: It measures how frequently the repair process introduces additional security weaknesses.
Relevance to CRAFT-Sec: An automated repair system should not eliminate one vulnerability by introducing another. Security regression rate is therefore essential for evaluating patch safety.
Limitations: The metric depends on the coverage and reliability of the security-analysis tools and test cases. An undetected vulnerability may cause the regression rate to appear artificially low. A repaired program can also contain an unrelated pre-existing weakness that should not be incorrectly classified as newly introduced.
To distinguish new regressions from pre-existing findings, the original and repaired programs will be analyzed using the same security-verification configuration. Findings will be matched using vulnerability category, affected code region, data-flow evidence, and other available identifiers.
7.5.7 Security Fix Rate
Security fix rate measures the proportion of original vulnerabilities that are no longer detected or confirmed after repair.
[
SFR=
\frac{N_F}{N_V}
]
Here:
                                             * (N_F): Number of original vulnerability instances for which the targeted weakness is successfully mitigated.
                                             * (N_V): Number of original vulnerability instances submitted for repair.
Scientific meaning: It measures the effectiveness of patches in addressing the original security weaknesses.
Relevance to CRAFT-Sec: It distinguishes targeted vulnerability mitigation from compilation and functional correctness.
Limitations: A vulnerability may appear to disappear because the analysis tool fails to detect it after code transformation. Independent verification and, where possible, vulnerability-specific tests are required. Security fix rate does not by itself establish the absence of newly introduced vulnerabilities.
7.5.8 Repair Efficiency
Repair efficiency measures the computational effort required to obtain an accepted patch.
The average repair time is:
[
ART=
\frac{1}{N_V}\sum_{i=1}^{N_V}t_i
]
Here:
                                             * (N_V): Number of original vulnerability instances.
                                             * (t_i): Total repair and validation time for instance (i).
A complementary measure is the average number of generated candidates:
[
ANC=
\frac{1}{N_V}\sum_{i=1}^{N_V}r_i
]
Here, (r_i) denotes the number of repair candidates generated for instance (i).
Scientific meaning: These metrics measure the computational and search effort required by the repair process.
Relevance to CRAFT-Sec: They help determine whether the framework can provide practical repair assistance within a reasonable resource budget.
Limitations: Repair time depends on hardware, model inference latency, test-suite complexity, network conditions, and tool execution overhead. Comparisons must use consistent environments and clearly defined timing boundaries.
7.6 Vulnerability Prevention Metrics
Vulnerability prevention evaluates whether CRAFT-Sec reduces security weaknesses during code generation rather than only detecting or repairing them after generation.
The prevention experiments will compare a baseline generation condition with a security-aware generation condition. Both conditions will use the same underlying model, task definitions, programming language, functional requirements, and evaluation procedures wherever possible.
Let:
                                             * (N_B): Number of valid generated code samples in the baseline condition.
                                             * (N_S): Number of valid generated code samples in the security-aware condition.
                                             * (V_B): Number of vulnerable samples in the baseline condition.
                                             * (V_S): Number of vulnerable samples in the security-aware condition.
                                             * (F_B): Number of baseline samples passing functional tests.
                                             * (F_S): Number of security-aware samples passing functional tests.
A valid generated sample is one that satisfies the predefined task-output and evaluation eligibility requirements. Invalid or non-executable outputs will be recorded separately rather than silently excluded.
7.6.1 Vulnerability Rate
Vulnerability rate measures the proportion of generated samples that contain at least one independently verified vulnerability.
[
VR=
\frac{V}{N}\times100
]
Here:
                                             * (V): Number of generated samples containing at least one confirmed vulnerability.
                                             * (N): Total number of eligible generated samples evaluated.
Scientific meaning: It represents the frequency of vulnerable outputs produced under a particular generation condition.
Relevance to CRAFT-Sec: It provides the primary measure for determining whether security-aware generation reduces vulnerability occurrence.
Limitations: Vulnerability rate depends on task selection, model configuration, vulnerability annotation quality, and the coverage of the security-analysis procedure. It does not measure the number or severity of vulnerabilities within each sample. Results must therefore be interpreted alongside CWE-level findings and severity information.
7.6.2 Vulnerability Reduction Rate
Vulnerability reduction rate measures the relative decrease in vulnerability occurrence under security-aware generation compared with baseline generation.
[
VRR=
\frac{VR_B-VR_S}{VR_B}\times100
]
Here:
                                             * (VR_B): Vulnerability rate under baseline generation.
                                             * (VR_S): Vulnerability rate under security-aware generation.
Scientific meaning: A positive value indicates that security-aware generation reduces the observed vulnerability rate. A negative value indicates that the vulnerability rate increased.
Relevance to CRAFT-Sec: It directly evaluates whether security constraints, feedback, and prevention mechanisms improve the security of generated code.
Limitations: The measure is undefined when the baseline vulnerability rate is zero. It can also be misleading if baseline and security-aware generation use different task distributions or unequal sample counts. Both absolute vulnerability-rate differences and relative reduction will therefore be reported.
The absolute reduction is:
[
\Delta VR=VR_B-VR_S
]
This provides the percentage-point difference between the two generation conditions.
7.6.3 Functional Pass Rate
Functional pass rate measures the proportion of generated programs that satisfy the predefined functional test suite.
[
FPR=
\frac{F}{N}\times100
]
Here:
                                             * (F): Number of generated samples that pass all required functional tests.
                                             * (N): Number of eligible generated samples evaluated.
Scientific meaning: It measures whether the generated code satisfies the intended functional requirements.
Relevance to CRAFT-Sec: Security-aware generation must not achieve lower vulnerability rates simply by producing incomplete, unusable, or non-functional programs.
Limitations: Passing functional tests does not prove complete functional correctness. Results depend on the quality and coverage of the test suite. Functional pass rate must be considered alongside vulnerability rate.
7.6.4 Functional Preservation Rate
Functional preservation rate measures the extent to which security-aware generation maintains functional performance relative to baseline generation.
[
FPR_{preserve}=
\frac{F_S/N_S}{F_B/N_B}\times100
]
Here:
                                             * (F_S/N_S): Functional pass proportion under security-aware generation.
                                             * (F_B/N_B): Functional pass proportion under baseline generation.
Scientific meaning: A value of 100% indicates equal functional pass proportions between the two conditions. Values below 100% indicate a lower functional pass proportion under security-aware generation.
Relevance to CRAFT-Sec: It helps determine whether security constraints reduce vulnerability occurrence at the cost of functional utility.
Limitations: The metric is undefined when the baseline functional pass proportion is zero. It is a relative measure and should be reported alongside the absolute functional pass rates and their confidence intervals. It does not prove semantic equivalence between individual programs.
7.6.5 Security Compliance Rate
Security compliance rate measures the proportion of generated samples that satisfy the predefined security requirements and policy checks.
[
SCR=
\frac{N_{compliant}}{N}\times100
]
Here:
                                             * (N_{compliant}): Number of generated samples satisfying the predefined security policy.
                                             * (N): Total number of eligible generated samples.
Scientific meaning: It measures the extent to which generated code adheres to specified security requirements.
Relevance to CRAFT-Sec: It evaluates whether the prevention component follows security constraints such as input validation, safe API usage, appropriate authorization checks, and secure resource handling.
Limitations: Compliance depends on the completeness and correctness of the security policy. Passing policy checks does not prove the absence of all vulnerabilities. A code sample may comply with selected rules while containing weaknesses outside the evaluated policy scope.
7.6.6 Prevention Functional-Security Trade-off
The prevention component must balance security improvement and functional preservation.
The trade-off will be evaluated by jointly examining vulnerability rate and functional pass rate across baseline and security-aware generation.
A security-aware generation condition will be considered practically beneficial when it produces a lower vulnerability rate without an unacceptable reduction in functional pass rate.
The comparison will therefore report:
                                             * Baseline vulnerability rate.
                                             * Security-aware vulnerability rate.
                                             * Absolute vulnerability-rate reduction.
                                             * Relative vulnerability reduction.
                                             * Baseline functional pass rate.
                                             * Security-aware functional pass rate.
                                             * Functional preservation rate.
                                             * Security compliance rate.
No single weighted score will replace these individual metrics unless a separate, justified decision-theoretic evaluation is introduced.

7.8 Metric Selection and Reporting Strategy
To prevent misleading interpretations, CRAFT-Sec will use a predefined reporting strategy that maps each metric to the corresponding research objective.
7.8.1 Primary Metrics
The following metrics will be treated as primary evaluation measures:
Component
	Primary metrics
	Vulnerability detection

	Explainability
	Comprehensiveness, Sufficiency, Attribution Stability
	Vulnerability localization

7.8.2 Secondary Metrics
Secondary metrics will provide additional diagnostic information.
For vulnerability detection, accuracy and ROC-AUC will help describe overall classification and ranking behavior. For explainability, attribution faithfulness and SAE feature similarity will provide complementary evidence about model explanations and latent feature reproducibility. For localization, precision and recall will reveal whether the system favors narrow or broad vulnerable regions. For repair, compilation success, test pass rate, security fix rate, and average repair time will describe intermediate and operational outcomes. For prevention, functional preservation and security compliance will provide evidence about the security-utility trade-off.
7.8.3 Handling Undefined Metrics
Some metrics may become mathematically undefined when their denominators are zero.
Examples include:
                                             * Precision when (TP+FP=0).
                                             * Recall when (TP+FN=0).
                                             * MCC when its denominator is zero.
                                             * IoU when the union of predicted and ground-truth regions is empty.
                                             * Vulnerability reduction rate when the baseline vulnerability rate is zero.
                                             * Functional preservation rate when the baseline functional pass rate is zero.
These cases will be reported as undefined or not applicable according to a predefined evaluation policy. They will not be silently replaced with arbitrary values.
7.8.4 Dataset Imbalance and Aggregation
Because the selected datasets differ in class balance, vulnerability categories, and project composition, the evaluation will report both macro- and micro-averaged metrics where appropriate.
For dataset-level comparisons:
                                             * Preserve the original test distribution.
                                             * Report the number of vulnerable and non-vulnerable samples.
                                             * Report the prevalence of the positive class.
                                             * Provide category-specific results for sufficiently represented CWEs.
                                             * Avoid combining incompatible dataset metrics into a single aggregate score.
                                             * Distinguish within-dataset performance from cross-dataset performance.
Macro-averaging will be particularly useful for assessing performance across CWE categories, whereas micro-averaging will describe aggregate instance-level performance.
7.8.5 Statistical Uncertainty
Metric estimates will be accompanied by uncertainty measures where feasible.
For repeated model-training trials, the mean and standard deviation will be reported. Confidence intervals will be calculated using an appropriate procedure, such as bootstrap resampling at the independent sample or project level.
Paired statistical comparisons will be preferred when the same test instances are evaluated by multiple methods. The choice of statistical test will depend on the distribution of paired differences and the experimental design.
Multiple comparisons across models, datasets, and CWE categories will be controlled using an appropriate correction procedure. Effect sizes will be reported alongside statistical significance to distinguish practical improvements from small but statistically detectable differences.
7.8.6 Independent Verification Requirements
The reliability of the evaluation depends on the quality of the ground-truth labels and verification procedures.
For vulnerability detection, predicted findings will be compared with independently established labels. For explainability, feature interventions will be evaluated using controlled procedures. For localization, line-level accuracy will be claimed only when corresponding ground-truth vulnerable regions exist. For repair, the original and repaired programs will undergo equivalent security-analysis procedures. For prevention, generated outputs will be evaluated under identical functional and security verification criteria.
The framework will not claim that a program is completely secure merely because no vulnerability was detected by the selected tools. Likewise, passing a test suite will not be interpreted as proof of formal functional correctness or security.
7.9 Summary
The evaluation metrics defined in this section provide a multidimensional assessment of CRAFT-Sec. Vulnerability detection metrics quantify classification quality, while explainability metrics examine whether model explanations are faithful and stable. Localization metrics measure the accuracy of vulnerable-region identification. Automated repair metrics evaluate whether generated patches compile, preserve functionality, mitigate the targeted weakness, and avoid introducing additional vulnerabilities. Finally, prevention metrics measure whether security-aware generation reduces vulnerability occurrence without substantially degrading functional performance.
The five evaluation categories are deliberately separated to avoid conflating detection performance with explanation quality, localization accuracy, patch validity, or prevention effectiveness. This separation is essential for determining which components contribute to the framework's overall performance and for identifying limitations that may remain even when individual metrics indicate improvement.
The proposed metric set will be applied to the selected vulnerability datasets and the separately constructed LLM-generated-code evaluation corpus. Actual results, confidence intervals, and statistical comparisons will be reported only after the corresponding experiments have been conducted. Through this evaluation strategy, CRAFT-Sec can be assessed not merely by its ability to identify vulnerabilities, but also by its ability to explain security risks, identify vulnerable code regions, produce validated repairs, and prevent insecure code generation.


VIII. Baseline Comparison and Ablation Study
8.1. Experimental Purpose and Comparison Strategy
The baseline comparison and ablation study are designed to evaluate the effectiveness of CRAFT-Sec against representative approaches to software vulnerability detection, explainability, security analysis, and automated program repair. The primary objective is not merely to determine whether the complete framework achieves a higher detection score, but to establish whether its individual components and their integration provide measurable benefits across different security-related tasks.
The evaluation is organized around two complementary experiments. First, baseline comparison experiments compare CRAFT-Sec with established approaches from six categories: traditional static analysis, machine learning-based vulnerability detection, transformer-based vulnerability detection, LLM-based security analysis, explainability methods, and automated program repair. Second, component ablation experiments systematically remove individual CRAFT-Sec components to quantify their contributions to the overall framework.
The experiments address the following research questions:
                                             * RQ-B1: Does CRAFT-Sec improve vulnerability detection compared with traditional static analyzers and learning-based detection models?
                                             * RQ-B2: Does SAE-based feature extraction provide useful security-related representations beyond conventional model representations?
                                             * RQ-B3: Does feature interaction analysis contribute information beyond the independent analysis of individual features?
                                             * RQ-B4: Does combining neural evidence with AST, CFG, DFG, and taint analysis improve vulnerability detection and localization?
                                             * RQ-B5: Does multi-feature evidence fusion improve the reliability of vulnerability assessment compared with individual analysis modalities?
                                             * RQ-B6: Does the explainability component produce more faithful and useful vulnerability explanations than conventional attribution techniques?
                                             * RQ-B7: Does CRAFT-Sec produce more effective security repairs while preserving functional correctness and avoiding security regressions?
                                             * RQ-B8: Which framework components contribute most significantly to detection, localization, prevention, and repair performance?
All comparisons are proposed experimental configurations. No numerical performance results are assumed or reported in this section. The final evaluation will use the same benchmark instances, ground-truth annotations, and evaluation procedures wherever the compared approaches support the corresponding task.
8.2. Traditional Static Analysis Baselines
Traditional static analysis tools examine source code without executing the program. Depending on their implementation, they use lexical patterns, syntax, type information, control-flow information, data-flow analysis, or predefined security rules to identify potentially vulnerable code.
These approaches are important baselines because they provide established, non-generative alternatives to neural vulnerability detection. They also allow the evaluation to determine whether CRAFT-Sec's combination of learned representations and program analysis provides benefits beyond conventional rule-based analysis.
The following tools are proposed for evaluation:
8.2.1. Flawfinder
Flawfinder is a pattern-based static analysis tool that searches C and C++ source code for potentially dangerous functions and constructs. It provides a lightweight baseline for detecting vulnerabilities associated with unsafe library calls, buffer handling, and related coding practices.
Experimental purpose: To determine whether CRAFT-Sec detects vulnerabilities that cannot be reliably identified through lexical patterns alone.
Evaluation considerations: Flawfinder should be evaluated using its reported findings and mapped to the benchmark's vulnerability labels. Its rule coverage and language limitations must be documented. A missing finding must not automatically be interpreted as evidence that a program is secure.
8.2.2. Cppcheck
Cppcheck performs static analysis of C and C++ code and identifies a range of programming errors, including certain memory-safety and resource-management problems. It provides a complementary baseline because its analysis extends beyond simple lexical matching.
Experimental purpose: To compare CRAFT-Sec against a conventional static analyzer that considers additional program-level information.
Evaluation considerations: The selected Cppcheck version, enabled checks, configuration, and severity thresholds must be recorded. Only findings relevant to the benchmark's vulnerability labels should contribute to vulnerability-detection comparisons.
8.2.3. Semgrep
Semgrep uses configurable rules to identify potentially insecure code patterns and supports structural matching and selected data-flow-oriented analysis capabilities. Its rule-based configuration makes it suitable for evaluating how predefined security rules compare with CRAFT-Sec's learned and multi-feature analysis.
Experimental purpose: To establish whether CRAFT-Sec provides additional detection and localization capabilities beyond configurable pattern-based security analysis.
Evaluation considerations: The selected Semgrep rulesets, custom rules, rule versions, and language-specific configurations must be disclosed. The rules should be fixed before evaluating the test set. Rules must not be developed or modified using test-set labels.
8.2.4. CodeQL
CodeQL represents a more advanced static analysis baseline. It uses a code database and query-based analysis to identify security-relevant relationships, including selected data-flow and control-flow properties.
Experimental purpose: To assess whether CRAFT-Sec's combination of neural representations, program structures, and evidence fusion provides advantages over a mature query-based program analysis approach.
Evaluation considerations: The CodeQL version, language support, query packs, database extraction settings, and security query configurations must be recorded. Where possible, the evaluation should distinguish default security queries from custom queries created for the experiment.
8.2.5. Static Analysis Baseline Configuration
The static analysis tools will be evaluated independently before any combination with CRAFT-Sec components. This is necessary to distinguish the performance of individual tools from the performance of a hybrid configuration.

8.3. Machine Learning-Based Vulnerability Detection Baselines
Machine learning-based approaches provide a second comparison category. Unlike traditional static analyzers, these approaches learn vulnerability-related patterns from labeled source-code examples. They provide a reference for evaluating whether CRAFT-Sec's multi-feature representation and evidence integration improve upon conventional learned vulnerability classifiers.
The proposed baselines include the following methods.
8.3.1. Bag-of-Words with a Classical Classifier
A Bag-of-Words representation will be constructed from source-code tokens. A conventional classifier, such as logistic regression or a random forest, will use this representation to predict whether a code sample is vulnerable.
Experimental purpose: To establish a simple, reproducible machine learning baseline and determine whether more sophisticated representations provide measurable improvements over token-frequency information.
Evaluation considerations: Tokenization, vocabulary construction, feature selection, and hyperparameter tuning must use only the training and validation partitions.
8.3.2. VulDeePecker
VulDeePecker is a deep-learning-based vulnerability detection approach that uses code gadgets and learned representations to identify vulnerability-related patterns [7].
Experimental purpose: To compare CRAFT-Sec with an established learning-based approach that focuses on code contexts associated with vulnerable operations.
Evaluation considerations: The implementation must follow the original method as closely as possible. Differences in preprocessing, code-gadget extraction, language support, and training data must be documented.
8.3.3. SySeVR
SySeVR represents vulnerable code through semantic vulnerability-related representations and uses deep learning to classify code samples.
Experimental purpose: To evaluate whether CRAFT-Sec's combined lexical, syntactic, semantic, structural, and security-related evidence provides advantages over a vulnerability-oriented representation pipeline.
Evaluation considerations: The original representation and classification procedure should be retained where feasible. If an exact reproduction is unavailable, the implementation should be identified as a reimplementation rather than a direct reproduction.
8.3.4. Devign
Devign uses graph-based program representations and neural learning to identify vulnerable code by modeling program semantics and structural relationships [8].
Experimental purpose: To compare CRAFT-Sec against a graph-based vulnerability detection model and determine whether its additional SAE, interaction, and evidence-fusion mechanisms provide complementary information.
Evaluation considerations: Graph construction, node features, graph extraction, and training configuration should follow the original method or a clearly documented reproduction protocol.
8.3.5. Reveal
REVEAL is a graph-learning-based vulnerability detection approach designed to learn representations from program structure and vulnerability-related information.
Experimental purpose: To provide a further graph-oriented baseline and assess whether CRAFT-Sec's separate AST, CFG, DFG, and taint evidence contributes beyond a learned graph representation.
Evaluation considerations: The implementation and benchmark compatibility must be verified before inclusion. Any unavailable or incompatible configuration should be reported rather than silently replaced with a different model.

8.4. Transformer-Based Vulnerability Detection Baselines
Transformer-based approaches provide a more recent class of vulnerability detection systems. They learn contextual representations of source code and can capture relationships between tokens that are not represented explicitly by conventional token-frequency methods.
The proposed comparison includes the following models.
8.4.1. CodeBERT
CodeBERT is a pretrained model designed to learn representations of programming languages and natural language [9]. It can be fine-tuned as a binary vulnerability classifier by adding a classification head to its contextual representation.
Experimental purpose: To determine whether CRAFT-Sec improves upon a pretrained code-language representation without the proposed SAE-based feature extraction and multi-feature security architecture.
Evaluation considerations: The same training data, validation procedure, and test samples should be used where possible. The model checkpoint, tokenizer, maximum sequence length, and fine-tuning configuration must be recorded.
8.4.2. GraphCodeBERT
GraphCodeBERT incorporates data-flow information into pretrained code representations. It provides a useful comparison because it introduces structural and data-flow information into transformer-based code understanding.
Experimental purpose: To determine whether CRAFT-Sec provides additional benefits beyond a transformer model that already incorporates selected structural information.
Evaluation considerations: The experiment should distinguish the pretrained model's built-in data-flow representation from CRAFT-Sec's separately extracted DFG and taint-analysis evidence.
8.4.3. CodeT5
CodeT5 is a pretrained encoder-decoder model for code understanding and generation. It can be adapted to vulnerability classification or used in a repair-oriented experiment.
Experimental purpose: To compare CRAFT-Sec with a pretrained model that supports both source-code understanding and generation-related tasks.
Evaluation considerations: For vulnerability classification, the classification configuration must be specified. For repair, the generation prompt, input context, decoding parameters, and repair acceptance criteria must be standardized.
8.4.4. LineVul
LineVul is a transformer-based approach for line-level vulnerability prediction [10]. Its localization capability makes it particularly relevant to CRAFT-Sec's explainable vulnerability localization component.
Experimental purpose: To compare the ability of CRAFT-Sec and transformer-based line-level prediction to identify the source-code locations associated with vulnerabilities.
Evaluation considerations: Both systems must be evaluated against the same ground-truth vulnerable-line annotations. Function-level labels must not be treated as line-level ground truth. Where exact line annotations are unavailable, localization metrics should be restricted to samples with sufficiently reliable annotations.

8.5. LLM-Based Security Analysis Baselines
LLM-based security analysis is an important comparison category because CRAFT-Sec is intended to analyze code produced by large language models and may also use LLMs for prevention and repair.
The evaluation will include direct LLM prompting and feedback-based analysis configurations. The selected models should be accessible during the experiment, and their exact model identifiers, versions, dates of access, and inference configurations should be recorded.
8.5.1. Direct Zero-Shot Security Analysis
In this configuration, an LLM receives a source-code sample and a fixed security-analysis instruction. It is asked to identify vulnerabilities, provide a CWE category where possible, and report the affected source-code location.
Experimental purpose: To establish the performance of a general-purpose LLM used directly as a security analyst without CRAFT-Sec's specialized evidence extraction and fusion.
Evaluation considerations: The prompt must be fixed before test evaluation. The model should not receive benchmark labels, expected vulnerability locations, or hidden test metadata.
8.5.2. Few-Shot Security Analysis
In this configuration, the LLM receives a small set of labeled examples from the training partition before analyzing a test sample.
Experimental purpose: To determine whether limited in-context examples provide a meaningful improvement over direct zero-shot security analysis and whether CRAFT-Sec offers additional benefits.
Evaluation considerations: Few-shot examples must be selected exclusively from the training partition. They must not contain duplicate functions, vulnerable-fix pairs, or near-duplicate examples from the test set.
8.5.3. Chain-of-Thought-Free Structured Analysis
The LLM is instructed to produce a structured security report containing the suspected vulnerability, CWE category, affected location, evidence, and confidence. The evaluation should assess the observable evidence and final prediction rather than treating private internal reasoning or verbose explanations as proof of correctness.
Experimental purpose: To compare CRAFT-Sec's evidence-grounded explanations with structured explanations generated directly by an LLM.
Evaluation considerations: Explanations should be evaluated for factual correctness, source-code grounding, localization accuracy, and consistency with independent verification. Explanation length should not be used as a proxy for explanation quality.
8.5.4. LLM with Static-Analysis Feedback
In this configuration, the LLM receives findings from a static analyzer and is asked to reassess the code or propose a correction. This baseline represents a hybrid approach in which an LLM uses external analysis feedback without CRAFT-Sec's complete evidence-fusion and interpretability architecture.
Experimental purpose: To determine whether CRAFT-Sec offers benefits beyond a simpler combination of an LLM and static analysis.
Evaluation considerations: The static analyzer, ruleset, feedback format, and number of refinement iterations must be fixed. The comparison should use the same analyzer configuration as the standalone static-analysis baseline.

8.6. Explainability Baselines
The explainability comparison evaluates whether CRAFT-Sec produces explanations that are more faithful to model behavior, more stable under controlled perturbations, and more useful for identifying vulnerable code locations.
The following methods are proposed as explainability baselines.
8.6.1. Gradient-Based Saliency
Gradient-based saliency estimates the sensitivity of a model's output to its input representation. For source code, gradients should be calculated with respect to token embeddings or another differentiable representation.
Experimental purpose: To establish a basic gradient-based reference for identifying input elements associated with a vulnerability prediction.
Evaluation considerations: Gradients with respect to discrete token identifiers are not directly meaningful. The implementation must use a valid differentiable representation, such as token embeddings, and should document the aggregation method used to convert embedding-level attribution into token or line scores.
8.6.2. Integrated Gradients
Integrated Gradients attributes a model prediction to input features by integrating gradients along a path between a baseline representation and the observed input [15].
Experimental purpose: To compare CRAFT-Sec's explanation method with a widely used attribution approach that accounts for changes between a reference input and the evaluated input.
Evaluation considerations: The baseline embedding and interpolation procedure must be specified. The evaluation should examine sensitivity to baseline selection and should not assume that attribution magnitude establishes causal influence.
8.6.3. SHAP
SHAP provides feature attribution using a Shapley-value-based framework for explaining model predictions [15].
Experimental purpose: To assess whether CRAFT-Sec provides more stable and computationally practical explanations than a feature-attribution method based on contributions to a prediction.
Evaluation considerations: The feature representation and background distribution must be fixed. Since source-code tokens and program structures can produce a large feature space, the selected SHAP approximation and computational budget must be documented.
8.6.4. Attention-Based Explanation
Attention weights from transformer models may be aggregated to identify tokens or code regions receiving high attention scores.
Experimental purpose: To evaluate whether attention-derived token importance provides a useful localization reference compared with CRAFT-Sec's evidence-grounded localization.
Evaluation considerations: Attention weights should be treated as a diagnostic signal, not automatically as faithful explanations of model predictions. Their usefulness must be assessed through perturbation and intervention-based tests.
8.6.5. SAE Feature Attribution Without Interaction Analysis
This baseline uses SAE-derived latent feature activations to explain vulnerability predictions but removes the explicit feature interaction analysis component.
Experimental purpose: To isolate the contribution of feature interaction analysis from the contribution of SAE feature extraction itself.
Evaluation considerations: The SAE architecture, dictionary size, training data, and activation extraction procedure must remain identical to those used in the full framework.

8.7. Automated Program Repair Baselines
The automated repair comparison evaluates whether CRAFT-Sec can generate patches that eliminate identified vulnerabilities while preserving required program behavior and avoiding new security defects.
Repair approaches differ substantially in their assumptions, input requirements, and supported languages. Therefore, the comparison will distinguish traditional automated program repair, learning-based repair, and LLM-based repair.
8.7.1. GenProg
GenProg is a search-based automated program repair technique that uses genetic programming to search for patches that satisfy a test suite [17].
Experimental purpose: To establish a traditional search-based repair baseline and evaluate the effectiveness of CRAFT-Sec relative to test-guided patch search.
Evaluation considerations: GenProg requires compatible execution and test environments. Its results should be reported only for supported benchmark programs and reproducible configurations.
8.7.2. TBar
TBar is a template-based automated program repair approach that applies predefined repair templates to generate candidate patches.
Experimental purpose: To compare CRAFT-Sec against a repair method that relies on predefined transformations rather than neural security reasoning.
Evaluation considerations: The available implementation and benchmark compatibility must be verified. Its template set and repair configuration must be fixed before test evaluation.
8.7.3. AlphaRepair
AlphaRepair is a learning-based program repair approach based on pretrained code representations and repair-oriented generation.
Experimental purpose: To compare CRAFT-Sec with a pretrained-model-based repair method and assess whether vulnerability-specific localization and evidence integration improve patch effectiveness.
Evaluation considerations: The repair input, fault-location information, model configuration, and candidate-generation budget must be documented. Results obtained with ground-truth fault locations must be separated from results obtained with predicted locations.
8.7.4. Direct LLM-Based Repair
A general-purpose LLM receives the vulnerable code and a fixed repair instruction. It generates one or more candidate patches without CRAFT-Sec's specialized evidence-fusion and validation pipeline.
Experimental purpose: To determine whether CRAFT-Sec's repair architecture provides benefits beyond directly prompting an LLM to fix vulnerable code.
Evaluation considerations: The prompt, model version, number of candidates, decoding settings, and token budget must be controlled. The LLM must not receive the ground-truth patch or hidden test information.
8.7.5. LLM-Based Repair with Static-Analysis Feedback
The LLM receives the original code and findings from a static analyzer. It generates a patch and may use subsequent analyzer feedback within a predefined refinement limit.
Experimental purpose: To establish a stronger hybrid repair baseline and determine whether CRAFT-Sec's multi-source evidence and explicit patch validation provide benefits beyond static-analysis-guided LLM repair.
Evaluation considerations: The number of repair attempts, feedback iterations, analyzer configuration, and total token budget must be fixed. All generated patches must be subjected to the same independent validation procedure.

8.9. Ablation Study Design
The ablation study is intended to quantify the contribution of each major CRAFT-Sec component. The complete framework will serve as the reference configuration. Each ablation will remove one component while preserving the remaining components and keeping the underlying dataset partitions, model checkpoints, training procedure, and evaluation protocol unchanged.
Let the complete CRAFT-Sec configuration be represented as:
[
\mathcal{C}_{full} = {SAE, INT, AST, CFG, DFG, TAINT, FUS, RISK, VAL}
]
where:
                                             * (SAE) denotes SAE-based security feature extraction.
                                             * (INT) denotes feature interaction analysis.
                                             * (AST) denotes abstract syntax tree analysis.
                                             * (CFG) denotes control-flow graph analysis.
                                             * (DFG) denotes data-flow graph analysis.
                                             * (TAINT) denotes taint analysis.
                                             * (FUS) denotes multi-feature evidence fusion.
                                             * (RISK) denotes security risk scoring.
                                             * (VAL) denotes patch validation.
For each ablation, one component is removed while the remaining components are retained. The purpose is to estimate the marginal contribution of the removed component under the selected experimental configuration.
8.9.1. Ablation A1: Without SAE Feature Extraction
Configuration: Remove SAE-based latent feature extraction. The framework retains the original model representations and the remaining program-analysis components.
Purpose: To determine whether SAE-derived features provide useful information beyond conventional transformer representations and explicit program-analysis evidence.
Expected analytical observation: The experiment will establish whether removing SAE features changes detection performance, explanation faithfulness, localization quality, or repair effectiveness. It will also reveal whether SAE extraction provides measurable benefits for white-box models.
Important constraint: For black-box models that do not expose internal activations, SAE extraction is unavailable by design. Such models should be evaluated through the source-code analysis pathway and must not be counted as an SAE ablation result.
8.9.2. Ablation A2: Without Feature Interaction Analysis
Configuration: Retain SAE feature extraction but remove explicit feature interaction computation. The system may still use individual SAE activations, but it will not calculate or use interaction terms in the evidence representation.
Purpose: To determine whether relationships among latent features contribute information beyond the independent contribution of each feature.
Evaluation focus: Compare detection, explanation, and localization performance against the complete framework. Where feasible, use controlled feature interventions to examine whether observed interaction effects reflect behavior changes rather than simple co-activation.
Important constraint: Co-activation or correlation alone must not be interpreted as evidence of causal interaction.
8.9.3. Ablation A3: Without AST Analysis
Configuration: Remove AST-derived structural features while retaining other available evidence sources.
Purpose: To evaluate the contribution of syntactic structure to vulnerability identification and localization.
Evaluation focus: Examine vulnerabilities that depend on syntax-sensitive relationships, such as unsafe function calls, expression structure, argument usage, and syntactic context.
Important constraint: The remaining components must not silently reconstruct the removed AST feature channel. If another component requires parsing, the parser may remain as an implementation dependency, but AST-derived evidence must be excluded from the ablated prediction and fusion inputs.
8.9.4. Ablation A4: Without CFG Analysis
Configuration: Remove explicit control-flow graph evidence from the framework.
Purpose: To determine whether modeling control-flow relationships contributes to the detection of vulnerabilities that depend on execution paths, branching conditions, loops, or unreachable and conditionally executed operations.
Evaluation focus: Measure changes in detection and localization performance, particularly for path-dependent vulnerability categories.
Important constraint: CFG-dependent evidence must be excluded from the model input and evidence-fusion process. Other analyses may continue using their own permitted representations.
8.9.5. Ablation A5: Without DFG Analysis
Configuration: Remove data-flow graph construction and its derived evidence from the framework.
Purpose: To evaluate the contribution of explicit data dependencies and value propagation relationships to vulnerability detection and localization.
Evaluation focus: Analyze vulnerabilities involving the propagation of untrusted data, unsafe assignments, variable dependencies, and sensitive operations.
Important constraint: DFG evidence must be excluded from fusion even if a transformer baseline internally encodes some data-flow information. The retained model configuration must be documented so that implicit and explicit data-flow representations are not confused.
8.9.6. Ablation A6: Without Taint Analysis
Configuration: Remove source-to-sink taint propagation and sanitizer-aware evidence from the framework while retaining the remaining program-analysis channels.
Purpose: To determine whether explicit tracking of untrusted inputs through the program contributes to the identification of injection, command execution, path traversal, and related vulnerabilities.
Evaluation focus: Compare detection and localization performance on vulnerability categories for which source-to-sink relationships are relevant.
Important constraint: The taint-analysis rules, source definitions, sink definitions, and sanitizer models must be specified before evaluation. A missing taint path must not be interpreted as proof that a program is safe.
8.9.7. Ablation A7: Without Multi-Feature Evidence Fusion
Configuration: Remove the learned or weighted integration of evidence sources. Individual components remain available, but the framework uses a predefined single-source or non-fused decision mechanism.
Purpose: To measure the value of combining neural, SAE, structural, control-flow, data-flow, and taint evidence.
Evaluation focus: Compare the complete fusion mechanism against individual evidence channels and a simple non-fused decision rule. The comparison should determine whether integrated evidence improves detection reliability, calibration, and localization.
Important constraint: The non-fused alternative must be defined explicitly. For example, it may use the neural detector as the sole decision source. A majority-vote configuration may be reported as an additional baseline, but it should not be substituted silently for the primary ablation.
8.9.8. Ablation A8: Without Security Risk Scoring
Configuration: Remove the risk-scoring component while retaining vulnerability detection, evidence fusion, localization, and repair.
Purpose: To determine whether explicit risk prioritization provides value beyond binary vulnerability classification and raw confidence scores.
Evaluation focus: Examine the ranking quality of detected findings, prioritization of high-impact vulnerabilities, and the relationship between assigned risk levels and independently assessed vulnerability severity.
Important constraint: Vulnerability probability and vulnerability severity are different quantities. The ablation must not replace severity assessment with classifier confidence or interpret a high prediction probability as evidence of high impact.
8.9.9. Ablation A9: Without Patch Validation
Configuration: Remove the explicit post-generation patch validation stage. The system returns generated repair candidates without requiring the complete validation process used by CRAFT-Sec.
Purpose: To quantify the importance of validating generated patches rather than treating generation as evidence of successful repair.
Evaluation focus: Compare candidate generation rate with accepted repair rate, functional correctness, targeted vulnerability mitigation, and security regression rate.
Important constraint: The ablated configuration must not be allowed to report generated patches as successful fixes. Its output should be recorded as unvalidated candidate patches. For fair evaluation, all candidates from all repair systems must still be independently assessed by the same external evaluation harness, even when the ablated system itself does not perform validation.

8.12. Additional Interaction and Cumulative Ablation Experiments
One-component-at-a-time ablations provide an interpretable estimate of the marginal contribution of each component, but they cannot fully identify dependencies among components. 8.12.1. Neural-Only Configuration
This configuration retains the base neural vulnerability detector but removes SAE extraction, feature interaction analysis, and explicit program-analysis evidence.
Purpose: To establish the performance of the underlying neural detector before the proposed interpretability and program-analysis mechanisms are introduced.
8.12.2. Neural + Program Analysis Configuration
This configuration combines the neural detector with AST, CFG, DFG, and taint evidence but excludes SAE-based feature extraction and latent feature interaction analysis.

8.12.3. Neural + SAE Configuration
This configuration retains neural vulnerability detection, SAE feature extraction, and feature interaction analysis but excludes AST, CFG, DFG, and taint evidence.
Purpose: To examine the contribution of mechanistic interpretability without explicit program-structure and data-flow evidence.
8.12.4. Full Evidence Without Risk Scoring
This configuration retains the complete detection and evidence-fusion pipeline but removes the risk-scoring mechanism.
Purpose: To isolate the effect of risk prioritization from the effect of vulnerability detection itself.
8.12.5. Repair Without Internal Validation
This configuration generates patches using CRAFT-Sec's repair mechanism but removes its internal patch-validation stage.
Purpose: To measure how often generated candidates fail independent functional or security verification and to quantify the difference between patch generation and accepted repair.

8.13. Fair Comparison Protocol
A fair comparison requires that differences in observed performance arise from the methods being evaluated rather than differences in data, preprocessing, test exposure, or computational resources. The following controls will be applied.
8.13.1. Common Dataset and Ground-Truth Protocol
All compatible baselines will be evaluated on identical test instances. Training, validation, and test partitions will be defined before model development. The same ground-truth vulnerability labels and CWE mappings will be used across methods.
Where a method cannot process the complete dataset because of language or input-format limitations, it will be evaluated on the largest compatible subset. The exact subset will be reported, and comparisons with CRAFT-Sec will be repeated on that same subset.
Function-level and line-level evaluation will be kept separate. A method that predicts only function-level vulnerability labels will not be assigned line-level scores unless a separate localization mechanism is implemented and evaluated.
8.13.2. Consistent Preprocessing
A common preprocessing specification will define source-code decoding, file filtering, language identification, duplicate handling, and label normalization. However, the original input representation required by each baseline will be preserved where necessary.
For example, a graph-based model may require graph extraction, while a transformer may require tokenization. These method-specific transformations are permitted, but they must be deterministic, documented, and applied consistently to the relevant training, validation, and test partitions.
The preprocessing pipeline must not remove security-relevant information from one method while retaining it for another without documenting the difference.
8.13.3. Hyperparameter Selection
Hyperparameters will be selected using the training and validation partitions only. Test-set performance must not be used to select thresholds, prompts, model checkpoints, feature dimensions, or repair configurations.
For trainable baselines, the hyperparameter search space and optimization budget should be defined before final testing. Where exact reproduction of a published method is feasible, its reported configuration should be used as the primary reproduction setting, with additional tuning reported separately.
8.13.4. Common Evaluation Metrics
The primary detection metrics will include precision, recall, F1-score, MCC, and PR-AUC. Localization will be evaluated using line-level precision, recall, F1, IoU, and Hit@k where valid ground truth exists.
Explainability methods will be compared using comprehensiveness, sufficiency, attribution faithfulness, and stability. Repair methods will be assessed using accepted patch success, functional correctness, targeted vulnerability mitigation, and security regression rate.
Metrics must be calculated from the same underlying test instances and ground-truth annotations. If a metric is not applicable to a method, it will be marked as not applicable rather than assigned a misleading value.
8.13.5. Threshold Selection and Calibration
For methods that output continuous vulnerability scores, decision thresholds will be selected using the validation partition. The selected threshold will remain fixed during test evaluation.
Where a tool produces severity categories rather than calibrated probabilities, its native severity output should be preserved and evaluated using suitable ranking or threshold-based analyses. A native severity label must not be interpreted as a calibrated probability.
8.13.6. Fault Localization Control for Repair
Repair performance depends partly on whether the vulnerable location is known. To separate repair capability from fault-localization capability, two repair settings will be considered:
                                             1. Oracle-localization setting: The repair system receives the ground-truth vulnerable location.
                                             2. Predicted-localization setting: The repair system receives the location predicted by the corresponding detection or localization method.
The oracle-localization experiment measures repair capability when localization is controlled. The predicted-localization experiment evaluates the end-to-end repair pipeline.
Results from these settings must be reported separately. An approach receiving the ground-truth location must not be compared directly with one required to identify the location independently.
8.14. Computational Budget and Resource Control
The comparison will use a documented computational budget to prevent one approach from receiving substantially greater resources than another. However, identical hardware alone does not guarantee equal computational effort because static analyzers, transformer models, and generative LLMs have different resource requirements.
The evaluation will therefore report both resource consumption and performance under clearly defined budget constraints.
8.14.1. Training Budget
Trainable models will receive predefined training limits, including maximum epochs, early-stopping conditions, batch size constraints, and hyperparameter-search budgets. The same training data will be used for comparable model configurations.
Pretrained models may use their original checkpoints, but additional fine-tuning must be reported separately. Training cost and inference cost should not be combined into a single runtime measurement.
8.14.2. Inference Budget
Inference evaluation will record:
                                             * Total analysis time.
                                             * Average time per code sample.
                                             * Peak memory usage.
                                             * CPU and GPU utilization where available.
                                             * Number of model inference calls.
                                             * Input and output token counts for LLM-based methods.
                                             * API or computational cost where applicable.
                                             * Tool failures, timeouts, and unsupported samples.
For LLM-based methods, the maximum number of requests, output-token limit, context length, and refinement iterations will be fixed in advance.
8.14.3. Repair Budget
Repair systems will receive a predefined candidate-generation budget. The maximum number of candidate patches, refinement iterations, and model calls per vulnerable instance will be recorded.
The evaluation will report both the best accepted patch under the fixed budget and the total resources required to obtain it. A method must not be given unlimited candidate generation while competing methods receive a restricted number of attempts.

8.15. Data Leakage Prevention
Data leakage is a major threat to the validity of vulnerability detection and repair experiments. Source-code datasets may contain duplicate functions, related commits, vulnerable and patched versions of the same code, or samples originating from overlapping repositories. If related examples appear in both training and test partitions, a model may achieve artificially high performance by memorizing code patterns rather than learning generalizable security properties.
CRAFT-Sec will use the following leakage-prevention procedures.
8.15.1. Duplicate and Near-Duplicate Detection
Exact duplicate source-code samples will be identified using normalized source-code hashes. Near-duplicate samples will be identified using token similarity, structural similarity, or other suitable similarity measures.
Normalization may include removing irrelevant whitespace and comments while preserving security-relevant syntax and semantics. The normalization procedure must be documented because overly aggressive normalization may merge distinct programs.
Samples identified as duplicates or near duplicates will be assigned to the same partition or removed according to a predefined policy.
8.15.2. Repository-Level Separation
Where repository metadata is available, repository-level separation will be used to reduce the likelihood that related functions from the same project appear in both training and test partitions.
For datasets that contain multiple versions of the same repository, related versions should be grouped to prevent cross-partition contamination. If repository-level separation is impossible because the dataset lacks metadata, this limitation must be stated.
8.15.3. Commit and Vulnerable-Fix Pair Separation
Vulnerable and patched versions of the same function or commit must not be split across training and test partitions in a way that allows direct memorization.
Where vulnerable-fix pairs are available, both members should be grouped during partitioning. Repair evaluation must also ensure that the reference patch is not exposed to the model during training, prompt construction, or candidate generation.
8.15.4. Temporal Separation
Where collection dates or commit timestamps are available, a temporal evaluation may be performed. Older samples will be used for training and validation, while newer samples will form a separate test set.
This setting provides an additional assessment of generalization to code and vulnerabilities that occur after the training period. The temporal cutoff must be defined before model training.
8.15.5. Prompt and Retrieval Leakage Prevention
Few-shot examples, retrieval indexes, and LLM context documents must be constructed exclusively from permitted training data or public technical documentation that does not reveal test labels or patches.
The evaluation system must not retrieve ground-truth test annotations, expected fixes, hidden test cases, or benchmark-specific answer files during inference.
8.15.6. Pretrained Model Contamination
Pretrained code models and general-purpose LLMs may have encountered public benchmark samples during pretraining. Complete verification of pretraining corpora may be impossible, particularly for proprietary models.
The study will therefore record known model training cutoffs where available, prefer temporally separated or newly collected evaluation samples where feasible, and disclose the limitations of contamination assessment. A model's lack of disclosed training data must not be interpreted as proof that it has not encountered benchmark examples.

8.16. Statistical Analysis of Baseline and Ablation Results
The statistical analysis will determine whether observed performance differences are consistent and practically meaningful rather than consequences of random initialization, sample selection, or model stochasticity.
Trainable methods will be evaluated using repeated runs with predefined random seeds. Where applicable, paired comparisons will be conducted using predictions on the same test samples.
For metric comparisons, the study will report:
                                             * Mean and standard deviation across repeated runs.
                                             * 95% confidence intervals.
                                             * Absolute and relative performance differences.
                                             * Appropriate effect sizes.
                                             * Paired statistical tests where the comparison is matched.
                                             * Multiple-comparison correction for groups of baseline and ablation tests.
                                             * Per-dataset, per-language, and per-CWE results.
The choice of statistical test will depend on the metric distribution and experimental design. Paired tests will be preferred when two methods are evaluated on the same samples. Non-parametric alternatives will be considered when distributional assumptions are not adequately supported.
The primary statistical comparison will focus on the complete CRAFT-Sec configuration against the strongest compatible baseline in each task category. Secondary comparisons will examine the remaining baselines and the nine primary ablations.
A statistically significant difference will not automatically be interpreted as practically important. Effect sizes, confidence intervals, computational cost, and the magnitude of the improvement will be considered together.
For ablation experiments, the estimated difference between the full framework and an ablated configuration will be reported separately for each primary metric. Multiple-comparison correction will be applied when testing several components or metrics to reduce the risk of false-positive conclusions.
8.17. Result Reporting and Interpretation Strategy
The results will be organized into separate tables for detection, localization, explainability, prevention, and repair. This separation is necessary because a method may perform well in vulnerability classification while providing weak explanations or generating ineffective patches.
8.17.1. Detection Comparison
The detection table will report precision, recall, F1-score, MCC, and PR-AUC for all compatible baselines. Results will be stratified by dataset, programming language, and CWE category where sufficient samples exist.
8.17.2. Explainability and Localization Comparison
The explainability table will report comprehensiveness, sufficiency, attribution faithfulness, and attribution stability. The localization table will report line-level F1, IoU, Hit@k, and MRR where valid line-level annotations are available.
The interpretation will distinguish prediction attribution from evidence-grounded vulnerability explanation. A visually plausible explanation will not be considered faithful without an appropriate evaluation.
8.17.3. Repair Comparison
The repair table will distinguish candidate generation, compilation, functional test success, targeted vulnerability mitigation, and final accepted patch success.
The study will report the number of generated candidates and the number that satisfy the complete acceptance criteria. This prevents a system that generates many candidates from appearing more effective merely because it produces more outputs.
8.17.4. Prevention Comparison
The prevention table will compare vulnerable-output rates and functional correctness under matched generation tasks. The same prompts, model versions, decoding settings, and evaluation procedures should be used for baseline and security-aware configurations.
A reduction in detected vulnerabilities must be considered alongside functional correctness. A system that avoids vulnerability by refusing to generate useful code or removing required functionality must not be interpreted as a successful secure-generation approach.
8.17.5. Ablation Comparison
The ablation table will report the full framework alongside each component-removal configuration. The interpretation will identify which components contribute to which outcomes rather than assuming that every component improves every metric.
For example, removing patch validation may have little effect on the vulnerability detector's raw classification score while substantially affecting the number of patches that can legitimately be accepted. Such task-specific effects are expected to be reported separately.
8.18. Threats to Validity
Several threats may influence the interpretation of the baseline and ablation experiments.
Construct validity: Vulnerability labels may not fully represent exploitability or contextual security impact. Static-analysis findings and model predictions must therefore be checked against independent ground truth wherever possible.
Internal validity: Differences in preprocessing, hyperparameter tuning, model access, or computational budgets may affect performance. The common evaluation protocol and documented resource limits are intended to reduce these effects.
External validity: Results from a limited set of programming languages, datasets, model families, or CWE categories may not generalize to all software projects. The study should report the supported scope and avoid universal claims.
Data validity: Dataset duplication, mislabeled examples, vulnerable-fix pair leakage, and incomplete annotations may distort evaluation. The proposed deduplication, grouping, and leakage-prevention procedures are intended to reduce these risks.
Explanation validity: Attribution methods may be sensitive to baselines, perturbations, and representation choices. Explanations should be evaluated through multiple complementary measures rather than a single attribution score.
Repair validity: A patch that passes a finite test suite may still contain vulnerabilities or violate untested requirements. Independent security analysis and, where feasible, expert review should supplement automated tests.
Reproducibility: Proprietary LLM versions, changing APIs, unavailable tool configurations, and nondeterministic generation may affect repeatability. Exact model identifiers, software versions, prompts, seeds, configurations, and execution dates should be recorded.
8.19. Summary
This section defines a comprehensive experimental comparison strategy for evaluating CRAFT-Sec against traditional static analyzers, machine learning-based vulnerability detectors, transformer-based models, LLM-based security analysis methods, explainability techniques, and automated program repair systems.
The proposed ablation study removes nine major components individually to examine the contributions of SAE feature extraction, feature interaction analysis, AST analysis, CFG analysis, DFG analysis, taint analysis, evidence fusion, risk scoring, and patch validation. Additional cumulative configurations are proposed to investigate interactions between neural representations, mechanistic interpretability, program analysis, and repair validation.
Fair comparison will be supported through common test instances, documented compatibility subsets, controlled threshold selection, consistent metrics, explicit computational budgets, and separate oracle-localization and predicted-localization repair settings. Data leakage prevention will address duplicate code, repository overlap, vulnerable-fix pairs, temporal contamination, retrieval leakage, and potential pretrained-model contamination.
The resulting experimental design is intended to determine not only whether CRAFT-Sec performs competitively against existing approaches, but also which components contribute to its effectiveness, under what conditions those contributions occur, and what computational and validation costs are associated with the proposed framework. All conclusions will be based on measured experimental evidence rather than assumed improvements.
